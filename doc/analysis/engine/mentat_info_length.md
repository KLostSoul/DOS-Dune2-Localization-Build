# 멘타트 하코넨 설명의 INFO 길이 오류

2026-10-22. 사용자는 `dalmuri639-original-flow`에서 멘타트 정지가 해결되고 설명이 출력되는 것을 확인했다. 이후 아트레이데스 멘타트의 하코넨 설명에서 일부 글자 노이즈와 다른 설명 문구가 섞이는 캡처를 제공했다.

## 원인

해당 항목은 `MENTATA.ENG`의 5번 설명이다. 원문은 `FHARK.WSA*Giedi Prime: \x0CThe Harkonnen...`이고 번역은 `기에디 프라임: ... 잔인하고 포악하며 공정한 경쟁이나 인간의 생명을...`이다.

앞선 수정에서 IFF 청크 위치·길이는 고쳤지만 **INFO 페이로드의 최대 읽기 길이를 영문 값으로 보존한 것이 잘못이었다.** 새 설명의 저장 크기는 NUL을 포함해 329바이트인데 INFO는 209바이트를 지정한다. 따라서 파일 끝 NUL이 작업 버퍼에 들어오지 않는다. 원본 압축 해제는 NUL까지 읽으므로 작업 버퍼의 이전 데이터까지 계속 해석할 수 있다. 이는 폰트 슬롯의 원본 픽셀이 달라진 문제와 구분된다.

## 원본 읽기 명령

원본 모듈 196의 `32E3:059B`에서 다음 경로를 확인했다.

- `32E3:0616..062B`: INFO 12바이트를 지역 버퍼에 읽는다.
- `32E3:064D..065D`: INFO+8의 DWORD를 바이트 순서 변환하여 저장한다.
- `32E3:06A8..06B5`: 그 DWORD를 설명 파일 읽기 길이로 전달한다.
- `32E3:06BD..06CE`: 원본 `2307:00F4`로 쌍 압축을 해제한다.
- `32E3:06D1..06E2`: 원본 `2307:0002`로 ESC 고위 바이트를 해제한다.

이 읽기 경로는 공통 문자 출력보다 먼저 실행된다. INFO+4의 최대 전개 길이도 읽지만, 이 함수에서 그 값을 작업 버퍼 주소의 오프셋으로 사용한다고 해석하지 않았다. 입력 버퍼는 별도 `GetBuffer(3)` 결과이며, 출력 버퍼는 게임 공용 포인터다.

REA 근거: `ev_bc9ddc2250afcb7c97797d6b96d6921fcf83f70ef25e605998f3a789d20dcfcb`. 원본 바이트를 추출한 분석용 컨테이너와 REA 기록은 `build/analysis/harkonnen-text/`에 보관했다. 해당 MZ는 정적 분석 컨테이너이며 게임 실행 파일이 아니다.

## 최소 수정

멘타트 세 파일의 INFO 페이로드 12바이트씩만 갱신했다. 청크 위치, 저장 문자열, 글리프, 후크, 치트, 실행 파일은 변경하지 않았다.

| 파일 | 항목 수 | 이전 최대 전개/읽기 | 새 최대 전개/읽기 | 이전 읽기 제한을 초과한 설명 |
|---|---:|---:|---:|---:|
| MENTATA.ENG | 47 | 334 / 209 | 392 / 392 | 31 |
| MENTATH.ENG | 49 | 363 / 227 | 449 / 449 | 26 |
| MENTATO.ENG | 47 | 382 / 238 | 365 / 365 | 25 |

최대 전개 길이는 쌍 압축 해제 단계와 ESC 해제 단계 모두의 크기를 NUL까지 포함해 계산한다. 한글 고위 바이트를 ESC로 저장하므로 첫 단계의 중간 바이트열은 최종 한글 토큰보다 크다. 최종 토큰 길이만으로 중간 버퍼 상한을 줄이지 않는다.

기준 빌드는 사용자가 멘타트 출력을 확인한 `build/dalmuri639-original-flow`로 보존했다. 수정 복사본은 `build/dalmuri639-original-flow-infofix`다. 현재 저장 파일도 기준 빌드의 source 폴더에서 복사했다. 수정 전 PAK는 새 폴더의 `ENGLISH.PAK.before-infofix`에 보관했다.

- EXE SHA-256: `c0d283360bdb88741624cd1ceee5bcf899fabb1db8ebb87baab9b4eb4194403c`로 동일.
- 새 PAK SHA-256: `a998d0f2f0c14464f569858105c729a2647709a20adb89facbc285b2d11c4af7`.
- `DUNEHAN.FNT`, `DUNEHAN.TBL`, 원본 DUNE.PAK, SCENARIO.PAK, 설정 파일 바이트 동일.
- 루트 `듄2_한글테스트.bat`은 새 복사본을 실행한다.

현재 멘타트 NAME·DESC·INFO 재생성은 `tools/build_game.py`의 `BuildInputs.rebuild_mentat()`가 맡는다. `tools/resources.py`는 공용 컨테이너·압축 코덱을 제공한다.

## 검증 범위

`tools/verify_mentat_info_pipeline.py`에서 새 세 가문의 143개 항목을 INFO의 실제 읽기 제한으로 읽고 원본 16비트 쌍 압축·ESC 해제 명령을 실행했다. 선언한 메모리 버퍼에서 모든 항목의 NUL이 읽히고 해제 결과가 전체 저장 문자열의 기대 결과와 일치했다.

하코넨 5번 항목은 이전 읽기 제한 209에서 파일의 NUL을 읽지 못했고, 이전 임무 문자열을 작업 버퍼에 둔 모형에서 기대 출력과 달라지는 것을 재현했다. 새 제한 392에서는 저장된 329바이트와 NUL이 모두 포함되어 전체 기대 바이트열과 일치했다. 캡처 순간의 실제 잔여 RAM을 확보한 것은 아니므로 노이즈 픽셀 하나하나를 동일하게 재현했다고 기록하지 않는다.

결과: `build/analysis/cleanup-2026-10-24/evidence/dalmuri639-original-flow-infofix/info-pipeline-verification.json`. 위 명령 검증은 에이전트가 수행했으며 DOSBox-X는 실행하지 않았다. 이후 실제 게임 출력에 대한 사용자 확인은 아래에 별도로 기록한다.

## 사용자 정상 출력 확인 — 2026-10-22

사용자는 INFO 길이 수정 후 현재 빌드가 정상적으로 출력된다고 확인했다. 앞서 확인한 멘타트 정지 해소와 함께, 하코넨 설명에서 보고한 출력 이상도 수정 후 정상 출력된 결과로 기록한다. 이것은 사용자가 확인한 화면의 결과이며, 세 가문 143개 항목과 게임 전체 화면을 모두 직접 실행해 확인했다는 뜻은 아니다.

현재 **사용자 정상 출력 확인 기준 빌드**는 `build/dalmuri639-original-flow-infofix`다. 실행 배치는 작업 공간 루트의 `듄2_한글테스트.bat`이며, 실제 대상은 해당 폴더의 `run_dalmuri639.bat`이다. EXE SHA-256은 `c0d283360bdb88741624cd1ceee5bcf899fabb1db8ebb87baab9b4eb4194403c`, ENGLISH.PAK SHA-256은 `a998d0f2f0c14464f569858105c729a2647709a20adb89facbc285b2d11c4af7`이다. 후속 작업은 이 확인된 빌드를 기준으로 한다.

## 남은 시각적 과제: 한글 테두리

정상 출력 확인과 별도로 사용자는 한글에 검은 테두리가 없어 배경 위에서 윤곽이 잘 보이지 않는다고 지적했다.

- 원본 `NEW6P.FNT`와 `NEW8P.FNT`의 실제 A·M 글리프를 확인한 결과, 글자 본체 색상 인덱스 1 외에 테두리·그림자 인덱스 2·3이 비트맵에 들어 있다. 표시 색은 원본 스타일 색 변환표를 따른다.
- 현재 달무리 변환은 배경 0과 본체 1만 생성한다. 원본 픽셀 출력기를 사용하는 것만으로 2·3의 테두리 픽셀이 자동 생성되지는 않는다.
- 원본 규칙에 맞춘 한글 테두리 추가는 미적용 상태다. 사용자는 먼저 현재 정상 출력 결과를 문서에 기록하라고 지시했으며, 이번 기록 작업에서 글꼴이나 실행 파일은 수정하지 않았다.
