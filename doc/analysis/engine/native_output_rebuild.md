# 멘타트 리소스와 원본 출력 인터페이스

## 원본 멘타트 구조

상주 주소와 호출 규약은 [원본 FNT 엔진 분석](font_engine.md), 화면별 경로는 [FNT 디버그 기록](font_runtime_debug.md)을 참조했다. 과거 잘못된 오버레이 범위에 붙인 논리 주소는 실제 파일 오프셋과 FBOV flags=3 코드 범위로 다시 확인했다.

```text
원본 PAK / IFF / ENG 읽기
  → 원본 압축 해제
  → 화면별 설명문·행·위젯 준비
  → 원본 폭 계산 / 줄바꿈 / 서식·정렬
  → 29C7:0004 문자 루프
  → 원본 DS:[66D8] = 20AA:07BD
  → 원본 FNT 오프셋·폭·높이·색 변환
  → 원본 20AA:0E02 활성 페이지 선택
  → 픽셀 출력
```

이 경로를 지키는 것이 재작성의 기준이다. 단순히 글리프 출력기 일부가 원본과 같다는 이유로 앞 단계의 구조도 정상이라고 판단하지 않는다.

## NAME·DESC·INFO의 길이와 오프셋

기존 포장기는 번역으로 `NAME` 청크 길이가 달라진 뒤에도 원본 청크 사이의 패딩과 `DESC` 크기 필드를 그대로 복사했다. 문자열을 다시 읽어 번역 바이트와 비교하는 검사는 통과해도 원본 IFF 탐색기는 다음 청크를 찾을 수 없었다.

아트레이데스 파일의 정확한 차이는 다음과 같다. 위치는 MENTATA.ENG 파일 안의 0부터 시작하는 바이트 오프셋이다.

| 항목 | 원본 | 결함 구현 | 재구성 구현 |
|---|---:|---:|---:|
| NAME 페이로드 크기 | 861 | 800 | 800 |
| NAME 뒤 필요한 패딩 | 1 | 0 | 0 |
| 실제 NAME 뒤 패딩 | 1 | **1** | 0 |
| 규칙상 DESC 헤더 시작 | 882 | 820 | 820 |
| 실제 DESC 헤더 시작 | 882 | **821** | 820 |
| DESC 크기 필드 | 5,710 | **5,710으로 남음** | 10,838 |

원본 IFF 탐색/읽기 함수 `32B4:0098`, `32B4:01CD`는 길이에 1을 더하고 최하위 비트를 지워 다음 청크로 이동한다. 실제 명령은 `ADD DX,1 / ADC AX,0 / AND DX,FFFEh`다. 따라서 새 NAME 길이가 800이면 바로 뒤에서 DESC 헤더가 시작해야 한다. 결함 구현의 불필요한 0바이트를 만나면 `DESC` 대신 `00 44 45 53`을 청크 ID로 읽는다.

하코넨·오르도스는 NAME 패딩 외에도 DESC 크기가 번역 후 본문 크기로 갱신되지 않아 뒤의 INFO 청크 탐색이 맞지 않았다. INFO는 장식용 데이터가 아니라 원본 파일의 별도 12바이트 청크다. NAME·DESC·INFO를 각각 원본 규격대로 재작성해야 한다.

### 원본 IFF 명령으로 재현한 결과

원본 모듈 187의 코드를 바꾸지 않고 CPU에서 실행했다. 파일 읽기와 위치 이동 두 경계만 메모리 바이트열로 모형화했다. 원본의 바이트 순서 변환과 청크 탐색 명령을 그대로 실행했다.

| 입력 | NAME 반환 크기 | DESC 반환 크기 | INFO 반환 크기 |
|---|---:|---:|---:|
| 원본 아트레이데스 | 861 | 5,710 | 12 |
| 새 아트레이데스 | 800 | 10,838 | 12 |
| 새 하코넨 | 841 | 10,177 | 12 |
| 새 오르도스 | 800 | 10,192 | 12 |
| 잘못 포장된 아트레이데스 표본 | 800 | **0** | **0** |

멘타트 포장기는 NAME·DESC의 짝수 패딩, 청크·FORM 길이와 24비트 본문 포인터를 재계산한다. INFO의 읽기·최대 전개 길이도 번역 후 데이터에서 계산한다. 상세 읽기 계약은 [INFO 길이](mentat_info_length.md)를 따른다.

LOGCPU 표본의 `4880:01F7 → 0251 → 0273 → 0362`는 IFF 읽기·바이트 순서 변환·청크 건너뛰기의 반환 위치와 일치한다. 실행 중 세그먼트·오프셋을 삽입 폰트 후크 주소로 바로 해석해서는 안 된다.

REA는 원본 모듈을 별도 분석용 MZ 컨테이너에 담아 분석했다. 게임용 바이너리가 아니다. 근거 `ev_40341c9e21c303c9208b1585e73df38e71acaf6b9a49a6d980efc7f4a28d2f9d`; 원본 바이트 위치는 `build/analysis/cleanup-2026-10-24/evidence/dalmuri639-original-flow/analysis/original-iff-reader-source.json`, 전체 REA 관측은 같은 폴더의 `original-iff-rea.json`에 있다.

## 한글 토큰과 원본 인터페이스

한글 FNT는 `D2DHAN2` 헤더 24바이트와 639개의 10바이트 레코드로 총 6,414바이트다. 레코드는 번호 2바이트와 완성 음절 비트맵 8바이트다. 원본 8×8 비트맵에 좌우 1픽셀 빈 열을 붙여 10픽셀 셀로 전달하고, 기존 수평 간격 값을 적용한다.

새 2바이트 토큰은 선행 `F8,F9,FB,FC,FD,FE`와 후행 `80..EA`를 사용한다. 6×107칸 중 639칸을 사용한다. 두 바이트 모두 ASCII 문장부호, 공백, CR, NUL, ESC, `%`와 겹치지 않는다. 비교 구현의 ASCII 후행 바이트가 문장 분할이나 서식 처리에서 별도 문자로 읽힐 수 있는 접점도 제거했다. 원본 압축 해제 코드는 그대로이며 저장할 때 두 고위 바이트를 기존 ESC 규칙으로 기록한다.

| 지점 | 유지한 계약 | 한글을 위한 명시적 확장 |
|---|---|---|
| `2326:0009` 단일 바이트 폭 | `[BP+6]` 바이트 인자, 폭과 간격 반환, 문자열 포인터를 받거나 변경하지 않음 | 원본 38바이트 명령을 그대로 옮기고 기존 진입점에서 연결 |
| `2326:002F` 전체 폭 | 원본 길이·누계·반환 구조 | 읽은 바이트 수를 반환받아 자신의 포인터와 카운터를 갱신 |
| `0EED:01B8` 일반 줄바꿈 | 원본 정방향 합산·역방향 공백 탐색·개행 기록 | 해당 루프가 반환된 문자 경계로 자신의 포인터를 갱신 |
| `32DD:1893` 설명문 분할 | 원본 문장부호·폭·페이지 분할 | 기존 FAR 호출 위치와 FBOV 재배치 위치에서 별도 읽기 진입점 호출 |
| `29C7:0004` 문자 출력 | 기존 CR, 좌표, 경계, 스타일, 줄 높이 | 폭 단계에서 토큰 폭 계산; 그리기 단계에서 글리프와 소비 바이트 수를 받아 SI를 직접 전진 |
| 고정 간격 문자 출력 | 원본 인자·피치·공통 렌더러 호출 순서 | 자신의 지역 버퍼를 3바이트 이상 확보해 한글 두 바이트와 NUL 저장 |
| `DS:[66D8]` | 원본 글리프 출력 주소 | 전역 후크로 바꾸지 않음 |
| `20AA:07BD` 픽셀 출력 | 원본 바이트 그대로 | 달무리 한 음절을 65바이트 Westwood FNT 작업 버퍼에 변환해 전달 |

고정 간격 함수의 실제 원본 진입 파일 오프셋은 `44624h`, 기존 렌더러 호출은 `44651h`다. flags=3 기준 모듈 180의 `3298:0854`, `3298:0881`에 해당한다. 이전 잘못된 범위표의 `2CA0:04FF`, `2CA0:052C` 표기는 새 패치 주소의 근거로 사용하지 않았다.

추가 함수는 반환 IP로 호출자를 추측하지 않는다. 부모 BP 프레임을 따라 올라가 문자열 포인터를 쓰지 않는다. 읽기 함수는 레지스터로 문자·길이·새 위치를 반환하고 각 원본 순회 루프가 그 값을 저장한다.

달무리 출력 때는 원본 드라이버 FNT 캐시를 자신의 스택에 저장하고, 한 슬롯의 Westwood FNT를 잠시 가리켜 원본 `[66D8]`를 호출한 뒤 캐시를 복원한다. 공통 폰트 전역, 원본 색 변환표와 활성 페이지 선택 코드는 유지한다. 자체 VGA 픽셀 루프는 없다. 639개 모두 원본 픽셀 명령으로 그려 소스 비트맵과 대조했다.

## 메모리 배치

| 부분 | 이미지 상대 세그먼트 / 크기 |
|---|---|
| 한글 확장 코드·작업 FNT·639음절 | `3D02h`, 7,568바이트 |
| 검증된 치트 | `3EDBh`, 2,448바이트 |
| 이동한 실행 중 스택 기준 | `3F74h` |
| MZ 적재 이미지 끝 | 파일 `44340h` |
| 원본 대비 상주 이미지 증가 | 10,016바이트 |
| 별도 DOS 한글 폰트 할당 | 0바이트 |
| 치트 화면 백업 XMS 요청 | 4,096바이트 |

폰트는 별도 DOS 블록을 만들지 않는다. 표의 상주 배치와 치트 스택은 해당 분석 표본의 값이다. 실제 실행 중 여유량은 MCB와 힙 상태로 따로 판정한다.
