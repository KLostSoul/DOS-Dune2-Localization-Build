# 보안 질문 생략과 임무 설명의 전환 구조

## 원래의 보안 종료 → 임무 설명 경로

보안 함수가 브리핑을 직접 호출하지 않아도, 정상 반환 뒤 다음 메인 루프의 상태 분기로 연결된다. 이 연결을 놓치고 별도 브리핑 경로를 새로 찾아야 한다고 했던 초기 결론은 철회한다.

| 순서 | 실제 모듈 주소 | 동작 |
|---|---|---|
| 1 | `1223:02A9`의 호출자 | `1223:03E6`에서 선택 문구 `DS:60C9`를 그리고 `040C`에서 원래 페이드아웃을 실행한다. |
| 2 | `1223:0432`, `0455` | `DS:38A6`이 1 또는 7이면 화면 자원을 처리하고 페이지 2를 페이지 0으로 320×200 전체 복사한다. 복사 인자는 `(0,0,0,0,40,200,2,0)`이다. |
| 3 | `1223:045D` → `32DD:0039` → `32DD:1099` | 보안 질문 호출. 최종 패치는 성공값 1을 원래 정리·반환 경로로 돌려준다. |
| 4 | `1223:04CA` 이후, `04EF`, `04F5` | 자원·오버레이 정리 후 `DS:38B2=1`, `DS:3792=0` 설정. |
| 5 | `044B:03FD` 호출에서 돌아온 다음 메인 반복 | 브리핑 대기 상태를 소비한다. 최종 패치는 이 상태에서만 앞선 팔레트 갱신을 건너뛴다. |
| 6 | `044B:01AD`, `01C5` → 게이트 `3314:0020` → 본체 `3314:0000` | 가문 `DS:3A2C`와 시나리오 `DS:38A4`를 넘겨 시나리오를 로드한다. `3314:001E`에서 준비하고 성공 후 `0091`에서 지도·유닛·건물 상태 등을 초기화한다. |
| 7 | `3314:0010..0019` → `3314:0C06` | `DS:3794==0`이면 임무 브리핑에 진입한다. |
| 8 | `3314:0C06 → 0C93 → 0E44` | 가문별 문자열 번호 `DS:38A6*4+4`와 `DS:8D99` 리소스로 설명을 준비한다. |
| 9 | `3314:0E5A` → 게이트 `32DD:0020` → 본체 `32DD:0000` | 멘타트 배경·설명 화면 준비. |
| 10 | `3314:0F13`, `0F2C` | 준비한 페이지 2를 표시 페이지 0으로 복사하고 `DS:3C26:3C28` 팔레트로 기존 페이드인 실행. |
| 11 | `3314:0F50` → 게이트 `32DD:0034` → 본체 `32DD:0AB8` | 기존 공통 멘타트 설명 출력. 폰트 상태 초기화 호출은 `32DD:0B60`, 본문 공통 포맷 호출은 `32DD:0DFF`. |

호출자의 `OR AX,AX / JNZ`에서 0은 화면 초기화가 아니라 종료로 연결된다. `FUN_1000:0377 → 0320 → 016B`를 따라 DOS `INT 21h/AH=4Ch`로 종료한다. 성공값 1을 유지해야 한다.

상위 `3283` 루틴은 시작·메인 루프 호출·종료를 감싼다. 메인 루프가 반환한 뒤 문자열 ID `0141h`(`DUNE.ENG #321`, `Thank you for playing Dune II.`)와 종료 정리를 처리한다. 이를 단순 종료 함수라고 부르거나, 그 반환 뒤에서 임무 브리핑을 찾은 것은 잘못이었다. 전환은 메인 루프 실행 중 처리된다.

## 페이드 뒤 정복 지도가 드러난 원인

호출자는 `1223:040C`에서 검게 페이드한 다음 `1223:0455`에서 페이지 2를 표시 페이지 0으로 복사했다. 보안 장면을 생략하면 이 페이지가 멘타트 보안 화면으로 덮이지 않는다. 복사 자체는 검은 팔레트 아래서 보이지 않을 수 있지만, 다음 메인 반복의 `044B:01AA`가 상태 검사보다 먼저 `044B:0559`를 호출해 게임 팔레트를 다시 적용할 수 있었다.

`044B:0559`는 색상 애니메이션 타이머가 만료되면 `DS:3C26/3C28` 팔레트를 `23A3:003A`에 넘긴다. 관련 호출은 `044B:05C2`, `06B9`, `073A`이며 갱신 시각의 간격은 각각 60틱, 3틱, 5틱이다. `23A3:003A → 29AA:0000` 드라이버는 캐시 `DS:712E`와 RGB 768바이트를 비교해 VGA DAC `03C8/03C9`에 색을 쓴다. 검은 페이드 상태에 게임 팔레트가 재적용되면 기존 페이지가 다시 보인다.

따라서 최종 수정은 **브리핑 대기 상태의 다음 메인 반복에서만 이전 팔레트 복원을 막고**, 시나리오와 브리핑 첫 프레임을 준비한 뒤 원래 페이드인으로 표시를 재개했다. 공통 설명 안에서도 같은 팔레트 함수를 사용하므로 전역으로 제거하지 않았다.

팔레트 처리는 임무 설명 대기 상태에 한정한다. 다른 화면에서도 사용하는 함수 자체를 제거하거나 별도 설명 호출을 삽입하지 않는다.

## 틱 카운터와 입력 대기의 적용 범위

- `1223:04FB..050C`는 `DS:608C/608E = DS:773C/773E + 300`을 기록한다. 같은 임무 종료 판정 함수의 다음 검사 시각이며, 메인 루프의 `DS:38B2==1` 분기는 이를 검사하지 않고 `3314:0000`으로 들어간다. 메인 루프가 `DS:31B0/31B2`에 300틱을 더하는 다른 위치도 `3314` 호출이 끝난 뒤다. 이 예약값은 브리핑 전 강제 대기가 아니다. 이 값을 임의로 제거하지 않았다.
- 실제 전환 전에는 시나리오 로딩, 지도 4,096개 항목 정리, 객체 구성, 문자열·WSA 준비가 있다. 각 작업의 실제 소요 시간 전체를 정적 분석으로 측정하지는 않았다. 최종 제거 대상은 확인된 공통 설명 함수의 첫 문장 전 30틱 가산이다.
- 과거 후보에서 지목한 `32DD:166E`(파일 `0x5177E`)의 `ADD DX,78h` 응답 루프는 그 후보의 진입 CFG에서 도달하지 않았다. 이를 회색 화면 지연의 원인으로 단정한 설명도 철회했다.

## MZ 로딩과 FBOV 주소 정정

분석 표본의 EXE SHA-256은 `642aabea9eb0b1c9945a5c17267b5c5b228ba237effdfccb85a5a04df379e7a3`였다. REA/Ghidra 12.1.4의 x86 16비트 리얼모드 MZ 로딩은 `verified`였다.

| MZ 항목 | 관측값 |
|---|---:|
| 헤더 | 19,456바이트 (`0x4C00`) |
| 초기화 모듈 | 260,480바이트 (`0x3F980`) |
| 파일 끝 오버레이·부가 데이터 | 102,130바이트 |
| 재배치 레코드 | 4,505개 |
| 독립 비교 검사 | 2,164개, 실패 0개 |
| MZ 진입점의 분석 적재 선형 주소 | `0x10000` |
| MZ/FBOV 경계 | 파일 `0x44580` |

MZ 헤더·본문·재배치 로더의 바이트 오독 증거는 없었다. 문제는 FBOV 오버레이를 기본 MZ 함수·호출 분석에 연결하지 못한 범위 한계였다. 자동 xref에 호출자가 없다는 결과를 실제 호출자가 없다는 의미로 해석하면 안 된다.

초기 분석은 파일 `0x36D10`의 FBOV 디렉터리 226개 항목에서 항목 169(`3208`, 크기 `FFFFh`, 플래그 `0004h`) 이후의 크기를 합산해 큰 블록으로 취급했다. 그 결과 같은 보안 함수에 `3208:3E3A`, 일부 분석 사본의 `3000:...` 주소를 붙였으나, 이 값들은 실제 실행 모듈 주소가 아니다. flag-3 모듈은 디렉터리 크기 합계가 아닌 **상주 게이트 헤더의 상대 파일 위치·코드 크기·fixup 크기**로 복원해야 한다.

| 올바른 FBOV 배정 | 값 |
|---|---|
| 디렉터리 항목 / 모듈 | 195 / `32DD` |
| 상주 게이트 시작 파일 위치 | `0x379D0` |
| 코드 시작·크기 | `0x50110` / `0x1A7C` |
| fixup 크기 / export | `0x018C` / 12개 |
| 보안 호출 게이트 | `32DD:0039`, 바이트 `CD 3F 99 10 00` |
| 보안 본체·파일 위치 | `32DD:1099` / `0x511A9` |
| 실제 상주 호출자 | `1223:045D`, 파일 `0x1728D`, 원시 `9A 39 00 DD 32` |

당시 Ghidra 상주 주소 `0x2263C`, `0x22685`, `0x2268D`, `0x22694`, `0x2271F`, `0x22725`, `0x2272B..0x2273C`는 분석 적재 선형 주소다. MZ 헤더가 있는 파일 오프셋과 혼용하지 않는다. 예를 들어 보안 호출 `1223:045D`는 Ghidra 선형 `0x2268D`, 파일 `0x1728D`다.

기존 실행 기록의 원시 스택·호출자 창은 세그먼트 재배치 부분을 제외해 대조했으며 원본과 수정 EXE에서 각각 유일하게 일치했다.

| 기존 실행 기록 | 원본 파일 | 수정 후보 파일 | 실제 주소 |
|---|---|---|---|
| 브리핑 초기 null 포맷, 반환 `48A7:0B65` | `0x4E310` | `0x50C70` | `32DD:0B60` |
| 가문 소개의 공통 본문 포맷 | `0x4E5AF` | `0x50F0F` | `32DD:0DFF` |

원본 모듈 `32DD`의 시작은 `0x4D7B0`이다. 브리핑 초기 호출은 기존 실행 관측이며, 본문 호출에서 직접 관측했던 문자열은 가문 소개였다. 임무 브리핑 본문 전체를 새로 실행 관측했다는 뜻은 아니다. 브리핑이 같은 `32DD:0AB8`로 진입함은 실제 게이트·호출 명령으로 확인했다.

분석용 이미지는 실제 코드와 상주 게이트가 겹치지 않도록 본체를 `6000:0000`에 격리했다. FAR 세그먼트 fixup은 실제 디렉터리와 MZ 분석 적재 세그먼트 `1000h`로 해석했다. `6000:0000`은 분석 좌표이며 실행 중 CS가 아니다. Ghidra의 함수·인자 형식 추론은 실제 명령·재배치·포트 출력과 대조했다. 당시 후보 모듈을 분리한 분석 MZ의 SHA-256은 `c9f6073a55ccbd35ef61ef1d1103bdfe5c4aee685009a89fef518f19bd312908`이며 게임 배치에 연결하지 않았다.

## 보안 리소스·원래 성공 처리

보안 본체는 `DS:3A2C`로 가문을 골라 `DS:2598/25A2/25AC`의 `FHARK.WSA`, `FARTR.WSA`, `FORDOS.WSA` 포인터를 선택한다. `DS:25B7`의 `PROTECT\0`(데이터 파일 `0x3A5D7`)를 리소스 선택 함수 `044B:075D`로 넘기는 호출은 파일 `0x51231`에 있다. 원시 `9A 5D 07 08 00`은 FBOV 게이트 규약으로 해석해야 한다. `0008:075D`를 보통 FAR 주소로 해석하면 연결이 사라진다. 당시 전체 EXE에서 확인한 `PROTECT` 참조는 이 인자 한 곳이었다.

추출 표에는 가문별 심문 서문, 정답·오답 응답, 질문과 그림 이름이 있다. 예를 들어 #1은 하코넨에 대한 충성 심문, #10은 `What type of structure is this?`다. 원래 시도 카운터는 0에서 시작하고 3회 초과 또는 상태 플래그 변경으로 종료한다.

수정 빌드 `0x5167C`부터 `0xDA`바이트는 원본 `export/DUNE2.EXE`의 `0x4ED1C`, `dalmuri672-english-subtitles`의 `0x5167C`, 검증된 달무리 치트 기준본의 `0x4FCCC`와 같았다. 이 무조건 정답 동작이 번역·MZ 분석에서 새로 생겼다는 근거는 없다.

## 패치 위치와 보존 계약

| 위치 | 처리 |
|---|---|
| `32DD:10AA` | 초기화 뒤 성공값 1을 설정하고 원래 정리 지점 `16B8`로 연결 |
| 메인 루프의 EXE 분석 오프셋 `9258h`부터 12바이트 | `DS:38B2=1`일 때만 앞선 팔레트 갱신 `044B:0559`를 건너뜀 |
| `32DD:0BD8` | 첫 설명의 `ADD DX,1Eh`를 `ADD DX,0`으로 변경 |

이후 설명의 원래 15틱 간격과 원본 페이드를 유지한다. 파일 오프셋은 분석 대상의 위치이며 빌더는 모듈과 명령 서명을 대조한다. 구현은 `tools/runtime_patches.py`, 원본 호출 연결은 [상태 경로](security_briefing_reanalysis.md)를 따른다.
