# 설명문 분할과 포인터 진행 조건

## 포인터가 진행하지 않는 분기

가문 설명을 표시하는 모듈 `32DD`는 `1893h`의 문장 분할 함수를 호출한다. `18B6h`부터 앞으로 글자 폭을 합산하고, 한 줄의 폭을 넘으면 `1901h`부터 공백까지 뒤로 이동한다.

역방향 폭 조회에서는 다음 순서로 처리한다.

1. `32DD:1901`에서 현재 문자열 포인터를 BX에 읽는다.
2. `1904`에서 부모 프레임의 문자열 포인터를 1 감소시킨다.
3. `1907`에서 감소 전 포인터의 글자를 AL에 읽는다.
4. `190B`에서 글자 폭 콜백을 호출한다. 반환 위치는 `1910`이다.
5. `1913–191A`에서 포인터 위치의 공백을 검사하고 공백이 아니면 반복한다. 이 반복에는 폭 수치로 탈출하는 조건이 없다.

새 후크는 이 역방향 호출을 구별하지 않고, AL이 한글 선행 바이트이면 먼저 ForwardTokenValid 경로로 처리한다. 감소 후 포인터의 앞 음절 후행 바이트를 현재 음절의 후행 바이트로 오인하여 유효 토큰으로 판별하면 부모 포인터를 다시 1 증가시킨다. 원본의 감소와 후크의 증가가 상쇄되어 같은 위치를 계속 읽는다.

또한 ReverseTokenCandidate의 비교도 원본이 이미 포인터를 감소시켰다는 계약을 반영하지 않는다. 단순히 forward 분기 하나를 우회하는 것으로 역방향 한글 처리가 완성되는 것은 아니다.

## 바이트 기반 분기 평가

실제 TEXTA.ENG[0] 번역 토큰과 원본 NEW8P.FNT 폭 표를 사용하고 수평 간격 -1, 줄 폭 304 조건에서 첫 본문 줄을 평가했다. 정방향 합산 후 오프셋 87, AL=FCh에서 역방향에 진입한다. 원본이 포인터를 86으로 감소시키지만 후크가 다시 87로 증가시킨다. 87의 바이트는 공백이 아니므로 같은 경로로 반복한다. TEXTH.ENG[0]에서도 같은 조건에서 오프셋 82의 F9h로 동일한 포인터 정지가 발생한다.

이 판정은 원본과 한글 후크의 포인터 변경 및 저장 문자열을 이용한 정적 분기 평가다. 특정 실행에서 멈춘 CPU 주소를 관측한 자료와는 구분한다.

메뉴 정상 표시만으로 이 경로가 정상이라고 판단한 이전 정적 확인 범위가 불충분했다. 메뉴 폭 합산과 설명문의 역방향 문장 분할은 호출 계약이 다르다.

## 증거와 필요한 수정 범위

- 수정 대상: 폭 콜백의 호출 위치별 정방향/역방향 분기와 토큰 소비 위치. 원본 메뉴 그리기 코드의 변경이 필요한 것으로 판명된 것은 아니다.

## 멘타트 설명의 분할 규칙

멘타트는 가문·임무 본문과 같은 `32DD:1893` 문장 분할기를 호출하지 않는다. 항목명은 `2CA0:2357`, 멘타트 본문은 `0EED:1FEF`에서 공통 문자 출력 루프 `29C7:0004`로 직접 들어간다. 본문은 저장된 CR과 렌더러의 화면 오른쪽 경계 줄바꿈을 사용한다. 따라서 문장 분할 후크를 멘타트에 억지로 붙이는 것은 같은 경로의 적용이 아니다. 한글 토큰 폭·글리프 출력 후크는 공통 `29C7:0004` 콜백에 있으므로 멘타트에도 이미 적용된다.

현재 한글 PAK의 멘타트 143개 레코드(아트레이데스 47, 하코넨 49, 오르도스 47)를 정적으로 재독해했다. 143개 항목명과 143개 압축 설명을 번역 CSV의 토큰 스트림과 각각 바이트 단위로 대조했고 모두 일치했다. 모든 한글 토큰은 639음절 코드표에서 유효했다. NEW6P.FNT와 NEW8P.FNT는 각 226 슬롯(인덱스 `00h`–`E1h`)이다.

아트레이데스 설명 6번과 36번에 CP437 `FAh`(유니코드 가운데점 `·`)가 남아 있었다. `FAh`는 해당 폰트의 226개 폭·글리프 표 범위 밖이라 원본 FNT 조회가 표 경계를 넘는다. 이는 실제 출력 경로에서 확인된 잘못된 글리프 인덱스지만, 관측된 화면의 멈춤의 직접 원인이라고 단정할 런타임 주소 증거는 없다. 같은 문자가 있던 `TEXTO.ENG[36]`, `CREDITS.ENG[26,36]`도 함께 정리했다.

원본 FNT 밖의 부호는 별도 글리프 선택이나 명시적 호환 치환이 필요하다. 원본 226슬롯 표에 FAh를 그대로 전달하는 비교 구현은 경계를 넘는다. 최종 부호 처리는 [달무리 출력 선택](../fonts/dalmoori_latin_symbols.md)을 따른다.
