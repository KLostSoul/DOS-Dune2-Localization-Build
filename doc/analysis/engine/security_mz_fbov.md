# 보안 질문 경로와 DOS MZ 분석 범위

> 2026-10-23 정정: 이 문서의 큰 `3208` 블록을 실제 코드 모듈로 배정한 부분은 잘못됐다. 실제 FBOV 게이트 헤더로 복원한 보안 질문 함수는 `32DD:1099`이며 호출자는 `1223:045D`다. 이전 후보 `e9695072…`는 사용자가 멘타트 초상·빈 회색 패널과 지연을 관측해 교체했다. 현재 후보는 함수 초기 상태 설정 뒤 성공값을 설정하고 원래 정리·FAR 반환부로 이동한다. 호출자 쪽 기존 팔레트 전환과 미션 후속 흐름은 그대로며, 보안 함수 내부 페이드·멘타트 화면·질문 경로는 건너뛴다. 현재 배치 EXE SHA-256은 `0cce3da6c800ceb83dc314ab376a745549cc4b6b6ceb692b1a5a092d750b72b1`이다. 세부 정적 CFG와 런타임 미확인 범위는 [회색 화면·지연 원인 보고서](security_gray_panel_delay.md)를 기준으로 한다.

## 대상과 확인 범위

분석 대상은 `build/dalmuri672-english-subtitles-feedback/source/VIRGIN/DUNE2/DUNE2.EXE`다. SHA-256은 `642aabea9eb0b1c9945a5c17267b5c5b228ba237effdfccb85a5a04df379e7a3`이다. 이 입력 파일은 수정하지 않았고 게임도 실행하지 않았다. 질문 건너뛰기 후보는 별도 빌드 폴더에 만들었다.

## MZ 이미지 로딩 결과

REA/Ghidra 12.1.4의 x86 16비트 리얼모드 로딩 결과는 `verified`다.

| 항목 | 관측값 |
|---|---:|
| MZ 헤더 | 19,456바이트 (`0x4C00`) |
| MZ 초기화 모듈 | 260,480바이트 (`0x3F980`) |
| 파일 끝에 붙은 오버레이·부가 데이터 | 102,130바이트 |
| 재배치 레코드 | 4,505개 |
| 독립 비교 검사 | 2,164개, 실패 0개 |
| MZ 진입점 | 적재 선형 주소 `0x10000` |

따라서 현재 확보한 증거에서 **DOS MZ 헤더·본문·재배치 로더의 바이트 오독은 확인되지 않았다.** 다만 MZ 적재 본문 뒤의 FBOV 오버레이는 일반 MZ 초기화 모듈이 아니므로 자동으로 코드 메모리에 올리지 않는다. 여기서 발생한 문제는 MZ 형식 판독 실패가 아니라 **FBOV 오버레이를 기본 함수·호출 분석에 연결하지 못하는 범위 한계**다.

## 보안 리소스를 읽는 실제 오버레이 코드

FBOV 디렉터리의 테이블은 파일 오프셋 `0x36D10`, 항목 수는 226개다. 항목 169는 세그먼트 `3208h`, 크기 `FFFFh`, 플래그 `0004h`로 기록되어 있다. 해당 코드 바이트는 현재 EXE 오프셋 `0x4D36F`부터 복원된다.

세그먼트 `3208h:3E3A`의 코드는 함수 진입 형태(`55 8B EC`, `PUSH BP; MOV BP,SP`)로 시작한다. 파일 오프셋은 `0x511A9`다. 이 함수는 다음 작업을 한다.

1. `DS:[3A2C]` 값에 따라 `DS:2598`, `DS:25A2`, `DS:25AC` 중 하우스 그림 파일명 포인터를 선택한다. 해당 데이터는 각각 `FHARK.WSA`, `FARTR.WSA`, `FORDOS.WSA`다.
2. `DS:25B7`을 인자로 넘겨 리소스 선택 함수를 호출한다. 이 주소의 실제 문자열은 `PROTECT\0`이며 MZ 데이터 파일 오프셋 `0x3A5D7`에 있다.
3. `PROTECT` 리소스를 연 뒤 화면 출력 및 입력 처리 루프로 들어간다. 별도 추출 문자열표에는 심문 서문, 정답·오답 응답, 질문과 그림 파일명이 포함된다. 예를 들어 1번 문구는 하코넨에 대한 충성을 증명하라는 심문 서문이고, 10번은 “What type of structure is this?”다.
4. 정적 제어 흐름상 시도 카운터를 0에서 시작해 3회 초과 또는 상태 플래그 변경 시 루프를 끝내고 그 상태값을 반환한다.

`3208h:3EC2`(파일 오프셋 `0x51231`)의 바이트 `9A 5D 07 08 00`은 오버레이 호출 게이트를 거쳐 MZ의 `044B:075D` 리소스 선택 코드로 연결된다. 이 호출 직전에 `DS`와 `DS:25B7`을 쌓는다. 현재 EXE 전체에서 `PROTECT` 이름의 참조는 이 로드 인자 하나만 발견됐다. 이 근거로 해당 함수가 보호 질문용 `PROTECT.ENG` 리소스를 여는 경로라는 점은 확인된다.

## 자동 분석에서 빠진 연결

기본 MZ 분석에서 Ghidra는 `3208h:3E3A`를 절차 진입점으로 찾지 못했다. 같은 오버레이 바이트를 분석용 MZ 사본의 진입점으로 지정했을 때에만 해당 함수 본문이 인식됐다. 원본 EXE는 변경하지 않았다.

또한 이 오버레이의 `CALL FAR 0008:075D`를 일반 far call로 처리하면 실제 FBOV 게이트 의미가 사라진다. 실제 실행에서 `0008:075D`는 오버레이 규약으로 MZ의 `044B:075D`에 연결된다. 그러므로 기본 MZ xref·호출자 목록에 해당 오버레이 연결이 없다는 결과를 “호출자가 없다”는 뜻으로 해석하면 안 된다.

현재까지 직접 코드 바이트로 `3208h:3E3A`를 가리키는 near/far 호출은 찾지 못했다. 오버레이 디스패치·간접 호출·FBOV 관련 참조 연결은 아직 정적으로 완전히 복원하지 못했다. 따라서 반환 상태값을 상위 코드가 어떤 의미로 검사하는지와 보호 질문을 건너뛸 정확한 상위 분기 위치는 미확정이다.

## 입력값과 무관한 성공 경로 및 질문 건너뛰기

사용자는 현재 빌드에서 어떤 답을 입력해도 정답으로 판정된다고 확인했다. 이 관찰과 현재 EXE의 원시 바이트가 일치한다.

현재 파일 오프셋 `0x51687`의 코드는 `CALL FAR 0000:38C6`, `ADD SP,8`, `OR AX,AX`, `JMP short +42h` 순서다. 질문 처리 호출 뒤의 `EB 42`는 조건 분기가 아닌 무조건 점프다. 이어지는 성공 경로는 오프셋 `0x51715`에서 로컬 상태값을 1로 설정하고, 종료부에서 `DS:3C3E`와 `DS:2574`를 0으로 정리한 뒤 그 상태값을 `AX`로 반환한다. 따라서 정상 반환한 입력 경로에서는 `AX`를 비교해 오답으로 되돌리는 분기가 없다. 이는 사용자가 확인한 “아무 답이나 정답” 동작을 설명한다.

이 코드가 번역 작업에서 생긴 변화인지 확인하기 위해 동일한 `0xDA` 바이트 구간을 비교했다. 현재 빌드 오프셋 `0x5167C`의 구간은 원본 `build/source/VIRGIN/DUNE2/DUNE2.EXE` 오프셋 `0x4ED1C`, `build/dalmuri672-english-subtitles` 오프셋 `0x5167C`, 검증 기준 `build/recovered-verified-dalmuri-cheat-baseline` 오프셋 `0x4FCCC`와 완전히 일치한다. 이 경로의 무조건 성공 동작은 현재 MZ 분석기나 이번 번역 빌드에서 새로 생긴 것이 아니다.

질문 화면 자체를 생략하도록 별도 실행 후보 `build/dalmuri672-english-subtitles-skip-security-question`을 만들었다. FBOV 항목 169의 `3208h:3E3A` 진입점(해당 빌드 파일 오프셋 `0x511A9`)에 다음 12바이트 stub을 넣었다.

```text
31 C0 A3 3E 3C A3 74 25 B8 01 00 CB
```

이 코드는 `AX=0`으로 두 상태 플래그 `DS:3C3E`, `DS:2574`를 정리하고, 기존 정상 성공 경로와 같은 값 `AX=1`을 반환하며 far return한다. 원래 함수는 진입 시 두 플래그를 1로 설정하고 정상 종료 시 0으로 되돌리므로, stub은 질문 리소스 로드·화면 출력 전에 같은 종료 상태를 보존한다. 파일 오프셋 `0x44580`의 MZ/FBOV 경계와 FBOV 표는 그대로다.

정적 사후 검증에서 출력 EXE는 입력과 382,066바이트로 길이가 같고, 변경된 9바이트는 모두 `0x511A9..0x511B4` stub 범위 안에 있다. 초기화 MZ 모듈 바이트는 완전히 동일하다. 새 EXE SHA-256은 `3724c48617dd539463ad189ce9e3cb648aaed1df2ca2d6f7a3e4a61457320a77`이다. 게임 실행 검증은 하지 않았다. 세부 대조값은 `build/dalmuri672-english-subtitles-skip-security-question/security-question-report.json`에 기록했다.

## 결론

- MZ 적재와 재배치 검증, 원시 바이트 대조에서 분석기 버그의 증거가 없다.
- FBOV 오버레이를 자동 함수·호출 분석에 포함하지 않는 한계는 확인됐다. 이전의 “MZ를 거부한다” 또는 “해당 주소에 절차가 없다”는 결과만으로 파일 오류라고 결론 내리면 안 된다.
- 보안 질문의 `PROTECT` 리소스 로드 함수, 무조건 성공으로 끝나는 입력 경로, 반환값을 정적으로 특정했다.
- 최초 진입 stub 후보는 성공값과 상태 플래그만 맞추고 함수의 기존 화면 전환·자원 정리 흐름을 건너뛰었다. 사용자 보고 뒤 폐기 대상으로 표시했으며, 교체 후보는 아래 페이드 전환 보정 후보에 기록했다.

## 페이드 전환 보정 후보

이전 후보는 파일 오프셋 0x51372에서 성공 상태를 설정하고 입력 루프를 건너뛰었다. 사용자는 그 후보의 페이드 인·아웃은 정상이라고 확인했지만, 질문은 남고 답 입력만 생략됐다고 보고했다. 질문 처리 도우미와 가문 초상 CG 경로를 각각 생략하도록 보완했다. 이후 사용자가 회색 화면과 지연을 보고해 후처리 경로도 다시 확인했다.

정적 분석에서 함수 `entry`는 파일 오프셋 0x51303 (Ghidra 선형 주소 0x36014)에서 오버레이 함수 `FUN_3208_3859` (Ghidra 주소 0x358D9, 오버레이 3208:3859)를 호출한다. 해당 도우미는 질문 리소스를 준비하고 텍스트 줄 처리를 하며 입력 상태를 읽는다. 호출 직후의 `ADD SP, 0x12`가 인자 18바이트를 정리한다. 호출 반환값은 그 사이 사용되지 않는다. 이에 호출 3바이트만 NOP으로 바꾸고 인자 정리와 후속 코드는 남겼다.

보안 질문 화면의 가문 초상 CG는 별도 WSA 경로로 그려진다. `entry`는 가문 값에 따라 `DS:2598`, `DS:25A2`, `DS:25AC` 중 하나를 `[BP-18]:[BP-1A]`에 넣는다. 이 포인터는 각각 `FHARK.WSA`, `FARTR.WSA`, `FORDOS.WSA`를 가리킨다. 파일 오프셋 0x51298에서 `FUN_3208_2da1` (Ghidra 선형 주소 0x34E21, 오버레이 3208:2DA1)에 이 포인터와 가문 값을 전달한다. 이 함수 분석에서 포인터가 0이 아닐 때만 WSA를 불러오는 `0x6920` 호출, 한 프레임을 그리는 `0x692A` 호출, 해제하는 `0x6925` 호출이 실행되는 것이 확인됐다. 포인터 두 단어를 0으로 넘기면 이 가문 초상 CG 로드·그리기 구간만 건너뛴다. 함수 뒤쪽의 공통 `FUN_3208_382F` 및 화면 상태 복구 호출은 그대로 실행되도록 해당 함수를 통째로 건너뛰지 않았다.

파일 오프셋 0x51298의 6바이트 명령열을 같은 길이로 바꿨다.

기준: `FF 76 E8 FF 76 E6` (`[BP-18]`·`[BP-1A]` 가문 WSA 포인터를 push)
수정: `33 C0 50 50 90 90` (`AX=0`; 0 두 개 push; 남은 두 바이트는 NOP)

호출 뒤 기존 `ADD SP, 0x6`가 3개 인자를 정리하므로 스택 크기는 유지된다. 보안 CG 함수 안의 공통 후처리도 유지된다. `FUN_3208_3859` 호출 생략은 별도로 질문 문구와 질문에 붙은 리소스/입력 처리를 건너뛴다.

추가 패치:

기준: `E8 C2 F8` (`CALL 3000:58D9`)
수정: `90 90 90` (`NOP` 3개)

질문 표시와 입력을 생략하는 성공 분기도 수정했다.

기준: `33 FF C7 46 E0 00 00 E9 23 04`
이전: `33 FF C7 46 E0 01 00 E9 9E 03`
현재: `33 FF C7 46 E0 01 00 E9 31 04`

`[BP-20]` 성공 상태를 1로 설정하고, 원래 near jump 목적지 `3000:64B0` 대신 기존 정리 시작 `3000:64BE`로 직접 이동하게 했다. 정적 CFG상 이 분기는 응답 패널 호출(`3000:61C2`, `3000:6433`)과 타이머·화면 갱신 루프(`3000:6488..64BD`)를 건너뛴다. `0x78`은 해당 루프에서 타이머 만료값에 더하는 값이다. 다만 사용자는 이 패치가 들어간 후보에서도 회색 화면과 지연이 남았다고 보고했다. 따라서 이 분기 수정이 사용자 관측을 해결했다고 결론 내릴 수 없으며, 실행 중 다른 경로가 화면 또는 대기를 만드는 원인은 미확정이다. `3000:64BE`부터는 원래 정리와 성공값 반환을 수행한다.

사용자는 앞선 후보에서 페이드가 정상이라고 확인했으며, 현재 직접 정리 후보에서도 회색 화면과 지연이 계속된다고 보고했다. 파일 자체에는 기대한 11바이트 패치가 확인되고 실행 배치는 이 후보의 `source`를 마운트한다. 에이전트는 게임을 실행하지 않았다. 그러므로 정적 바이트 적용과 사용자가 관측한 동작을 분리해 기록하며, 화면·지연이 실제로 발생하는 실행 경로는 미확정이다.
