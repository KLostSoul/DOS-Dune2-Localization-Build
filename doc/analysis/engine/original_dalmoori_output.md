# 원본 출력기와 한글 토큰 처리의 인터페이스 비교

## REA로 확인한 차이

REA의 Ghidra 12.1.4 DOS MZ 분석을 사용했다. 아래 원본 주소는 파일의 이미지 상대 세그먼트:오프셋이며, REA 기본 선형 주소에는 로드 기준 10000h가 더해진다.

| 단계 | 원본 | 현재 한글 수정판 | 확인 범위 |
|---|---|---|---|
| 리소스 읽기 `0DD4:0088` | 오프셋 표에서 시작 위치를 읽고 문자열 데이터를 버퍼에 읽음 | 코드 266바이트 동일 | REA 명령과 파일 바이트 대조 |
| 쌍 압축 해제 `2307:00F4` | 상위 비트가 설정된 바이트를 내장 두 글자 표로 전개 | 코드 107바이트 동일 | REA와 실제 EXE의 144바이트 변환표 대조 |
| 확장 바이트 해제 `2307:0002` | 1Bh 뒤 바이트에 7Fh를 더해 확장 바이트를 만듦 | 코드 79바이트 동일 | 파일 바이트와 별도 명령 대조 |
| 일반 줄바꿈 `0EED:01B8` | 바이트를 앞뒤로 읽으며 글자 폭을 합산 | 본문 187바이트 동일, 호출되는 폭 함수가 달라짐 | 원본·수정판 각각 REA로 관측 |
| 설명문 문장 분할 `32DD:1893` | 폭, 공백, 마침표, 느낌표, 물음표, CR, NUL을 보고 원본 버퍼에 CR/NUL을 씀 | 해당 오버레이 코드 동일 | 오버레이 원본 바이트의 REA 분석 |
| 한 글자 폭 `2326:0009` | `[BP+6]`의 문자 인자를 읽고 FNT 폭과 간격을 반환. 부모 문자열 포인터를 바꾸지 않음 | 첫 4바이트가 `[66D8]`로 가는 FAR JMP. 후크는 입력 AL을 사용하고 호출자의 부모 프레임에 있는 문자열 포인터도 바꿈 | 두 실행 파일을 각각 REA로 분석 |
| 서식 처리 `0000:111F` 이후 | `%`를 서식 시작으로 해석하는 CRT 포맷 루틴 | 비교한 1,171바이트 동일 | REA에서 잘린 함수 본문은 1183h의 후속 본문까지 따라감 |
| 문자 출력 루프 `29C7:0004` | 한 바이트 단위로 순회하고 FNT 폭 표를 조회 | 비교한 234바이트 중 A0h~A4h의 폭 조회 5바이트가 콜백 호출로 바뀜 | 파일 전체 구간 대조 |
| 픽셀 출력 `20AA:07BD` | 활성 FNT의 오프셋·폭·높이 표와 색상 변환표를 사용 | 영문은 원본으로 연결. 한글은 후크 내부의 639음절 표와 8×8 비트맵을 사용하며 10픽셀 셀로 그림 | 원본 REA와 수정판 소스·기존 REA 자료 대조 |
| 화면 페이지 선택 `20AA:0E02` | 활성 화면 번호로 페이지 세그먼트를 조회 | 한글 후크가 같은 조회 순서를 내부에 구현 | 원본 함수 34바이트와 후크 명령 대조 |

원본은 **한 바이트 문자, 폭 조회의 포인터 부작용 없음**을 전제로 한다. 수정판은 **두 바이트 한글, 폭 조회 중 부모 포인터 변경**을 추가했다. 따라서 원본의 모든 바이트 처리와 새 토큰 처리의 접점을 검토해야 한다. 이 구조 차이 자체가 현재 멈춘 명령을 입증하는 것은 아니다.

원본 폭 함수는 스택 인자 `[BP+6]`을 읽는데 후크의 StringWidthLookup은 AL을 사용한다는 인자 전달 방식 차이도 남아 있다. 정적으로 읽은 주요 호출자들은 호출 직전에 AL을 읽고 AX를 인자로 넣는다. 이 관측만으로 모든 실행 경로에서 AL과 스택 인자가 항상 같다고 보장하지 않는다.

## 세 가문의 첫 설명문 해제 결과

번역 도구의 왕복 검사만 반복하지 않고, 원본 EXE의 변환표와 두 단계 해제 명령에 따라 저장된 바이트를 별도로 계산했다.

| 파일의 0번 설명문 | 원본 저장 바이트 | 원본 해제 바이트 | 한글 저장 바이트 | 한글 해제 바이트 | 번역 토큰과 일치 |
|---|---:|---:|---:|---:|---|
| TEXTA.ENG | 194 | 317 | 336 | 235 | 일치 |
| TEXTH.ENG | 136 | 217 | 257 | 180 | 일치 |
| TEXTO.ENG | 189 | 308 | 325 | 227 | 일치 |

이 세 설명문에서 압축 표현의 불일치는 확인되지 않았다. 실제 실행 중 읽은 버퍼 주소와 내용까지 확인한 것은 아니다. 저장 파일과 정적 해제 결과가 맞는다는 결론을 실제 버퍼 상태가 정상이라는 결론으로 확대하지 않는다.

## 전체 문장 분할 명령의 제한된 평가

`tools/analyze_dalmuri_wrap_instructions.py`는 Capstone으로 읽은 실제 16비트 명령의 메모리·분기·스택 효과를 오프라인에서 계산한다. DOS·BIOS·장치·게임 실행은 포함하지 않는다. 원본과 현재 수정판의 `32DD:1893` 및 실제 폭 함수/후크 명령을 사용했다.

선언한 조건은 NEW8P.FNT, 폭 304, 간격 -2/-1/0, 분석용 오버레이 CS=6000h, 적재 기준 0000h, 외부 호출 `0198:0009 → 2326:0009`다. 실제 게임에서 관측한 런타임 배치라는 뜻이 아니다. 각 함수의 FAR 호출 스택과 입력 문자열을 구성해 명령 수를 제한했다.

세 가문 × 원본/한글 × 간격 세 가지, 총 18개 입력에서 모두 함수가 반환했다. 따라서 **현재 수정판이 이 선언된 입력에서도 같은 역방향 반복에 빠진다고 설명하는 것은 맞지 않는다.** 실제 게임의 호출 인자·세그먼트·FNT 포인터가 이 조건과 같은지는 디버거로 확인해야 한다.

역방향 폭 반복의 종료 여부와 멘타트 항목 읽기의 정지는 서로 다른 경로다. 폭 루프의 결함만으로 리소스 읽기 정지까지 특정할 수 없다. NAME·DESC·INFO 경계도 함께 검사한다.

## 서식 바이트와 글리프 바이트의 접점

한글표는 후행 바이트 25h도 사용한다. TEXTA[0]에서 `들`과 `영`의 토큰 후행 바이트가 25h다. 원본 포맷 루틴은 한글 토큰을 구별하지 않고 바이트 25h를 `%`로 검사한다. 다만 원본에는 미지원 서식을 만났을 때 남은 문자열을 문자 그대로 복사하는 경로도 있다. **25h가 존재한다는 사실만으로 현재 멈춤 원인이라고 판단하지 않는다.** TEXTH[0]와 TEXTO[0]에는 이 바이트가 없다.

## 오버레이 분석 자료의 출처와 한계

원본의 설명문 모듈은 MZ 적재 이미지 뒤의 FBOV 오버레이다. REA의 일반 MZ 적재만으로 이 영역의 함수를 직접 분석했다고 주장하지 않는다. 원본 모듈 195의 코드 1A7Ch바이트를 그대로 추출하고, 분석용 MZ 헤더만 붙여 REA에 별도로 열었다. **게임용 실행 파일이 아니며 실행하지 않는다.** 코드 해시는 원본·검증본·수정판에서 모두 `a2bb4e53b5ead045068c81254f916730d638f38e8db5d8ef3d71a5bea82786b2`로 같다.

추출 원본 경로·파일 오프셋·길이·해시는 `build/analysis/dalmuri-original-vs-korean/derived-artifacts.json`에 있다. 분석용 선형 11893h는 원본 모듈의 `32DD:1893` 코드에 해당한다. 이 분석용 컨테이너의 외부 FAR 호출은 원래 FBOV 선택값을 그대로 갖기 때문에, 컨테이너의 자동 외부 호출 이름을 게임의 실제 호출 대상으로 간주하지 않았다.

Ghidra의 일부 세그먼트 MOV 피연산자 방향 표기와 자동 함수 경계는 불완전했다. 실제 바이트·Capstone과 교차 대조했으며, 코드 주소를 잘못 요청해 인접 함수가 반환된 결과는 해당 함수의 근거로 사용하지 않았다.
