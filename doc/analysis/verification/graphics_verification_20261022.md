## 3. CG 디코딩·재인코딩 도구와 검증

관련 도구는 `tools/cg_codec.py`, `tools/edit_cg.py`, `CG_편집용_추출.bat`, `CG_재인코딩.bat`이다. 원래 크기의 개별 PNG를 편집 입력으로 사용한다. 기존 접촉 시트는 미리보기이므로 인코딩 입력으로 사용하지 않는다.

인코더는 원본 PAK·원본 리소스 해시, 프레임 수와 크기, 팔레트, 투명색을 대조한다. 결과를 다시 해제해 입력 픽셀과 비교하고, PAK의 멤버 이름·순서·데이터도 검사한다. 입력 크기를 임의로 바꾸거나 색을 근사 변환하지 않는다. 출력은 새 폴더에 만들며 기존 출력에 덮어쓰지 않는다.

2026-10-22 전체 추출 상태에서 실시한 저장된 검증 보고서는 [`build/cg-codec-check-20261022-165136-614030/check-report.json`](../../../build/analysis/cleanup-2026-10-24/evidence/cg-codec-check-20261022-165136-614030/check-report.json)이다.

| 확인 항목 | 저장된 결과 | 범위 |
|---|---|---|
| 무수정 PAK의 원본 바이트 일치 | 통과 | 당시 편집 사본에 변경이 없던 상태 |
| 실제 리소스마다 픽셀 수정 | 143개 | 각 리소스의 사본 프레임에 실제 픽셀 변경 적용 |

| 원본 게임 PAK 보존 | 통과 | 검증 전후 원본 해시 비교 |
| WSA 버퍼 증가 기본 차단 | 통과 | 증가가 필요한 시험 변경은 기본 설정에서 오류로 중단 |
| 게임 실행 | 하지 않음 | 위 결과는 코드·데이터 검사 |

픽셀 비교에 더해 인코더는 WSA의 연결 프레임·루프와 프레임 크기·팔레트·투명색을 검사한다. 버퍼 증가를 허용하는 옵션은 시험 사본에서 명시적으로 사용했으며 기본값은 차단이다. 현재 편집 목록에서는 WSA·ICN·FNT를 제외했지만, 당시 전체 리소스 검증 기록은 그대로 유효한 이력으로 보존한다.

**143개는 과거 전체 검증 집합이고, 현재 편집 집합은 10개다.** 이번 기록 작업에서 과거 143개 시험을 새로 실행했다고 기술하지 않는다. 현재 `MISC.ENG` PNG에는 의도적인 편집이 있으므로, 무수정 입력을 가정하는 과거 검증 스크립트의 시작 조건과도 구분해야 한다.

CG 재인코딩은 PAK를 만드는 작업이다. 현재 배치가 EXE를 함께 패치하거나 게임을 자동 실행하는 빌드 통합 기능은 구현하지 않았다. 세 줄 `MISC.ENG`처럼 EXE와 배치가 맞아야 하는 자산은 해당 EXE와 짝을 맞춰 사용한다.

## 4. BTTN.ENG과 SCREEN.CPS의 차이

실제 PNG를 열어 확인한 `BTTN.ENG`의 구성은 다음과 같다.

| 프레임 | 내용 | 크기 |
|---:|---|---|
| 000 | MENTAT 버튼 그림 | 80×16 |
| 001 | MENTAT 버튼의 다른 상태 그림 | 80×16 |
| 002 | OPTIONS 버튼 그림 | 80×16 |
| 003 | OPTIONS 버튼의 다른 상태 그림 | 80×16 |
| 004 | Credits 표시 | 64×16 |

두 상태의 정확한 누름·복원 호출 순서를 역분석한 결과로 위 순서를 지정하지는 않았다. 실제 그림의 내용과 크기를 기록한 것이다.

`DUNE/SCREEN.CPS`는 320×200 한 장짜리 화면 그림이며, 그 PNG의 상단 픽셀 자체에도 MENTAT·OPTIONS·Credits가 들어 있다. 따라서 버튼 문구를 한글화할 때 상태별 버튼 그림과 배경에 들어 있는 같은 표시를 함께 맞추는 것이 편집 방향이다. 두 파일은 별개 리소스이므로 한 파일의 픽셀이 다른 파일로 자동 전파되지는 않는다. 이번 비교는 픽셀 자산 확인이며, 각 그림을 게임이 덮어 그리는 모든 시점을 실행 추적한 결과는 아니다.

문서 정리 시 현재 원본 리소스를 다시 해제해 편집용 PNG와 대조했다. `BTTN.ENG`의 5프레임과 `SCREEN.CPS`의 1프레임은 모두 변경 픽셀 0개였다. 이 두 리소스에 한글 버튼을 이미 적용했다고 기록하지 않는다.

## 6. MISC.ENG 원본 구조와 출처

`ENGLISH.PAK/MISC.ENG`는 문자열표가 아니라 CPS 그림이다. 크기는 320×200이고, 해제 결과는 64,000바이트의 팔레트 인덱스 픽셀이다. 원본 파일은 3,493바이트이며 CPS 압축 방식 4, 내부 팔레트 길이 0이다.

질문 문장·가문 이름·물음표가 모두 그림에 포함되어 있다. 이 질문을 `INTRO.FNT`로 그린다고 한 이전 설명은 잘못이며, [기존 출처 역분석 문서](../graphics/house_question_source.md)에 이미 정정되어 있었다. 또한 앞선 답변에서 정확한 복사 좌표가 미확인이라고 했지만, 그 문서와 `tools/analyze_house_join_prompt.py`에는 좌표와 명령 근거가 기록되어 있었다. 그 자료를 놓친 설명도 정정한다.

원본의 질문 표시 코드는 실제 FBOV 오버레이 모듈 206, 논리 주소 `3314:0FB0`의 가문 선택 함수 안에 있다. `MISC` 이름을 언어별 파일명 생성기로 넘겨 리소스를 읽은 뒤 화면 영역 복사 두 번으로 문장을 합친다. `3314:13B3`과 `3314:13DF`가 두 복사 호출이며, 기존 화면 복사 래퍼·드라이버는 계속 사용한다.

복사 인자 순서는 `(원본X, 원본Y, 대상X, 대상Y, 폭, 높이, 원본페이지, 대상페이지)`다. X와 폭만 8픽셀 단위이고, Y와 높이는 픽셀 단위다.

| 부분 | 원본 픽셀 사각형 `(X,Y,W,H)` | 화면 위치 `(X,Y)` |
|---|---|---|
| 공통 Do you wish to join House | `(0,0,208,24)` | `(0,0)` |
| 하코넨 이름·물음표, 가문 번호 0 | `(0,24,104,24)` | `(208,0)` |
| 아트레이데스 이름·물음표, 가문 번호 1 | `(0,48,104,24)` | `(208,0)` |
| 오르도스 이름·물음표, 가문 번호 2 | `(0,72,104,24)` | `(208,0)` |

표시 결과는 312×24픽셀이다. 이 합성 경로는 CSV의 문장을 읽거나 FNT 글리프를 그리는 경로가 아니다. 따라서 그림 문구를 바꾸는 작업과 번역 문자열표의 항목을 바꾸는 작업을 구분해야 한다.

## 7. 완성 문장 세 줄 시험의 설계와 적용

사용자가 제시한 목표는 가문마다 완성된 문장 한 줄을 저장하고 선택된 가문의 줄 하나만 표시하는 것이다. 첫 시험에서는 원본 영문 그림 조각을 그대로 합쳐 출력 경로부터 확인했다. 아직 세 줄 그림을 한글로 다시 그린 것은 아니다.

| 가문 번호 | 이미지에 저장한 문장 | 새 픽셀 사각형 |
|---:|---|---|
| 0 | Do you wish to join House Harkonnen? | `(0,0,312,24)` |
| 1 | Do you wish to join House Atreides? | `(0,24,312,24)` |
| 2 | Do you wish to join House Ordos? | `(0,48,312,24)` |

원본의 가문 번호 순서를 보존했다. 파일 안에는 세 줄을 저장하지만 게임 화면에는 선택한 가문의 한 줄만 `(0,0)`에 표시한다. CPS 전체 크기는 그대로 320×200이고 세 문장 이외의 공간은 비어 있다.

### 영문에서만 새 방식 사용

사용자 지시에 따라 다른 언어에는 새 배치를 적용하지 않는다. 실제 파일명 생성기 `044B:075D`에서 언어 선택값 `DS:[37AA]`를 읽는 명령을 확인했다. `DS:31CC`의 코드는 포인터 배열이 아니라 `ENG\0FRE\0GER\0`의 4바이트 간격 인라인 문자열 표다.

| 선택값 | 언어 | 질문 복사 방식 |
|---:|---|---|
| 0 | ENG | 새 완성 문장 한 줄 복사 |
| 1 | FRE | 기존 공통 부분 + 가문명 부분의 두 번 복사 |
| 2 | GER | 기존 공통 부분 + 가문명 부분의 두 번 복사 |
| 그 밖의 0이 아닌 값 | 새 배치 적용 제외 | 코드 분기는 기존 두 부분 경로를 유지함. 유효한 추가 언어가 있다는 의미는 아님. |

### EXE 변경 범위

기반 EXE의 실제 오버레이 페이로드 시작은 파일 `0x57FD0`이다. 그 안의 논리 주소 `3314:1398..13E6` 79바이트만 다시 작성했다. 파일 범위는 `0x59368..0x593B6`이며, 끝 제외 주소는 `0x593B7`이다. 과거 원본 EXE의 파일 위치와 현재 확장 빌드의 위치를 혼동하지 않는다.

- 처음에 언어가 0인지 검사하고, ENG이면 공통 앞부분 복사를 건너뛴다.
- 두 번째 호출의 인자를 ENG와 다른 언어로 나누어 준비한다.
- `3314:13B3`과 `3314:13DF`의 기존 5바이트 FAR 호출 명령과 위치를 보존했다.
- FBOV 표·오버레이 크기·재배치 자료, 기존 화면 복사 함수와 그래픽 콜백을 보존했다.
- `PUSH imm8`, `IMUL r16,r16,imm8`을 사용한다. 이들은 80186 이상에서 지원되는 명령이며, 기존 486 시험 설정에서 지원된다.

실제 수정 명령 목록은 [`verification/patched-question-block.txt`](../../../archives/builds/verified/cg-house-question-three-lines-test.zip#cg-house-question-three-lines-test/verification/patched-question-block.txt)에 저장했다. 제작 도구는 [`tools/build_house_question_three_lines_test.py`](../../../archives/tools/legacy-tools-20261024.zip#tools/build_house_question_three_lines_test.py)다. 기존 시험 출력이나 배치가 있으면 덮어쓰지 않고 중단한다.

## 8. 언어·가문 9조합의 정적 검증

Capstone으로 실제 수정 바이트를 해독하고 조건 분기, 가문 번호, 곱셈, 인자 스택, 기존 FAR 호출까지 평가했다. 함수 호출은 문서화된 화면 복사로 취급해 픽셀을 재구성했다. DOSBox에서 9회 실행한 결과로 표현하지 않는다.

다음 표의 좌표·폭은 실제 함수에 넘기는 8픽셀 단위 값이다. 다른 언어의 첫 호출은 모든 경우 `(0,0,0,0,26,24,2,0)`으로 원본과 같다.

|---|---|---:|---|---|
| ENG | 0 하코넨 | 1 | `(0,0,0,0,39,24,2,0)` | 통과 |

| ENG | 2 오르도스 | 1 | `(0,48,0,0,39,24,2,0)` | 통과 |

## 10. 사용자 게임 확인과 편집용 PNG 채택

사용자는 세 줄 시험판에 대해 **“정상적으로 출력된다”**고 보고한 뒤 `cg/editable/images/ENGLISH/MISC.ENG`도 그 세 줄 이미지로 바꾸도록 지시했다. 이 보고는 가문 질문 세 줄 표시 시험의 정상 결과로 기록한다. FRE·GER와 세 가문 각각을 모두 실행했다고 따로 보고한 것은 아니므로 그 범위를 확대하지 않는다.

지시 후 실제 교체한 파일은 [`cg/editable/images/ENGLISH/MISC.ENG/frame_000.png`](../../../import/GFX/images/ENGLISH/MISC.ENG/frame_000.png) 한 개다. 검증된 시험 PNG와 파일 전체가 같고, 320×200 및 원래 팔레트를 유지한다. 위에서부터 하코넨·아트레이데스·오르도스 순서다.

| 편집용 PNG 항목 | 확인값 |
|---|---|
| 파일 길이 | 3,579바이트 |
| 파일 SHA-256 | `8aaff12fdfd1e865debbfa1c02aa309aa5d3fb2577d456326b568cf2b327bb52` |
| 색상 인덱스 픽셀 SHA-256 | `6d130eefe1757a14d60c31bce1e1bfe6bf7dd02c0b933604892ecaac56fd4a2a` |
| 원본 CPS와 다른 인덱스 픽셀 | 17,944개 |
| 재인코딩한 MISC.ENG | 사용자 정상 확인 시험판의 멤버와 전체 바이트 일치 |

17,944개는 이미지 프레임 전체의 색상 인덱스 차이다. 한글 글자 수나 글자 획의 픽셀 수를 뜻하지 않는다. 현재 10개 리소스·44개 프레임을 원본과 읽어 비교하면 편집 차이가 있는 리소스는 `MISC.ENG` 한 개다.

### 기준 리소스와 매니페스트를 바꾸지 않은 이유

인코더는 `resources/ENGLISH/MISC.ENG`를 해제한 원본 이미지와 편집 PNG를 비교한다. 매니페스트의 리소스 해시·프레임 픽셀 해시도 이 **비교용 원본**을 가리킨다. 따라서 PNG를 바꾸면서 이 기준까지 새 그림으로 덮어쓰지 않았다.

- `cg/editable/resources/ENGLISH/MISC.ENG`: 원본 3,493바이트 유지.
- `cg/editable/original/ENGLISH.PAK`: 기존 전체 PAK 유지.
- `cg/editable/manifest.json`: 기준 해시 유지.
- `cg/editable/images/ENGLISH/MISC.ENG/frame_000.png`: 검증된 세 줄 이미지 채택.

교체 전후 편집 프로젝트의 파일 해시를 비교해 PNG 한 개만 바뀌었음을 확인했다. 또한 실제 PNG를 인코더의 `load_pixels`와 `encode_cps`로 읽어 재인코딩했고, 결과가 정상 확인 시험판의 `MISC.ENG`와 일치했다. 기준을 보존한 상태에서도 새 그림이 정상적으로 편집으로 감지된다.
