# Dune II 원본·한글 시험본 메뉴 렌더링 역분석

분석일: 2026-10-20

## 정적 분석 결론 — 이전 후크 배치

**후크를 넣은 `255A:01C2`와 `255A:0412`는 사용하지 않는 코드 공간이 아니다. 원본 타이머 스택과 원본 드라이버 상태 영역이다.** 원본에서 0인 바이트만 찾고 그 영역의 읽기·쓰기 참조를 조사하지 않아 잘못된 위치에 후크를 넣었다. 글자 폭 중복보다 먼저 처리해야 하는 메모리 소유권 오류다.

위 충돌은 정적 파일 대조에서 찾았다. 분석 스크립트는 `tools/audit_hangul_hook_static.py`, 당시 근거는 `build/analysis/hangul-static/evidence.json`과 같은 폴더의 어셈블리 덤프다. 아래의 `255A` 충돌·스택·변수 분석은 **폐기한 이전 시험본**에 해당한다. 그 결과를 반영해 코드를 다시 배치한 뒤 설치된 DOSBox-X에서 메뉴 실행을 확인한 기록은 문서 끝부분에 덧붙였다.

### 1. 원본 초기화가 한글 FNT 로더의 RET를 파괴한다

원본 함수 `1BDA:0393`은 `255A:07E4`를 호출한다. 그 초기화 함수에는 다음 명령이 있다.

```asm
; 원본 파일 0x2A998
255A:07F8  mov word ptr cs:[046C], 0000
```

그런데 시험본의 같은 주소 `255A:046C`에는 `LoadHangulFont` 마지막 명령 `RET`(`C3`)가 있다. 후크의 끝부분은 다음과 같다.

```text
주소 0466부터: 07 1F 5A 59 5B 58 C3 00 00 00
원본 초기화의 WORD 쓰기를 적용한 뒤:
              07 1F 5A 59 5B 58 00 00 00 00
```

앞의 여섯 POP 명령은 남지만 **복귀 명령이 없어져 다음 메모리로 실행이 넘어간다.** 분석 스크립트는 시험본을 메모리에만 복사한 뒤 원본의 이 한 번의 쓰기를 적용해 `C3 → 00`을 재현했다. 실제 게임을 실행하거나 메모리에 패치를 적용한 결과가 아니다.

이는 모든 한글 글자가 그려진 뒤의 간격 문제가 아니라 **첫 한글 토큰을 처리하며 폰트를 읽는 함수가 정상 복귀하지 못하게 만드는 충돌**이다. 메뉴는 첫 항목부터 순차적으로 그리므로 그 처리에서 제어 흐름이 깨지면 뒤의 영문 항목까지 그리기에 도달하지 못할 수 있다. 저장된 빈 메뉴 화면에서 정확히 어느 명령에 멈췄는지까지 정적 분석으로 관측했다고 주장하지는 않는다. 하지만 이 후크 배치가 원본과 공존할 수 없다는 사실은 원본 쓰기 주소와 시험본 명령 바이트로 확정된다.

### 2. 첫 번째 삽입 영역은 원본 INT 08 타이머의 전용 스택이다

원본 `255A:0633`은 인터럽트 벡터 `0000:0020/0022`에 `255A:0519`를 등록한다. INT 08 벡터다. 핸들러에는 다음 흐름이 있다.

```asm
255A:0535  mov cs:[03C2], ss
255A:053A  mov cs:[03C4], sp
255A:053F  mov ax, cs
255A:0541  mov ss, ax
255A:0543  mov sp, 03C2
; 타이머 슬롯 조회
255A:05A7  call far cs:[si+0012]
; 원래 스택 복구
255A:05B9  mov ss, cs:[03C2]
255A:05BE  mov sp, cs:[03C4]
```

스택은 `03C2` 아래로 자란다. 한글 후크의 실제 코드 끝은 `03A8`이고, 스택 시작점에서 코드 끝 다음 바이트까지 여유가 25바이트뿐이다. 타이머 콜백과 그 하위 호출이 사용하는 스택이 후크 코드와 같은 메모리에 놓여 있다. 또한 빌더가 빈 공간이라고 분류한 범위에는 원래 SS·SP 보관 변수 `03C2/03C4`도 포함되어 있다. 특정 콜백이 어느 바이트까지 덮었는지는 별도 실행 관측 사항이지만, 이 영역을 독점 코드 영역으로 사용할 수 없다는 것은 정적으로 확인된다.

### 3. 후크 변수·파일 이름도 원본 상태 변수와 겹친다

| 겹치는 주소 | 원본 명령 위치와 쓰기 | 시험본에서의 용도 |
|---|---|---|
| `255A:0480` | `255A:1314`에서 AX 저장, `13DF`에서도 AX 저장 | 한글 폰트 메모리 세그먼트 |
| `255A:0482` | `255A:104A`에서 SI 저장 | 원래 렌더러의 복귀 연결 오프셋 |
| `255A:0484` | `255A:104F`에서 DS 저장 | 원래 렌더러 세그먼트 |
| `255A:0486` | `255A:1061`에서 `8000` 저장 | DOS 파일 핸들 |
| `255A:0488/048A` | `255A:1034/103B`에서 `04C0`/CS 저장 | 초성·중성·종성 인덱스 |
| `255A:048C` | `255A:1043`에서 AX 저장 | 초성 구성 글리프 번호 |
| `255A:0492/0496` 등 | `255A:1695/169D` 등에서 원본 값 저장 | 한글 X좌표·색상 |
| `255A:04B0/04B2` | `255A:1275/127A`에서 SI/DS 저장 | `DUNEHAN.FNT` 문자열의 앞부분 |

원본도 이 값을 쓰고 후크도 같은 값을 쓴다. 따라서 원래 렌더러 연결, 폰트 포인터, 파일 핸들, 파일명 모두 오염될 수 있고, 후크의 쓰기도 원본 드라이버 상태를 망가뜨린다. 세그먼트 표의 크기 검사와 파일의 0바이트 검사는 이 충돌을 검출하지 못한다. 기존 보고서의 `hook_verified_caves`라는 이름은 잘못된 안전성 판단이었다.

## 원본 메인 메뉴 구성과 출력 경로

오버레이 코드도 조사했다. 아래 `0x49xxx`, `0x50xxx` 값은 **EXE 파일 오프셋**이다. DOS의 CS:IP가 아니다. 오버레이의 FAR CALL 세그먼트 피연산자는 로더 재배치 전의 세그먼트 표 오프셋이므로 그대로 런타임 세그먼트로 해석하면 안 된다. 예를 들어 `00A0 / 8 = 20`번 표 항목은 원본 세그먼트 `0EED`다.

### 메뉴 항목 표

데이터 `3342:219D`, 파일 `0x3A1BD`에 각 6 WORD, 12바이트짜리 목록 네 개가 있다.

| 목록 번호 | 문자열 번호 목록 |
|---:|---|
| 0 | `27, 28, 29, 0, 0, 0` |
| 1 | `27, 28, 92, 29, 0, 0` |
| 2 | `27, 28, 29, 334, 0, 0` |
| 3 | `27, 28, 92, 29, 334, 0` |

`0x49F02–0x49F31`에서 파일 존재 확인 결과와 다른 조건값으로 목록 번호를 만든다. `0x49F66–0x49FA6`은 `목록번호 × 12 + 항목번호 × 2 + 219D`에서 문자열 번호를 읽고 문자열 조회 함수 `0DD4:005F`에 넘긴다. 반환된 DX:AX를 스택의 FAR 문자열 포인터 배열에 저장한다. `0x49FAB–0x49FBA`는 첫 0 항목으로 메뉴 항목 수를 정한다.

### 폭 계산·메뉴 목록·각 행 출력

1. `0x49FE3–0x4A022`가 각 문자열을 `2326:002F`에 보내 가장 넓은 문자열 폭을 찾는다. 이 값으로 패널 크기와 위치를 계산한다.
2. `0x4A159`가 메뉴 목록 출력 함수를 호출한다. 대상은 세그먼트 표 197번의 오버레이 스텁 `32E9:0025`다. 스텁의 코드 오프셋은 `0108`, 데이터 시작은 파일 `0x50390`이므로 실제 함수는 파일 `0x50498`이다.
3. 파일 `0x504F7–0x50578`이 메뉴 행을 순차적으로 순회한다. Y는 원본 폰트의 높이 `DS:[6CFD]`와 추가 행간을 사용한다. 선택 상태에 따라 색상을 고르고, `0x5056C`에서 각 행의 문자열을 `0EED:1E65`로 보낸다.
4. `0EED:1E65`는 폰트·색상·정렬을 설정하고 문자열을 포맷한다. 중앙/우측 정렬에서도 `2326:002F`로 폭을 다시 계산한다. 마지막 `0EED:1FEF`, 파일 `0x15ABF`에서 `29C7:0004`를 호출한다.
5. `29C7:0004`는 문자 폭 조회 → 경계 확인 → 글리프 콜백 `DS:[66D8]` 호출 → X 이동 → 다음 문자 순서로 처리한다. 원본 콜백은 `20AA:07BD`다.

게임 EXE의 메뉴 구성 코드와 목록 표는 수정하지 않았다. 후크 코드의 변경 지점은 문자 루프의 폭 조회 5바이트, 문자열 폭 함수 `2326:0009`의 진입 4바이트, 콜백 포인터, 그리고 MZ 로드 이미지 끝에 추가한 상주 코드다.

## 메모리 충돌 외에 확인된 출력 규약 오류

### 2바이트 조합 인덱스와 문자열 폭 처리

완성형 음절의 조합 인덱스는 `n=(L×21+V)×28+T`, 범위 `0..11171`이다. NUL 종료 문자열에서 인덱스의 어느 바이트도 0이 되지 않도록 다음 2바이트 혼합 진법으로 저장한다.

```text
lead  = 0x80 + floor(n / 127)     ; 0x80..0xD7
trail = 1 + (n mod 127)           ; 0x01..0x7F
decode n = (lead - 0x80) × 127 + trail - 1
```

88개 lead와 127개 trail 조합으로 11,176개 값을 만들 수 있어 한글 11,172음절 전부를 담고 네 값이 남는다. `DUNE.ENG` 원본 문자열 데이터에서 예약 lead 범위 `0x80..0xD7`는 발견되지 않았다.

원본 `2326:002F`는 문자열 바이트 수를 DI로 세며, 매 반복에서 포인터를 한 바이트 증가시킨 뒤 `2326:0009`를 호출한다. 후크는 해당 호출에서 lead와 trail을 확인하면 포인터와 DI를 각각 한 번 더 증가시켜 두 바이트를 한 음절로 센다. 별도의 정방향·역방향 폭 계산 호출도 확인했으며, 정방향은 포인터가 가리키는 trail을, 역방향은 trail 앞의 lead를 각각 건너뛴다. 두 경로 모두 원본 문자 폭 조회와 동일하게 10픽셀 음절 폭에 `DS:[6CF8]` 간격을 더한다. `29C7:00A4` 출력 폭 조회도 예약 lead에 10픽셀을 반환하고 나머지 문자는 기존 조회를 따른다.

### 2026-10-20 사용자 실행 확인 — 메뉴 문구에 따라 박스 폭이 바뀜

앞선 4바이트 시험본에서 메인 메뉴 표에 쓰이는 `DUNE.ENG` 문자열 인덱스 `27, 28, 29, 92, 334`를 모두 `가나다라`로 바꿨고, 사용자가 실행해 메뉴 박스가 이전보다 작아진 것을 확인했다. 이 관찰은 박스 폭이 문구에 따라 달라짐을 보여 주지만, 문자 폭 계산 자체의 정확성을 검증하지는 않는다. 현재 2바이트 16×16 시험본은 메인 메뉴 네 항목을 `처음하기`, `오프닝 다시 보기`, `불러오기`, `종료하기`로 교체했다. 2026-10-20 사용자가 DOSBox-X에서 실행해 네 문구가 정상 출력됨을 확인했다. 항목별 토큰 바이트와 확인 기록은 [`menu-labels-test.json`](../../../build/analysis/cleanup-2026-10-24/evidence/hangul-runtime-16x16/menu-labels-test.json)에 있다.

앞선 화면에서 메뉴 박스가 좁아진 것은 메뉴 문구 폭에 따라 박스가 바뀐다는 실행 관찰이다. 원본에서 가장 긴 항목이었던 `Replay Introduction`이 네 음절 문구로 대체됐기 때문에 나타난 변화와 맞는다. 그 화면은 4바이트 이전 시험본의 결과이며, 새 2바이트 토큰의 글자 폭 정확성을 증명하지 않았다. 현재 빌드에서는 `2326:002F`의 바이트 카운터를 포함해 폭 계산을 수정했고, 사용자가 네 한국어 선택문의 정상 출력을 확인했다.

### 화면 버퍼 선택을 생략했던 오류 — 수정·실행 확인됨

원본 글리프 렌더러의 파일 `0x25F0B`, `20AA:086B`는 `20AA:0E02`를 호출해 출력 대상 세그먼트를 얻는다. 이 함수는 활성 화면 번호를 읽고 `((화면번호 & 1E) × 2)`로 화면 테이블의 WORD 세그먼트를 선택한다. 반환 AX를 ES로 옮긴 뒤 글리프를 쓴다.

이전 한글 후크는 이 절차 없이 ES를 `A000`으로 고정했다. 수정본은 원본의 `20AA:0E02`가 수행하는 활성 페이지·표 조회를 후크 안에서 재현해 반환된 화면 세그먼트에 그린다. 이 선택을 적용한 뒤 메뉴의 한글 출력이 화면 캡처에서 확인됐다.

### X 중복 이동

이전 후크는 저장된 X를 16 늘리고, 호출부가 복구한 X에 폭 16과 간격을 다시 더했다. 수정본에서는 저장된 X 인자를 건드리지 않아 원본 루프가 한 번만 이동시킨다.

### 콜백 종류 구분과 오류 경로

공유 렌더러 콜백의 폭 조회와 글리프 출력은 반환 IP와 호출 세그먼트 조합으로 구분한다. `2326:0009` 문자열 폭 호출은 원본 폭 조회와 글리프 출력 콜백과 구분해 정·역방향 토큰 소비를 처리한다. FNT 읽기 오류에서는 DOS carry flag를 검사하지 않고 AX의 크기만 비교한다. 잘못된 토큰은 원본 렌더러로 넘기며, 유효하지 않은 두 번째 바이트를 별도 문자로 처리한다. 이 오류 경로는 현재 시험에서 관측된 문제가 아니다.

## 구성 FNT와 이전 기록 정정

## 16×16 메뉴 박스 내부가 검게 남는 원인 — 픽셀 채우기 경계 검사

검은 내부의 원인은 색상표나 한글 글리프 렌더러가 아니라, 메뉴 박스의 솔리드 채우기 함수에 넘기는 포함형 아래쪽 좌표가 화면 높이를 넘은 것이다. 이 경로는 원본 EXE의 함수와 실제 함수 포인터, 팔레트값까지 정적으로 추적했다.

1. 메뉴 오버레이 `0x4A13C`는 `0A0:057F`를 `(1, 2, 13)`으로 호출한다. `0A0:057F`는 박스 레코드 13에서 `DS:[4126..412C]`의 사각형 위치와 크기를 읽는다. 원본 함수는 물리 오프셋 `0x1404F`에 있다.
2. 이 함수는 프레임 헬퍼 `0A0:0008`을 호출한다. 헬퍼의 첫 호출은 채우기 플래그를 켠 뒤, `3342:[66F4]`의 함수 포인터를 통해 `20AA:0D3B`를 호출한다. 포인터는 원본 데이터 세그먼트에서 `20AA:0D3B`로 확인된다.
3. `20AA:0D3B`의 원본 명령은 끝 좌표를 포함형으로 처리한다. Y2가 `200` 이상이면 `cmp dx, 0xC8` / `jge` 경로로 채우기 루프 전에 반환한다. 이 함수는 끝 좌표를 화면 안으로 잘라 주지 않는다. 프레임 헬퍼는 그 뒤에 테두리를 별도 그래픽 호출로 그리므로 채우기만 실패해도 테두리는 남는다.
4. 박스 스타일 3의 색상표는 `DS:[35F8 + 3×8]`이며 첫 값은 `E9`다. `IBM.PAL`의 `E9`는 6비트 RGB `(44, 44, 49)`이고 VGA의 6→8비트 확장 결과 `(178, 178, 199)`가 된다. 옆 테두리에서 쓰는 `E8`은 흰색, `EB`는 `(85, 85, 121)`로, 스크린샷의 회색 내부·흰 테두리·남보라색 그림자 조합과 일치한다. 채우기가 건너뛰면 제목 화면의 검정 바탕이 그대로 보이는 설명도 맞는다.

네 항목의 16×16 메뉴에서는 박스 높이가 `16×4+11=75`다. 기준점 158은 위쪽 126과 포함형 아래쪽 `126+75−1=200`을 만들어 채우기 함수의 경계 검사를 넘는다. 이전 시험값 157은 위쪽 125, 아래쪽 199였다. 이번 요청으로 거기서 2픽셀 더 올린 현재 기준점은 155이며, 위쪽 123, 아래쪽 `123+75−1=197`이다. 생성된 `build/analysis/cleanup-2026-10-24/evidence/hangul-runtime-16x16/patch-report.json`에 실패했던 좌표와 이전·현재 좌표를 기록한다.

따라서 “박스 CG가 없어서 검정” 또는 “한글 폰트가 검정을 쓴다”는 설명은 맞지 않는다. `TITLE.png`에는 제목 로고가 있고 박스는 런타임의 사각형 채우기와 테두리 코드가 그린다. 기준점 158에서는 채우기 호출이 하단 경계 검사에 걸려 화면 바탕이 노출된다. 기준점 155는 정적 좌표 계산상 화면 안이다. 사용자는 한글 메뉴 선택문이 정상 출력됨을 확인했지만 채우기 색상은 별도로 언급하지 않았으므로, 보고서의 `panel_fill_static_analysis.runtime_verified`는 `false`로 남긴다.

별도 FNT의 8바이트 매직 뒤 데이터는 당시 제공된 최소화 Unifont 후보와 같았다. 해당 후보 FNT와 시험용 조합 도구는 현재 사용하지 않아 `font/` 정리 때 제거했다. 당시 후크의 선택식으로 정적으로 대조한 구성 번호는 다음과 같다.

| 음절 | L,V,T | 초성 클래스 | 구성 번호 |
|---|---|---:|---|
| 가 | 0,0,0 | 0 | 0,114 |
| 나 | 2,0,0 | 0 | 12,114 |
| 다 | 3,0,0 | 0 | 18,114 |
| 라 | 5,0,0 | 0 | 30,114 |

이전 문서의 `가 = 1,114를 관측`이라는 기록은 잘못됐다. 받침이 없는 경우의 클래스 표는 `24+V`인데, 앞선 수동 계산은 받침이 있는 표 `24+21+V`를 읽었다. 이 계산값을 런타임 관측값이라고 적은 주장도 철회한다. 이번 결과는 FNT와 소스에서 산출한 정적 값이다.

## 수정 전제와 분석 범위

기존 원본 폰트를 유지하고 별도 한글 FNT를 쓰는 요구는 유지한다. 이전 `255A` 삽입은 폐기했다. 현재 2바이트 시험본은 빌드와 정적 바이트 검사를 마쳤고, 사용자가 DOSBox-X에서 정상 출력을 확인했다. 어시스턴트는 이 변경 이후 DOSBox-X를 직접 실행하지 않았다.

1. 후크를 MZ 로드 이미지의 원래 끝 `0x41C20`에 추가했다. 새 세그먼트는 `3D02`, 진입점은 `01C2`다. MZ 페이지 길이를 갱신했고, 재생성 시 Borland 오버레이 표와 오버레이 바이트가 그대로인지 확인한다.
2. 폰트 로더·변수·파일명이 `255A` 원본 드라이버 메모리를 더 이상 사용하지 않는다.
3. 출력은 원본 활성 화면 페이지 선택을 따르며, 원본 루프가 X를 한 번만 이동시킨다.
4. 메뉴 폭 사전 계산은 2바이트 토큰 단위로 처리하도록 수정했다. 사용자는 시험 메뉴의 출력이 이상 없음을 확인했다. 다른 번역 문자열의 정렬·행 높이는 아직 별도 검증 대상이다.

**과거 런타임 확인:** 앞선 4바이트 시험본은 설치된 `C:\DOSBox-X\dosbox-x.exe`에서 실행했다. 실행 `launch-01m5b2e2dpdsjjjn6s2emrtxka`의 프레임 963 캡처 [menu-frame963.png](../../../archives/builds/verified/hangul-runtime.zip)에 첫 항목 `가나다라`와 나머지 영문 메뉴 세 항목이 함께 보인다. 캡처 SHA-256은 `793a10e94993727942236a4560dfd8986c03ca67ee167605e04ed409e47453f4`다. 이 캡처는 현재 2바이트 빌드의 증거가 아니다. 현재 시험본의 `runtime_verified`는 사용자가 정상 출력을 확인한 사실을 반영해 `true`로 기록했으며, 확인 출처는 `patch-report.json`에 구분해 적었다.

## 원본 메뉴의 문자열 경로

`ENGLISH.PAK`의 `DUNE.ENG`에는 340개 문자열 오프셋이 있다. 메뉴 문자열은 다음 인덱스에 있다.

| 인덱스 | 원본 문자열 |
|---:|---|
| 27 | Play a Game |
| 28 | Replay Introduction |
| 92 | Load a game |
| 29 | Exit Game |

시험본은 27번 문자열만 `D0 80 A0 C0` 형식의 4바이트 토큰 네 개로 바꿨다. `DUNE.ENG[28]`, `[92]`, `[29]`의 문자열 바이트는 원본과 같다. 27번 항목이 12바이트에서 17바이트로 늘어나 뒤쪽 오프셋이 5씩 이동한다. PAK를 다시 풀어 확인했을 때 나머지 문자열 데이터는 그대로다.

`DUNE.PAK`과 `INTRO.PAK`은 원본과 시험본의 SHA-256이 각각 같아 변경되지 않았다. 따라서 시험본에서 기존 영문 글리프가 달라진 원인은 원본 폰트 리소스의 변경이 아니다.

## 폐기한 이전 시험본의 EXE 변경점

아래 변경 목록은 `255A` 코드 공간을 사용했던 폐기본에만 해당한다. 이 EXE는 371,474바이트였고, 코드를 추가한 수정본의 파일 길이는 372,690바이트다.

| 파일 오프셋 | 원본 | 시험본 | 역할 |
|---:|---|---|---|
| `0x2A362` 이후 | 원본 타이머 스택·드라이버 상태 영역 | 후크 코드 등 567바이트 | 잘못된 위치에 삽입됨 |
| `0x2E914` | `32 E4 26 8A 01` | `FF 1E D8 66 90` | 글리프 폭 조회를 후크로 전달 |
| `0x3E6F8` | `BD 07 AA 20` | `C2 01 5A 25` | 콜백 포인터 `20AA:07BD`를 `255A:01C2`로 교체 |

코드 세그먼트 표에서 원래 글리프 렌더러는 `20AA:07BD`, 후크는 `255A:01C2`다. 세그먼트 차이는 `0x04B0`다. 원래 콜백 포인터는 파일 오프셋 `0x25E5D`의 글리프 렌더러 진입점에 대응한다.

원래 텍스트 렌더러의 글자 루프는 파일 오프셋 `0x2E914`에서 폭을 읽고, `0x2E944`에서 콜백을 호출한다. 콜백 직전에 텍스트 렌더러는 `CX`, `BX`, 글자값을 순서대로 스택에 넣는다. 따라서 콜백 프레임에서 `[BP+6]`은 글자, `[BP+8]`은 X, `[BP+10]`은 Y다. 콜백이 끝나면 호출부는 글자 인자를 버리고 저장해 둔 `BX`, `CX`를 꺼낸 뒤 `BX`에 폭과 간격을 더한다.

## 확정된 후크 오류: 한글 글자 폭을 두 번 이동

후크의 `D0` 처리 종료부는 저장된 X값을 16픽셀 더한 뒤 반환한다.

```asm
mov  ax, word ptr [bp+8]
add  ax, 16
mov  word ptr [bp+8], ax
```

하지만 원래 호출부는 콜백 반환 직후 그 저장값을 `BX`로 복구하고, 폭 조회에서 받은 16픽셀과 공통 간격을 다시 더한다. 그러므로 한글 한 글자 뒤의 이동량은 `16 + (16 + 간격)` 픽셀이 된다. 후크의 X좌표 수정은 호출부의 폭 처리와 중복된다. 이 오류는 `가나다라`의 가로 간격을 두 배로 벌린다. 글자 폭만 반환하고 콜백이 저장된 X값을 바꾸지 않는 것이 원래 호출 규약에 맞다.

## 2026-10-21 Hall of Fame 포함 다섯 항목 메뉴 수정

사용자가 `789e0277cc9b` 빌드의 Enter 제한이 정상이라고 확인했다. 이후 요청에 따라 타이틀 메뉴를 현재 위치에서 5픽셀 올리고 다섯 항목일 때 검은 내부가 남는 원인을 수정했다.

원본의 메뉴 높이는 `16×항목 수+11`, 위쪽은 `기준점−(16×항목 수)/2`다. 이전 기준점 155에서 다섯 항목은 위쪽 115, 높이 91, 포함형 아래쪽 205였다. 요청대로 기준점만 150으로 옮기면 위쪽 110, 아래쪽 200이다. 원본 채우기 `20AA:0D3B`는 Y2가 200 이상이면 사각형 전체를 그리지 않기 때문에 5픽셀 이동만으로는 해결되지 않는다.

따라서 기준점을 155에서 150으로 옮기고, 박스 여유 높이를 11에서 10으로 줄였다. 글자 셀과 행 간격 16픽셀은 그대로다. 다섯 항목은 위쪽 110, 높이 90, 아래쪽 199가 되고, 네 항목은 위쪽 118, 높이 74, 아래쪽 191이다. 박스 내부는 기존 스타일 3의 회색 E9 채우기를 그대로 사용한다. 전역 채우기 함수의 경계 검사는 변경하지 않았다.

현재 EXE SHA-256은 `1351f62bd837703a72580df275a0734499dca4456b2add6db97025a4045d7eb9`, 제목 식별자는 `1351f62bd837`이다. 실행 배치는 루트 `듄2_치트테스트.bat`이다. 적용한 공통 메뉴 레이아웃 소스는 `tools/build_hangul_runtime_patch.py`이며 `16x16-memoryfix` 기반을 재빌드한 뒤 치트 빌드를 재생성했다.

직전 EXE와 새 EXE의 길이는 377,794바이트로 같다. 실제 변경은 파일 오프셋 `0x4B908`의 `9B→96`과 `0x4B917`의 `0B→0A` 두 바이트뿐이다. 치트 모듈 해시는 동일하여 사용자가 확인한 Enter 제한 코드도 동일하다. 빌드 직전 저장 파일 해시와 빌드 후 실제 파일 해시가 일치한다. 근거는 `build/analysis/title-menu-five-items/layout-change.json`이며 이전 EXE는 같은 폴더의 `before/`에 보관했다.

이번 작업에서는 게임을 실행하지 않았다. 회색 배경이 실제 화면에 나타나는지는 사용자 확인 전이다. 이전 치트창의 진행 중 소실 문제는 이번 메뉴 좌표 수정 대상에 포함하지 않는다.
