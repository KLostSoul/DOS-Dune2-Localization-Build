# Dune II 치트창 소실 원인: 원본 화면 갱신과 후크 대조

작성일: 2026-10-21

## 분석 대상과 사용자가 확인한 현상

사용자는 **치트창이 처음에는 정상적으로 표시되지만 게임이 진행되면서 창이 사라진다**고 확인했다. 처음부터 패널을 그리지 못하는 현상으로 바꾸어 해석하지 않는다.

- 원본 EXE SHA-256: `99f44e83b309dd826f3dbc5068c61679bb68047eed8d738dcef594ba0eef7552`
- 현재 치트 EXE SHA-256: `6855dcdf746a2f6305d492a838d5adb2b2cc53c3ba27929636d5484ef275f327`
- 현재 패널: `(16,160)`부터 `128×32`, 포함 좌표 `x=16..143, y=160..191`
- 현재 치트 모듈의 로드 이미지 상대 세그먼트: `3DF4`

주소는 원본 MZ 로드 이미지에 대한 상대 세그먼트 주소다. DOS 실행 시 실제 CS에는 로드 세그먼트가 더해진다. 아래 분석은 원본/현재 EXE 바이트, 역어셈블, 후크 제어 흐름과 좌표 계산을 사용했다. 이번 작업에서 DOSBox-X나 게임은 실행하지 않았다. 실행 파일도 수정하거나 다시 빌드하지 않았다.

## 원인

치트창은 키 입력 시 그려지지만, 정상 게임 루프가 그 뒤에 전장 버퍼의 변경 구역을 표시 화면으로 복사한다. 이 복사 구역은 치트창과 겹치며 원본 코드에는 치트창을 피하는 처리가 없다. 치트 후크에는 복사가 끝난 뒤 창을 다시 그리는 연결도 없다. 따라서 처음 정상 표시된 창이 게임 진행 중 갱신된 구역부터 지워질 수 있다.

이 결론은 단순히 “화면 갱신 후크가 없다”는 소스 관찰에 그치지 않는다. 덮어쓰는 원본 호출 경로, 실제 쓰기 명령, 쓰기 좌표와 현재 EXE에서 그 코드가 보존된 사실을 아래와 같이 특정했다.

## 1. 정상 게임 루프에서 표시 화면으로 이어지는 경로

```text
044B:03D4  전장 갱신 함수 05DD:0000 호출 (인자 page=0)
  05DD:02BF  PUSH CS / near CALL 034D
    05DD:0387  239C:000A 호출 (작업 페이지를 2로 변경)
    ... 전장 타일·유닛·효과 등을 작업 페이지에 그림 ...
    05DD:153F  22D5:0007 호출 (변경된 타일 행을 page 2에서 page 0으로 복사)
      22D5:0092  FAR CALL ES:[66C8]
        3342:66C8 = 20AA:06E1
          20AA:0751 / 0759  원본/대상 페이지의 세그먼트를 각각 조회
          20AA:0754 / 075C  DS=원본 페이지, ES=대상 페이지
          20AA:078D        REP MOVSW로 실제 픽셀 복사
```

`239C:000A`는 이전 `3342:[6D1D]`를 반환하면서 인자로 받은 페이지 번호를 이 전역 변수에 기록한다. `05DD:0383..0387`은 상수 2를 전달한다. `05DD:155F`에서 이전 작업 페이지 번호를 복구한다.

`05DD:1526`은 대상 페이지 번호 0을 스택에 넣고, `1529`는 현재 작업 페이지 번호 `[6D1D]`를 원본 페이지로 넣는다. 이 경로에서 작업 페이지는 2다. `153F`의 호출은 다음 계약을 따른다.

| FAR 호출의 BP 기준 인자 | 의미 | 해당 경로의 값 |
|---|---|---|
| `+06`, `+08` | 원본 X, Y | 변경 구역의 시작 |
| `+0A`, `+0C` | 대상 X, Y | 원본과 같은 화면 위치 |
| `+0E`, `+10` | 폭, 높이 | 변경된 타일 구간 폭, 16픽셀 높이 |
| `+12` | 원본 페이지 | 2 |
| `+14` | 대상 페이지 | 0 |

X와 폭은 이 복사 API에서 8픽셀 단위다. `20AA:06EF..06FD`와 `071D..072B`가 X를 3비트 왼쪽 이동하며, `075E..076D`는 폭을 WORD 개수로 바꾼다. `078D`는 그 개수만큼 복사하고 `078F/0791`은 다음 행의 320바이트 간격에 맞춘다.

원본 VGA 초기화 경로는 표시 페이지 0의 세그먼트를 `A000h`로 설정한다. 반면 2번은 전장 작성에 사용하는 작업 페이지다. **원본의 현재 작업 페이지 선택 함수 `20AA:0E02`가 표시 페이지를 항상 반환하는 것은 아니다.** 원본 FNT 렌더러가 이 함수를 쓰는 이유는 게임이 지정한 작업 버퍼에 문자를 그리기 위해서다.

## 2. 패널과 전장 복사 좌표가 실제로 겹친다

`05DD:14DD..14E4`는 타일 행 번호 `r`의 화면 Y를 `40 + 16*r`로 계산한다. `150A`는 복사 높이를 16으로 설정하며 `154A`의 루프는 0..9행을 처리한다. X는 타일 열의 16픽셀 간격에 대응한다.

현재 패널은 타일 열 1..8과 다음 세 행에 걸친다.

| 타일 행 r | 복사 Y 범위 | 패널과 겹치는 Y 범위 |
|---|---|---|
| 7 | 152..167 | 160..167 |
| 8 | 168..183 | 168..183 |
| 9 | 184..199 | 184..191 |

변경 구역의 X 범위가 패널과 겹치면 `REP MOVSW`가 그 겹친 픽셀을 그대로 교체한다. 게임은 화면 전체를 항상 다시 복사하지 않고 변경된 타일 행의 구간을 복사하므로, 창이 한 번에 전부 없어질 수도 있고 일부분부터 사라질 수도 있다. 이는 초기 표시 성공과 양립하는 원본 동작이다.

`05DD:1468 → 2A1C:0006`에는 다른 전장 전환용 복사 경로도 있다. 그러나 현재 사용자가 확인한 “정상 표시 후 진행 중 소실”을 설명하는 데는 위의 정상 변경 구역 복사 경로만으로 충분하다. 스크린샷 한 장으로 두 경로 중 어느 명령이 특정 프레임에 적중했는지 측정한 것으로 보고하지 않는다.

## 3. 현재 후크에는 원본 복사 이후의 재표시가 없다

현재 EXE에 들어 있는 후크 코드를 실제 바이트에서 다시 디코드했다.

| 현재 EXE 상대 주소 | 역할 |
|---|---|
| `3DF4:0040` | 키보드 입력 후크 진입 |
| `3DF4:0471` | SavePanel |
| `3DF4:049C` | RestorePanel |
| `3DF4:04C0` | DrawPanel |
| `3DF4:04E6` | DrawVideoPanel |
| `3DF4:0583` | SelectVideoPage |

`DrawPanel`의 직접 CALL 위치는 `3DF4:00DE, 0135, 0148, 019E, 01B3`다. 모두 키보드 입력 후크의 열기·문자 입력·삭제·오류 표시·키 해제 경로에 있다. 원본 게임 루프나 전장 복사 함수에서는 이 루틴을 호출하지 않는다.

EXE 패치 지점도 시작 시 스택 처리, 키 입력 함수, 키보드 ISR 후속 분기, 임무 결과 분기의 네 곳이다. 전장 갱신 완료 지점에 패치를 넣은 기록이나 명령 바이트는 없다.

따라서 다음 순서가 가능하며, 창이 진행 중 사라지는 결함을 만든다.

```text
키 입력 → 치트창 정상 표시
게임 실행 계속 → 전장 변경 구역을 page 2에서 page 0으로 복사
복사 구역과 겹치는 치트창 픽셀 교체
그 뒤의 치트창 재표시 없음
```

페이지 번호를 키 입력 시 다시 읽거나 좌표만 바꾸어도 이 실행 순서가 보장된 채로 남는다.

## 4. 원본과 현재 EXE의 대조

아래 구간은 원본과 현재 치트 EXE에서 바이트 단위로 동일하다. 구간 끝은 미포함이다. 각 구간의 양쪽 SHA-256은 `evidence.json`에 기록했다.

| 구간 | 의미 | 대조 |
|---|---|---|
| `044B:0306..0414` | 정상 게임 루프의 그리기·갱신 호출 | 동일 |
| `05DD:034D..1574` | 전장 작업 페이지 작성·표시 페이지 복사 | 동일 |
| `239C:000A..0025` | 작업 페이지 번호 변경 | 동일 |
| `22D5:0007..009E` | 변경 구역 복사 래퍼 | 동일 |
| `20AA:06E1..07A0` | 실제 화면 구역 복사 | 동일 |
| `20AA:0E02..0E24` | 현재 작업 페이지 선택 | 동일 |
| `23C9:0008..03F8` | 그래픽 페이지 초기화 | 동일 |
| `3342:66C8` | 복사 함수 포인터 `E1 06 AA 20` | 동일 |

즉 원본 전장 갱신 코드의 손상으로 생긴 결함이 아니라, 추가한 치트창이 원본 화면 갱신 순서에 연결되지 않은 데서 생긴 결함이다.

## 5. 앞선 설명의 정정과 별도 발견

### 작업 페이지와 표시 페이지

앞선 수정은 원본 FNT와 같은 작업 페이지를 선택하면 치트창도 올바르게 유지될 것이라는 전제를 사용했다. 이번 역분석에서 그 전제가 부족함을 확인했다. 전장 함수는 작업 페이지를 일시적으로 2로 바꾸고 표시 페이지 0으로 필요한 구역만 옮긴다.

키보드 인터럽트에서 현재 작업 페이지에 직접 창을 그리는 설계에는 게임용 작업 버퍼에 창이 섞일 위험도 있다. 이는 이번 사용자 관찰과 별도로 확인한 구조적 위험이며, “처음부터 창이 일부만 표시됐다”는 관찰로 바꾸어 설명하지 않는다.

### 빨간 테두리

빨간 아래 선이 게임의 덮어쓰기를 입증한다는 앞선 설명은 잘못됐다. 치트 코드가 아래/오른쪽 테두리에 쓰는 인덱스 `08h`는 원본 `IBM.PAL`에서 6비트 RGB `(42,0,0)`, 표시 RGB `(170,0,0)`인 빨강이다. 치트 소스 주석의 “dark lower/right edge”와 실제 팔레트가 맞지 않는다. `EBh`는 같은 팔레트에서 `(85,85,121)`의 어두운 UI 색이다. 이번에는 팔레트 인덱스를 수정하지 않았다.

## 6. 수정 시 지켜야 할 렌더 순서

치트창의 그리기 요청과 실제 픽셀 출력을 분리해야 한다. 키보드 ISR은 입력 상태와 다시 그릴 필요만 기록하고, 일반 게임 실행 문맥에서 전장 복사가 끝난 뒤 표시 페이지에 치트창을 덧그려야 한다. 게임용 작업 페이지 2에 치트창을 그리지 않아야 한다.

정상 게임 루프에서 `044B:03D9`는 전장 갱신 호출 직후다. 다만 `044B:03E7`에는 메시지 큐 갱신이 추가로 있으므로 이 앞에서 그리면 모든 출력의 최종 단계라고 단정할 수 없다. `044B:03EF`는 전장·메시지 갱신 후에 놓이는 정상 게임 루프의 후크 후보 지점이다. 이 주소를 모든 메뉴·승패 화면의 공통 완료 지점이라고 주장하지 않는다.

배경 복원도 처음 열 때 저장한 화면을 장시간 뒤에 덮어쓰면 진행된 전장 내용을 되돌릴 수 있다. 수정 시에는 갱신된 화면과 패널의 저장·복원 순서를 함께 다뤄야 한다. 키 입력마다 패널을 반복해서 그리는 조치만으로는 이번 결함을 해결했다고 판정할 수 없다.

역분석을 끝낸 시점에는 실행 파일을 수정하지 않았다. 이후 사용자 지시에 따른 적용 기록은 7절에 있다. 해당 스크린샷이 찍힌 순간의 실제 작업 페이지 번호, 변경 구역 인자, 덮어쓰기 명령의 런타임 적중 기록은 확보하지 않았다. 정적으로 규명한 것은 정상 표시 후 소실을 만드는 원본의 구체적인 복사 경로와 당시 치트 후크의 연결 누락이다.

## 7. 프레임 후크 적용 (2026-10-21)

사용자의 수정 지시에 따라 적용했다. 새 EXE SHA-256은 `0a01ceb6b5c70939b7584860e8a99e36dbf5d3ec104331a3c0ba0d657078ea9b`다.

| 수정 지점 | 적용 내용 |
|---|---|
| `044B:0309` | 원래 `CALL 239C:000A`를 `CALL 3DF4:0240`으로 교체. 원래의 페이지 0 선택과 AX의 이전 페이지 반환을 재현하고, 이전 패널이 있으면 현재 2번 작업 페이지에서 동일 구역을 0번 표시 페이지로 복사해 제거한다. |
| `044B:03EF` | 원래 `CMP [38EC],0`을 `CALL 3DF4:0280`으로 교체. 정상 게임 상태에서 전장·메시지 갱신 후 열린 창을 다시 그리고, 원래 비교 명령을 실행해 플래그를 반환한다. 종료 상태면 입력창 상태를 닫는다. |
| 키보드 ISR | 패널 그리기·복원 호출을 모두 제거했다. 입력 내용과 열림/닫힘 상태만 변경한다. |
| 화면 배경 | 치트창용 4 KiB XMS를 제거했다. 패널 구역이 전장 안에 있으므로 현재 페이지 2의 깨끗한 전장 픽셀을 이용한다. 패널은 페이지 0에만 그려 페이지 2를 오염시키지 않는다. |
| 마우스 | 원본 영역 숨김 `2971:0191`과 표시 `2971:028C`를 화면 쓰기 전후에 짝지어 사용한다. FAR 포인터 세그먼트는 시작 시 로드 베이스에 맞춰 계산한다. |
| 테두리 | 빨강인 `08h`를 원본 UI 그림자 색 `EBh`로 교체했다. |

프레임 후크는 FLAGS, 16비트 일반 레지스터, DS/ES를 보존한다. 프레임 시작은 원래 페이지 선택 함수의 AX 반환값을 먼저 설정해 저장한다. 프레임 종료는 레지스터·FLAGS 복구 후 실제 원본 비교를 실행하여 다음 `JE 0405`의 조건 플래그를 재현한다. 화면 복사는 `CLD` 상태에서 수행하고 원래 DF를 복구한다.

프레임 시작 후크는 원래 FAR CALL의 재배치 `044B:030C`를 재사용한다. 종료 후크에는 `044B:03F2`를 추가한다. 기존 시작·입력·결과 후크와 함께 추가 재배치 수는 4개다. 상주 모듈 크기 `0x0990`과 기존 스택 이동 크기는 늘리지 않았다. 한글 비트맵용 기존 10 KiB XMS는 별도이며 유지한다.

빈 Enter·Esc 또는 명령 실행으로 창을 닫으면 다음 프레임 시작에서 최신 전장을 복원한다. 처음 열 때 저장한 오래된 화면을 덮어쓰지 않는다. 정상 게임 진행 중 원본 변경 구역 복사가 패널을 덮더라도 해당 루프의 갱신 완료 후 다시 표시한다.

빌더는 기존 `_SAVE*.DAT`, `SAVE*.DAT`를 기반 트리 복사에서 제외하고 빌드 전후 해시를 대조한다. 저장 파일은 보존됐다.

`tools/audit_cheat_frame_overlay.py`로 조립된 EXE를 정적으로 확인했다. 시작·키 입력·ISR 후속 처리·프레임 시작·프레임 끝·결과의 6개 진입점에서 도달 가능한 572개 명령에 중첩이나 코드 밖 직접 분기가 없었다. 각 진입점과 near 헬퍼의 SP/BP 깊이가 복귀 계약과 일치했다. 키보드 입력 경로는 화면 복사·채우기·마우스 FAR 호출에 도달하지 않으며, 치트 XMS 호출도 없다.

전체 재배치 목록, 기존 원본 FAR CALL의 재배치 재사용 횟수, 프레임 종료의 실제 비교 명령을 대조했다. 원래 한글 시험 EXE의 상주 바이트는 명시한 6개 패치 지점 외에 바뀌지 않았고, FBOV 오버레이·명령 레지스트리·5×7 글리프도 보존됐다.

## 8. 깜박임 재보고와 게임 중 Enter 제한 (2026-10-21, 최신 적용)

7절의 `0a01ceb6…` 후보는 사용자 확인에서 창과 전장이 번갈아 보이는 깜박임이 발생했다. 매 프레임 시작에 표시 페이지 0의 패널을 지우고 프레임 끝에 다시 그리는 순서가 전장을 노출하는 구간을 만들었다. 앞선 정적 분기·스택 검사 통과는 화면 유지가 검증됐다는 의미가 아니었다. 7절은 실패한 이전 적용 기록으로 보존하며, 현재 동작은 이 절을 따른다.

### 표시 유지 방식

- 열린 창은 매 프레임 지우지 않는다. 처음 열거나 입력 내용이 변경됐을 때만 그린다.
- 원본 행 복사 `20AA:078D`의 `REP MOVSW; ADD SI,BX; ADD DI,BX`를 보호 복사 후크로 연결했다. 표시 페이지 0으로 전장을 복사할 때 열린 패널 `x=16..143, y=160..191`과 겹치는 부분만 건너뛰고 양쪽 전장은 원래대로 복사한다. 원래 SI/DI 이동량과 CX 종료값을 유지한다.
- 모달 처리 중에는 원래 복사를 허용하고 패널 재표시 필요 상태를 기록한다. 모달 화면을 가리지 않도록 입력도 함께 차단한다.
- 창을 닫을 때만 페이지 2의 최신 전장으로 복원한다. 전장 작업 페이지 2에는 패널을 기록하지 않는다.

### Enter가 저장·이름 입력에서 빠진 문제

키보드 후크가 그래픽 모드와 임무 상태만 보고 Enter를 가로채면 같은 임무 안에서 호출되는 저장 이름 입력도 치트 진입으로 처리할 수 있다. 정상 게임 진행 여부를 별도 허용 플래그로 관리하고, 다음 원본 호출 경계를 추가 연결했다.

| 원본 위치 | 원본 호출 | 적용 |
|---|---|---|
| `044B:0317` | 위젯·메뉴 처리 `32A5:002A` | 호출 중 치트 차단. 원래 두 인자를 복사해 전달하고 반환 후 허용 복구. 저장·불러오기 및 그 안의 문자 입력은 원래 키 처리 사용. |
| `044B:03A9` | 게임 명령 처리 `044B:0481` | 단축키에 따른 메뉴 처리 중 차단. 원래 인자 하나를 전달하고 반환 후 허용 복구. |
| `044B:03FD` | 임무 결과 평가 `1223:02A9` | 치트 입력과 패널을 닫고 허용 상태를 해제한 뒤 원본으로 FAR JMP. 승패·스코어 이름 입력으로 차단 상태 유지. |
| `044B:03EF` | 정상 게임 프레임 완료 | 정상 진행 상태에서만 허용. 게임 종료 상태에서는 해제. |

허용 플래그는 시작 시 0이다. 비허용 상태의 Enter는 원래 키 처리기로 전달한다. 키 해제는 비허용 상태에서도 치트 반복 방지 표에 반영해 메뉴 전환 때 눌림 상태가 남지 않도록 했다. 키보드 인터럽트에서는 그래픽·마우스·XMS 함수를 호출하지 않는다.
