# 폰트·치트의 상주 배치와 DOS 힙 확장

DOS 메모리 오류는 남은 총량뿐 아니라 PSP 뒤의 연속 공간과 Borland 힙 상한으로 판정해야 한다. 별도 폰트 블록이 메인 블록 바로 뒤에 있으면 같은 PSP 소유여도 기존 블록의 연속 확장을 막는다.

## 원본 오류 경로

Borland `0000:17E0`은 FAR 힙 부족 시 `1AE8`로 확장을 요청한다. `1B62`는 break 변경 `1A33`을 호출하고 `1A7D`가 원래 PSP와 새 크기를 `21DE`에 전달한다. `21E1..21E9`의 DOS `AH=4Ah`는 기존 PSP 블록을 확장한다.

```text
AH=4Ah 연속 확장 실패: CF=1, AX=8, BX=최대 크기
0000:21F2..21F7 → 최대 크기를 반환
0000:1A94..1A99 → DS:[0091] 상한 갱신
0000:1AA2 → AX=0
0000:1B65..1B67 → 실패 분기
0000:1B11..1B14 → FFFF:FFFF
0000:17E7..17EA → 실패값 확인
0000:1824..1826 → NULL
21E5:0087..009A → 오류 콜백
232C:001B..002A → Insufficient memory와 키 대기
```

상한이 낮아진 뒤의 요청은 `0000:1B3C..1B4D`에서 더 일찍 거절될 수도 있다. `maxalloc=FFFFh`나 실행 이미지 크기만으로 실제 힙 여유량을 확정할 수 없다.

## MCB 관측의 해석

| 항목 | 관측값 |
|---|---|
| 메인 MCB | 074A, 583,680바이트 = 8E80h 문단 |
| 바로 뒤 할당 MCB | 95CB, 11,040바이트 = 02B2h 문단 |
| 그 뒤 자유 MCB | 987E, 30,720바이트 = 0780h 문단 |
| 확장 요청 | AX=4A4Bh, ES=074B, BX=9200h |

요청 증가분은 380h 문단, 14,336바이트다. 총 자유 공간은 충분해도 중간의 할당 블록 때문에 AH=4Ah가 합칠 수 없다. 비교 폰트 로더 `3D02:0616..061B`의 `BX=02B2h/AH=48h`와 이 블록 크기가 일치한다. MCB 이름만으로 폰트라고 판정하는 대신 실제 로더 요청·크기·유지 시점을 함께 확인한다.

이 값은 해당 덤프의 배치이며 최종 빌드의 여유량을 뜻하지 않는다. 별도 블록을 없앤 달무리 관측에서는 메인 579,584바이트 뒤에 자유 45,872바이트가 연속했다.

## 원본 할당기와 XMS 계약

게임 FAR 할당·해제는 관리 바이트와 전체 포인터를 보존해야 한다. `21E5:000E`의 반환 DX:AX 중 AX를 버리거나 내부 포인터를 `21E5:01CC`에 전달하면 헤더를 잘못 읽는다. 상세 계약은 [폰트 수명](../fonts/font_memory_lifecycle.md)에 있다.

XMS 성공 여부는 CF가 아니라 AX=1이다. 이동 구조체는 DWORD 길이, WORD 원본 핸들, DWORD 원본 위치, WORD 대상 핸들, DWORD 대상 위치이며 필드 오프셋은 0/4/6/10/12다. 파일 읽기·XMS 이동 뒤 레지스터를 무조건 보존된 것으로 가정하지 않는다.

## 최종 배치 규칙

달무리 데이터와 처리 코드는 MZ 상주 이미지에 넣고 뒤쪽 치트·스택·재배치를 함께 계산한다. 별도 DOS 폰트 MCB와 FAR 힙 할당을 만들지 않는다. 영상 Unifont와 치트 배경은 XMS를 사용한다. 현재 크기는 번역과 생성 결과에 따라 달라지므로 [폰트 안내](../../FONTS.md)의 배치와 빌드 보고서를 따른다.

키보드 IRQ에서 화면·XMS를 호출하지 않고 정상 게임 루프에서 저장·그리기·복원한다. 배경 저장은 행 간격을 포함해 패널 전체를 다뤄야 한다. 288×32 패널을 320픽셀 피치로 그리면서 연속 9,216바이트만 저장하는 비교 구현은 896픽셀을 저장하지 못한다. 최종 128×32 패널은 [모달 대기 규칙](cheat_modal_wait.md)을 따른다.
