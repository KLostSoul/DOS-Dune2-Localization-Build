# 치트 추가 후 메모리 오류: 원본·한글 전용·치트 빌드 정적 대조

작성일: 2026-10-20. 실행 파일, 기존 문서, 치트 소스를 대조했다. 게임을 새로 실행하거나 게임 EXE를 수정하지 않았다. 사용자의 프로세스 중단 지시 후 DOSBox-X 1개와 작업용 EmuCap 서버 6개를 종료했고, 이후 작업은 파일 기반 정적 분석만 수행했다.

## 1. 확인된 결론과 범위

치트 코드를 2,448바이트로 줄였다는 사실만으로 메모리 오류가 해결됐다고 판단할 수 없다. **현재 치트 시작 후크는 한글 전용 빌드보다 초기 힙 경계를 4,208바이트 뒤로 이동시킨다.** 이전 문서는 파일 증가량과 실제 힙 경계 이동량을 구분하지 않았다.

**오류 문구를 출력하는 원본 경로는 게임 메모리 할당 실패 처리다.** 이 할당기·오류 처리기 자체는 원본, 한글 전용, 치트 빌드에서 바이트가 동일하다. 치트는 시작 메모리 배치와 키보드 처리 경로를 변경한다.

**치트 입력기는 DOS 텍스트 모드와 남아 있는 플레이어 포인터만으로도 활성화된다.** 따라서 게임의 치명적 오류 처리 중 키 대기에서도 Enter를 가로채 치트 창을 표시하고 원래 키 대기를 방해할 수 있다. 사용자 캡처에 오류 문구와 치트 창이 함께 보이는 현상과 부합하는 코드 경로다. 이 입력 조건은 정상 게임 문맥 판정으로 사용할 수 없다.

정적 파일과 캡처만으로 이번에 실패한 할당의 요청 크기, 당시 사용 가능 블록, 호출자를 특정할 수는 없다. **4,208바이트의 경계 이동이 이번 오류의 유일한 원인이라고 확정하지 않는다.** 아래 항목은 실제 바이트로 확인한 결함 및 메모리 변화다.

## 4. 시작 코드에서 실제로 달라진 메모리 경계

원본 시작 코드는 다음 순서로 스택과 힙을 정한다.

```text
0000:0059  DX = SS
0000:005B  BP = DOS 블록 끝 세그먼트 - DX
0000:0062  DI = DS:[7AF4]       ; 세 빌드 모두 1000h
0000:0075  DI = (DI >> 4) + 1  ; 0101h 문단
0000:0083  BX = DX + DI
0000:0085  DS:[0089] = BX      ; 힙 하한
0000:0089  DS:[008D] = BX      ; 초기 break
0000:0097  INT 21h/AH=4Ah      ; PSP 블록 크기 조정
0000:009D  SS = DX
0000:009F  SP = 1010h
```

치트 빌드는 `0000:005D`를 `3D68:0000`으로 바꾸고, 그 후크에서 `DX = 로드 기준 + 3E01h`, `BP -= 0107h`로 변경한다. 이어서 원래 `0000:0062`로 돌아간다. 위 계산이 다른 DX로 실행되므로 힙 하한도 이동한다.

| 항목 | 원본 | 한글 전용 | 현재 치트 |
|---|---:|---:|---:|
| MZ 헤더 초기 SS:SP | `3CFA:0080` | `3CFA:0080` | `3CFA:0080` |
| 시작 코드가 정하는 SS:SP | `3CFA:1010` | `3CFA:1010` | `3E01:1010` |
| 초기 힙 시작 세그먼트 | `3DFB` | `3DFB` | `3F02` |
| 초기 PSP 블록 예약 문단 | `3E0B` | `3E0B` | `3F12` |

힙 경계 이동량은 `(3F02h − 3DFBh) × 16 = 4,208`바이트다. 치트 파일 증가량 `0x990 = 2,448`바이트와 다르다. 초기 실행 이미지 크기만 비교해서 메모리 손실량을 계산한 이전 설명은 불충분했다. 또한 원본 시작 코드는 최대 DOS 블록을 그대로 계속 유지하지 않고 `AH=4Ah`로 줄이며, 이후 힙 처리에서 다시 확장한다. `maxalloc=FFFFh`만으로 게임 내부 할당 상태를 확정하면 안 된다.

한글 전용 빌드도 무조건 안전한 메모리 기준으로 사용할 수 없다. 한글 후크의 로드 이미지 `[3D020h,3D680h)`는 원본이 예약하는 스택 `[3CFA0h,3DFB0h)` 안에 들어 있다. 현재 치트의 스택 이동은 이 겹침을 피하는 효과가 있지만, 그만큼 초기 힙 경계를 뒤로 민다. 이것은 주소 범위의 정적 겹침이며, 어느 시점에 스택이 한글 코드까지 내려갔는지를 실행 관측한 결과는 아니다.

근거: [`원본 시작 코드`](../../../build/analysis/cheat-static/original-0000-0000.txt), [`현재 후크의 실제 명령`](../../../build/analysis/cheat-static/compiled-hook-blocks.txt).

## 5. 오류 화면에서 치트 창이 뜨는 이유

원본은 메모리 오류를 출력한 뒤 `27EC:0804`에서 게임 키 큐의 입력을 기다린다. 게임 정리는 이 키 대기 뒤에 있다.

치트는 원본 키 입력 함수 `27EC:0A54`와 INT 09h 처리 후속 지점 `27EC:0F0B`를 가로챈다. 새 입력기는 Enter make 코드 `1Ch`일 때 BIOS 모드가 `03h` 또는 `13h`이고 `DS:[3A30]`이 0이 아니면 창을 연다. 메모리 오류 처리 중인지, 임무 실행 중인지, 종료 중인지 확인하는 조건이 없다.

이 경로에서는 `SavePanel`, `DrawPanel`을 호출하고 `CONSUME=1`로 설정해 원래 키 이벤트 처리를 건너뛴다. `AfterKeyHook`는 IRQ 확인/복귀 지점 `27EC:0F58`로 보내므로, 원래 오류 처리기가 기다리는 키 큐에 해당 Enter가 들어가지 않는다. 치트 창 안에서 입력 없이 Enter를 누르면 명령 검색을 건너뛰고 `ClosePanel`로 닫도록 바꿨다.

따라서 오류 문구 위에 치트 창이 보이는 것은 이 입력 조건으로 설명된다. **치트 창이 보인다고 정상 임무 문맥에서 치트가 작동한 것으로 기록하면 안 된다.** 텍스트 모드를 허용한 현재 설계와 오류/종료 상태 차단 누락이 확정된 문제다.

현재 텍스트 창도 원본 게임 UI를 사용하지 않는다. 직접 `B800:07D0`부터 320워드를 쓰며, 80열 텍스트 모드에서 시작 위치는 12행 40열이다. 이 위치는 행의 시작이 아니므로 채움과 문자열이 화면 행 경계를 가로지른다.

## 6. 인터럽트 안의 작업 및 별도 결함

### IRQ 내부에서 처리하는 범위가 지나치게 크다

원본 INT 09h는 스캔 코드 변환, 키 상태/큐 처리, IRQ 종료로 이어진다. 현재 치트는 그 중간에서 XMS 화면 이동, 화면 그리기, 명령 검색, 플레이어 자금 쓰기, 임무 종료 요청까지 실행한다. 설계 문서의 '입력만 수집하고 메인 루프의 안전한 지점에서 효과 적용'을 구현한 상태가 아니다. 특히 `CREDITS`는 인터럽트가 중단시킨 게임의 자금 처리와 동기화되지 않는다. 다만 이 구조만으로 이번 메모리 오류의 직접 원인을 단정하지 않는다.

### XMS 성공 판정이 잘못됐다

현재 EXE `3D68:07CC`의 XMS 할당 호출 뒤는 `JB 07DE`이며, `3D68:07F2`의 이동 호출 뒤도 CF로 분기한다. XMS의 성공 결과 AX를 검사하지 않는다. 저장된 DOSBox-X 참조 소스 `src/ints/xms.cpp`의 `SET_RESULT`는 AX에 성공 1/실패 0, BL에 오류 코드를 기록하며 CF를 성공 결과로 설정하지 않는다. 따라서 현재 코드는 XMS 실패를 정확히 검출하지 못하며 준비/저장 성공 플래그가 결과와 어긋날 수 있다. 이 결함이 이번 conventional memory 할당 실패를 직접 일으켰다고 확인된 것은 아니다.

### 첫 그래픽 패널 구현의 백업 범위가 그리는 범위와 다르다

2026-10-21 크기 수정 전 패널은 너비 288, 높이 32, 화면 행 간격 320으로 그렸다. 저장은 첫 주소 `A000:C810`부터 연속 `0x2400 = 9,216`바이트만 복사했다. 행 간격을 고려하면 그리는 픽셀 896개가 저장 범위 밖에 있다. 따라서 저장 호출이 성공해도 패널 전체의 복원은 보장되지 않았다. 새 구현에서 행별 백업으로 고친 내용은 18절에 기록했다. 이는 화면 복원 결함이며, 게임 할당 실패의 직접 근거로 사용하지 않는다.

## 7. 수정 전에 충족해야 하는 조건

1. 추가 코드·폰트·스택·힙의 소유 범위를 함께 확정한다. 기존 한글 빌드의 스택 겹침도 고려하고, 파일 증가량으로만 메모리를 보고하지 않는다.
2. 정상 임무 상태와 오류/종료/모달 상태를 실제 원본 상태 변수로 구분한다. BIOS 모드와 플레이어 포인터만으로 Enter를 가로채지 않는다.
3. 키 인터럽트는 입력 수집으로 제한하고 화면/XMS/게임 상태 변경을 원본 메인 루프의 확인된 처리 지점으로 옮긴다.
4. XMS 반환값과 화면 저장 범위를 바로잡고, 실패 시 입력창을 열지 않는 경로를 정의한다.
5. 이번에 실패한 구체적인 할당은 현재 정적 근거만으로 확정하지 않는다. 확인되지 않은 요청 크기나 자유 블록 상태를 만들어 원인으로 기록하지 않는다.

이번 작업에서는 분석기와 증거·문서만 추가했다. 게임 EXE, 치트 어셈블리, 빌더, 실행 설정은 변경하지 않았다.

## 8. 추가 추적: 별도 폰트 DOS 블록과 Borland 힙 확장의 충돌

### 2026-10-21 사용자 제공 DOSBox-X 관측으로 확인된 실제 배치

이후 사용자가 LOSE 입력 시점의 MCB 목록과 `INT 21h/AH=4Ah` 중단점 레지스터를 제공했다. 이 관측으로 아래에서 미확정이라고 표시했던 폰트 블록 인접 조건이 실제 실행에서 성립했음을 확인했다.

| 관측 | 값 | 의미 |
|---|---:|---|
| 게임 메인 MCB | `074A`, 583,680바이트 = `8E80h` 문단 | 데이터 세그먼트 `074B`의 현재 크기 |
| 바로 뒤 할당 MCB | `95CB`, 11,040바이트 = `02B2h` 문단 | 소유 PSP는 DUNE2. 크기는 한글 로더의 AH=48h 요청과 일치 |
| 뒤쪽 자유 MCB | `987E`, 30,720바이트 = `0780h` 문단 | 폰트 블록 때문에 메인 블록에 연속하지 않음 |
| DOS 호출 | `AX=4A4Bh`, `ES=074B`, `BX=9200h` | 메인 블록을 `9200h` 문단으로 늘리는 요청 |

요청은 현재 `8E80h` 문단보다 `380h` 문단(14,336바이트) 크다. 뒤쪽 자유 공간은 요청량보다 많지만, 바로 다음 MCB가 할당된 폰트 블록이므로 AH=4Ah는 이를 넘어 확장할 수 없다. 따라서 이 실행에서 확인된 직접 원인은 **한글 폰트의 별도 DOS 블록이 DUNE2 메인 블록의 확장을 막은 것**이다. 사용자가 오류 화면 뒤 DOS 프롬프트로 복귀해 호출 뒤 CF/AX를 보존하지 못했으므로 반환 레지스터 자체는 관측되지 않았다. 그러나 관측된 AH=4Ah 요청·MCB 순서와 이어진 게임의 메모리 오류가 이 실패 경로와 일치한다.

MCB 파일명 `DUNE2`만으로 95CB 블록의 모듈을 판별할 수는 없다. 한글 로더의 `BX=02B2h` 요청과 크기가 정확히 일치하고 LOSE 시점에도 해당 블록이 유지된 점을 결합해 폰트 블록으로 판정했다.

새로 특정한 설계 충돌은 **한글 로더의 직접 DOS 블록 할당과 원본 Borland 힙의 PSP 블록 확장 방식이 서로 조정되지 않는 것**이다. 정적 분석과 위의 사용자 제공 MCB/레지스터 관측이 같은 충돌을 가리킨다.

### 서로 다른 두 할당 경로

| 위치 | 확인된 명령/처리 |
|---|---|
| 한글 로더 `3D02:0616–061B` | `BX=02B2h`, `AH=48h`, `INT 21h`: 별도 DOS 블록 11,040바이트 요청 |
| 한글 로더 `3D02:061F` | 반환 세그먼트를 자체 `CS:[0500]`에 저장 |
| 한글 로더 `3D02:0638` | 파일 읽기가 성공하면 파일 닫기로 이동; 폰트 블록 해제 경로는 건너뜀 |
| Borland `0000:17E0` | FAR 힙 부족 시 `0000:1AE8`로 힙 확장 요청 |
| Borland `0000:1B62` | break 변경 함수 `0000:1A33` 호출 |
| Borland `0000:1A7D` | 원래 PSP 세그먼트와 새 블록 크기를 `0000:21DE`에 전달 |
| Borland `0000:21E1–21E9` | `AH=4Ah`, `ES=원래 PSP`, `INT 21h`: 기존 PSP 블록을 연속 확장 |

한글 폰트의 11,040바이트는 원본 FAR 힙에 등록되지 않는다. 원본 FAR 할당기는 별도 폰트 블록 뒤에 있는 자유 DOS 블록을 새 힙 블록으로 직접 붙이는 `AH=48h` 경로를 이 확장 지점에서 사용하지 않는다.

DOSBox-X 참조 소스의 `DOS_ResizeMemory`는 확장 대상 다음 MCB가 **비어 있을 때만** 합친다. 다음 블록이 할당된 폰트 블록이면 같은 PSP가 소유한 블록이어도 합치지 않는다. DOS의 first-fit 전략으로 폰트가 PSP 바로 뒤의 자유 블록 앞에 놓이면, 뒤쪽에 남은 메모리가 많아도 원본 FAR 힙은 그 경계를 넘어 확장할 수 없다.

### 반환 실패가 게임 오류로 전달되는 정확한 분기

```text
DOS AH=4Ah: 요청 크기보다 연속 블록이 작음
  → CF=1, AX=8, BX=최대로 확장 가능한 PSP 크기
0000:21F2–21F7: 최대 크기 BX를 함수 반환 AX로 전달
0000:1A94–1A99: DS:[0091] = PSP + 최대 크기
0000:1AA2: AX=0 반환
0000:1B65–1B67: AX=0이면 1B11로 분기
0000:1B11–1B14: DX:AX = FFFF:FFFF
0000:17E7–17EA: 실패값 확인 후 1824로 분기
0000:1824–1826: DX:AX = 0000:0000
21E5:0087–009A: NULL 포인터 확인 → 오류 콜백

```

이후의 힙 확장 요청은 이미 낮아진 `DS:[0091]` 한도 검사(`0000:1B3C–1B4D`)에서 더 일찍 거절될 수도 있다. 이 경로는 단순히 '남은 전체 DOS 메모리 바이트 수'만으로 판단할 수 없으며 **PSP 뒤의 연속 블록과 Borland의 상한값**을 함께 보아야 한다.

### 정적 산술 예시와 실제 관측의 구분

[`dos-font-block-pinning.json`](../../../build/analysis/cheat-static/dos-font-block-pinning.json)은 임의로 명시한 MCB 배치에 실제 코드의 블록 크기 `02B2h`를 적용한 산술 증거다. CPU나 게임을 실행하지 않는다. PSP 크기 `4000h` 문단 뒤에 자유 공간 `3000h` 문단이 있을 때 폰트를 그 앞에 할당하면, 자유 공간 `2D4Dh` 문단이 뒤에 남아도 PSP를 `4100h` 문단으로 늘리는 요청은 실패한다. 폰트 할당 전에는 같은 요청이 들어간다.

이 숫자는 사용자 게임에서 읽은 값이 아니다. 이번 오류의 실제 요청 크기·PSP 크기·폰트 세그먼트로 제시하지 않는다. 정적으로 확정한 것은 이 배치에서의 확장 실패와 그 반환 경로다. 이 실패 조건은 치트 이전 한글 전용 빌드에도 존재하며, 치트의 추가 예약과 함께 검토해야 한다.

근거: [`실제 폰트 로더 명령`](../../../build/analysis/cheat-static/hangul-font-dos-allocation.txt), [`Borland 확장 경로`](../../../build/analysis/cheat-static/original-0000-160D.txt), [`DOS resize 래퍼`](../../../build/analysis/cheat-static/original-0000-21DE.txt), 참조 소스 `tools/emucap-1.1.0/dosbox-x-source/joncampbell123-dosbox-x-4f19017/src/dos/dos_memory.cpp`의 `DOS_AllocateMemory`/`DOS_ResizeMemory`와 `src/dos/dos.cpp`의 `AH=4Ah` 처리.

## 9. 네 후크와 내부 보조 함수의 정적 검증 범위

기존 3D68 치트 EXE의 네 진입점 `3D68:0000/0040/0200/0300`에서 직접 분기를 따라 **700개 도달 가능한 명령**을 추출했다. 직접 CALL/JMP의 목표가 명령 중간이나 `0816h` 이후 상태 데이터로 들어가지 않는지 확인했다. 어셈블리 소스만 보고 판단하지 않고 실제 출력 바이트를 사용했다. 새 메모리 수정판의 동적 세그먼트 배치는 12절에 기록한다.

| 대상 | SP/BP 정적 추적 결과 |
|---|---|
| 시작 후크 `0000` | 원본으로 이동하기 위한 두 PUSH와 RETF의 스택 변화 상쇄 |
| 입력 후크 `0040` 원본 연결 | 저장 BP와 4바이트 지역 변수를 남긴 상태로 `27EC:0A5A` 연결; 원본 프롤로그와 같은 SP/BP 깊이 |
| 입력 후크 `0040` 가로채기 | 지역 프레임과 저장 레지스터를 회수한 후 원래 FAR 반환 프레임 제거 |
| 입력 후속 후크 `0200` | 원래 이벤트 AX 인자 한 워드를 POP한 뒤 FAR 이동; 원본 후속 지점의 스택 깊이와 일치 |
| 결과 후크 `0300` | 추가한 FAR CALL 반환 프레임 4바이트를 제거한 뒤 원래 결과 분기로 연결 |
| 직접 호출되는 내부 보조 함수 | 각 경로에서 PUSH/POP 및 SP/BP 변경이 복귀 전 상쇄됨 |

XMS 외부 호출이 호출자의 SP를 복원한다는 API 규약은 전제로 두었다. 이 분석은 XMS 성공 판정, 인터럽트 안에서의 안전성, 게임 상태의 유효성을 보증하지 않는다. 증거는 [`hook-stack-frames.json`](../../../build/analysis/cheat-static/hook-stack-frames.json)과 [`hook-control-flow.json`](../../../build/analysis/cheat-static/hook-control-flow.json)에 있다.

별도로 원래 MZ 재배치 항목 하나를 `0000:005E → 0000:0060`으로 옮기고 세 항목을 더한 결과가 실제 EXE 표와 정확히 같은지 확인했다. 중복 재배치가 없으며 한글 전용 빌드 대비 뒤로 옮긴 FBOV 이후 바이트는 동일하다. 따라서 현재 증거에서 단순 FAR 복귀 프레임 불균형이나 MZ 재배치표 누락을 메모리 오류 원인으로 제시하지 않는다.

입력 후속 후크는 원본 연결 때 BX를 게임 코드 세그먼트로 바꾸고 복원하지 않는 차이도 있다. 최종 IRQ 복귀에서는 원본 저장 BX가 복원되지만, `27EC:0F18`의 선택적 FAR 콜백은 그 이전에 호출된다. 해당 콜백이 BX를 사용하지 않는다는 증명 없이 원본과 완전히 같은 레지스터 전달이라고 보아서는 안 된다. 이 차이를 현재 메모리 오류의 직접 원인으로 확인한 것은 아니다.

## 10. 이 단계에서 확정한 것과 남은 것

파일 기반 정적 대조는 추가 상주 코드 배치, 초기 힙 이동, 원본 할당 실패 경로, 폰트 DOS 블록과 힙 확장의 충돌, 네 후크의 직접 제어 흐름·스택 깊이, MZ 재배치와 오버레이 보존까지 완료했다. 사용자 제공 실행 관측으로 메인 블록 크기, 폰트 크기와 인접 순서, AH=4Ah 요청 크기도 확보했다.

호출 뒤 CF/AX와 게임 오류 래퍼가 받은 FAR 할당 크기는 저장되지 않았다. 그러나 실제 MCB 배치에서 `074B`가 바로 다음 할당 MCB를 넘어 `9200h` 문단으로 확장할 수 없고, 바로 그 뒤 게임 메모리 오류가 나타났다. 따라서 이 재현의 MCB 충돌 원인은 특정됐다. 이전의 “실제 MCB 배치가 미확정”이라는 문구는 위 2026-10-21 관측으로 대체한다.

## 11. 후속: 원본 폰트 할당과 해제 규약

[폰트 메모리 수명 역분석](../fonts/font_memory_lifecycle.md)에서 원본 `2371:000E`가 `21E5:000E`로 FNT를 할당하는 경로와 `21E5:01CC`의 관리 바이트 복원을 추적했다. 원본 할당기로 옮길 경우 단순히 DOS 할당 호출만 바꿔서는 안 된다. 현재 한글 렌더러의 세그먼트:0000 접근을 유지하려면 `20h` 정렬 플래그가 필요하며, `10h`만 사용하면 반환 오프셋까지 모든 참조에 반영해야 한다. 해제도 원본 함수와 짝을 맞춰야 한다.

이 후속 분석은 9개 명령열 바이트 대조, 조사 대상 직접 호출 125건의 명령 경계, 정규화 오프셋 16가지의 정렬/해제 산술을 확인했다. 이 문단이 작성될 당시에는 EXE/후크 수정과 게임 실행을 하지 않았으며 실제 MCB 배치도 미확정이었다. 이후 확인한 관측과 별도 수정판은 12절에 기록한다.


## 12. 사용자 MCB 관측에 따른 원인 확정과 수정판

2026-10-21 사용자가 제공한 MCB 목록에는 DUNE2 메인 블록 바로 뒤에 11,040바이트의 DUNE2 소유 블록이 있고, 그 뒤에 30,720바이트의 자유 블록이 있었다. 이어 제공된 중단점 레지스터는 AX=4A4Bh, ES=074Bh, BX=9200h였다. 현재 메인 블록은 8E80h 문단이고 14,336바이트 확장이 필요했다. 바로 다음 MCB의 02B2h 문단 크기는 한글 로더가 DOS AH=48h로 할당한 크기와 같다. 따라서 별도 폰트 블록이 확장 경로를 끊은 것이 이 실행의 메모리 오류 원인이다. DOS 프롬프트로 빠진 뒤라 호출 후 CF/AX는 보존되지 않았다.

이를 고치기 위해 별도 메모리 수정 빌드를 만들었다. 기존 성공 빌드 build/hangul-runtime-16x16과 기존 치트 빌드는 덮어쓰지 않았다.

- tools/hangul-render-hook-16x16.asm의 폰트 로더는 DOS AH=48h 대신 게임 FAR 할당기 21E5:000E에 11,034바이트와 정렬 플래그 20h를 전달한다.
- 짧은 읽기에서만 같은 FAR 포인터를 게임 해제 함수 21E5:01CC로 돌려준다.
- 생성된 실제 로더 명령 3D02:0540–05DA를 정적으로 역분해해 포인터 계산, DS 선택, 인자 순서, 할당·해제 호출을 확인했다. 해당 범위에는 DOS AH=48h/AH=49h가 없다.
- 코드 로더를 여유 공간 0540h로 옮겨 기본 MZ 이미지 끝은 0x42200이 됐다. 새 치트 모듈은 세그먼트 3D60h, 스택은 3DF9h에 배치됐고, 시작 힙 이동량은 4,080바이트다.
- 수정판 EXE SHA-256: cfb774bfa9bbe937ac5b2ae7820890b4cecc235eedc79260019ea0a1474a99c8.
- 실행 파일: build/cheat-hangul16-runtime-memoryfix/source/VIRGIN/DUNE2/DUNE2.EXE.
- 사용자가 실행할 배치: build/cheat-hangul16-runtime-memoryfix/run_cheat_hangul16_test.bat.

DOSBox-X 실행이나 LOSE 입력은 하지 않았다. 따라서 수정판에서 폰트 MCB가 사라지고 LOSE가 정상 처리되는지는 사용자의 실행 확인 전까지 미검증이다.

## 13. 2차 수정: 폰트 비트맵을 XMS로 이동

12절의 FAR 힙 수정은 별도 MCB를 없애도 11,034바이트를 게임 conventional-memory 힙에서 계속 사용한다. 메모리 배치 전체를 개선하지 못한 불완전한 수정이었다. 이에 `hangul-render-hook-16x16.asm`의 폰트 로더와 렌더 경로를 XMS 저장 방식으로 다시 바꾸고, 2026-10-21에 기존 memoryfix 실행 파일을 새 결과물로 재생성했다. 사용자가 앞서 제공한 `095CB`의 11,040바이트 MCB 관측은 DOS `AH=48h`를 쓰던 이전 빌드의 증거이며 최신 XMS판의 MCB 배치로 간주하지 않는다.

정적 대조 결과:

- FNT 헤더와 1,530바이트 선택표(합계 1,554바이트)를 상주 이미지에 둔다. 316개 15×15 구성 비트맵 9,480바이트는 10 KiB XMS 핸들에 둔다.

- 상주 후크 이미지 `0xF20`바이트, 내장 선택표 `0800h–0E11h`, scratch `0E20h–0F1Fh`다. OMF 코드 영역과 데이터 예약 영역이 겹치지 않는지 빌더가 확인하며, 내장 선택표는 원본 폰트 선두 1,554바이트와 바이트 단위로 일치한다.
- 최신 치트 EXE의 MZ 이미지 끝은 `0x434D0`, 치트 모듈 세그먼트는 `3DF4h`, 시작 스택 세그먼트는 `3E8Dh`다. 기존 FAR 힙판에 비해 폰트 런타임 할당 11,034바이트를 제거하고 상주 이미지가 2,368바이트 커졌으므로 정적 산술상 conventional-memory 절감은 약 8,666바이트다. 실제 MCB/힙 배치 측정값은 아니다.

## 14. 재발 보고와 XMS ABI 결함 수정

당시 사용자는 XMS판에서도 게임 진행 중, 치트를 사용하지 않아도 메모리 오류가 발생한다고 보고했다. 이후 15절의 실제 덤프 분석으로 해당 실행은 구형 DOS 폰트 로더였음을 확인했다. 따라서 이 보고를 XMS판의 재현 결과로 취급하지 않는다. 13절의 배치 계산 자체도 실제 오류 해결의 증거는 아니다.

새로 확인한 확정 결함은 폰트 XMS 이동 구조체의 잘못된 필드 위치다. 저장된 DOSBox-X `src/ints/xms.cpp`의 packed `XMS_MemMove`는 다음과 같다.

| 바이트 오프셋 | 형식 | 필드 |
|---:|---|---|
| 0 | DWORD | 이동 길이 |
| 4 | WORD | 원본 핸들 |
| 6 | DWORD | 원본 오프셋 |
| 10 | WORD | 대상 핸들 |
| 12 | DWORD | 대상 오프셋 |

기존 폰트 코드는 길이 뒤 필드를 2바이트 일찍 기록했다. 실제 출력 기계어에 예시 핸들 `1234h`를 적용하면 업로드의 원본 핸들이 버퍼 오프셋 `0E20h`로 해석되고, 다운로드 길이는 `1234001Eh`로 해석된다. 이는 규격에 맞지 않는 이동 요청이다. 이 결함만으로 게임의 conventional-memory 오류 발생 원인을 확정할 수는 없다.

수정판은 전체 필드를 16바이트 규격에 맞춰 기록한다. [audit_xms_font_abi.py](../../../archives/tools/README.md)가 조립된 실제 기계어의 descriptor 작성 명령을 해석하여 이전 오류를 재현했고, 수정 후 38개 적재 청크 및 316개 구성 글리프의 주소·길이와 9,480바이트 페이로드를 확인했다. [증거 JSON](../../../build/analysis/xms-font-abi/evidence.json)의 `game_memory_error_root_cause_proven`은 `false`다. 게임이나 XMS 관리자는 실행하지 않았다.

- 최신 EXE SHA-256: `67a26ffb3f586db63d205735047401446bec7f0d231588d715e655c866d7a1be`.
- 실행 배치와 EXE 경로는 기존 memoryfix 디렉터리를 사용한다.
- 새 배치는 호스트 작업 디렉터리를 배치 폴더로 고정한다. 창 제목의 `Memory trace 67a26ffb3f58`로 새 빌드를 구별한다.

### 사용자 실행에서 오류 시점 수집

오류 메시지가 키 입력을 기다리는 상태에서 디버거를 열고 다음을 입력한다. DOS 프롬프트로 빠진 뒤에는 수집하지 않는다.

```text
DOS MCBS
MEMDUMPBIN DS:0000 10000
```

두 명령과 레지스터 이름·길이 파싱은 저장된 DOSBox-X 디버거 소스에서 확인했다. 두 번째 명령은 게임 DS부터 64 KiB를 저장한다. 16비트 세그먼트 오프셋이 64 KiB에서 순환할 수 있으므로 `0000:0000 100000`으로 전체 1 MiB를 덤프하는 명령은 사용하지 않는다. 현재 빌드에서는 이 DS 창에 힙 경계 변수, 폰트 후크, 치트 후크, 게임 스택이 모두 들어간다. 디버거의 DS가 게임 DS인지 여부는 코드 서명으로 검사한다.

새 배치로 시작한 세션의 덤프 경로는 `build/cheat-hangul16-runtime-memoryfix/MEMDUMP.BIN`이다. 현재 CPU 레지스터와 `DOS MCBS` 출력도 보존한다. [analyze_dune2_memory_dump.py](../../../archives/tools/README.md)는 덤프에서 실제 코드 버전, 폰트 적재 상태, 힙 하한·현재 break·상한, 할당 실패 콜백의 스택 프레임 후보를 추출하도록 준비했다. DS 정렬 확인과 프레임 해석은 합성 자료로만 점검했으며 실제 최신 덤프는 아직 없다. 덤프만으로는 현재 SS:SP를 알 수 없어 오래된 스택 흔적을 현재 프레임이라고 단정하지 않는다.

## 16. 사용자 확인: LOSE 사용 후 정상 진행 (2026-10-21)

실행 경로를 정리하고 최신 수정판 실행을 안내한 뒤 사용자가 **“lose를 사용해도 문제없이 진행된다”**고 보고했다. 이는 사용자가 직접 수행한 실행 확인이다. 작업 에이전트가 게임을 실행하거나 치트를 입력한 결과가 아니다.

| 기록 항목 | 내용 |
|---|---|
| 안내한 실행 배치 | 루트 `듄2_치트테스트.bat` → `build/cheat-hangul16-runtime-memoryfix/run_cheat_hangul16_test.bat` |
| 대상 EXE | `build/cheat-hangul16-runtime-memoryfix/source/VIRGIN/DUNE2/DUNE2.EXE` |
| 대상 EXE SHA-256 | `67a26ffb3f586db63d205735047401446bec7f0d231588d715e655c866d7a1be` |
| 창 제목 식별자 | `Memory trace 67a26ffb3f58` |
| 메모리 방식 | 선택표는 상주 후크, 구성 글리프 비트맵 9,480바이트는 10 KiB XMS, 상주 전송 버퍼 256바이트 |
| 사용자 확인 범위 | `LOSE`를 사용한 뒤에도 이전 메모리 오류 없이 진행된다는 보고 |
| 확인의 한계 | 성공 세션의 실행 코드 덤프·MCB 목록·해시를 별도로 수집하지 않았다. 위 해시는 안내한 디스크 EXE이며 문서 기록 시 다시 확인했다. |

관측과 원인 판단을 다음처럼 구분한다.

1. **구형 실행의 배치 문제는 실제 덤프로 확인했다.** 폰트 포인터 `95CC:0000`, 폰트 MCB `95CB`, 힙 상한 `95CB`가 일치한다. 별도 폰트 블록이 메인 블록 뒤를 막고 있었다. 근거는 15절과 [사용자 덤프 분석 JSON](../../../build/analysis/xms-font-abi/user-memory-dump-analysis.json)이다.
2. **XMS 이동 구조체 결함은 별도의 정적 분석으로 수정했다.** 길이 DWORD와 필드 위치 `0/4/6/10/12`를 적용했다. 근거는 14절과 [ABI 검사 JSON](../../../build/analysis/xms-font-abi/evidence.json)이다. 이 결함을 구형 실행의 conventional-memory 오류 원인으로 단정하지 않는다.
3. **최신판 안내 후 LOSE 정상 진행은 사용자 확인으로 기록한다.** 이전 재발 보고를 최신 XMS판 실패로 보았던 판단은 실제 덤프에 따라 정정한다.

이번 확인으로 모든 메모리 문제가 해결됐다고 판정하지 않는다. `WIN`, `CREDITS`, 장시간 진행, 모든 임무·가문, 실제 DOS 환경, 최신판의 실제 MCB 배치와 메모리 절감량은 이번 사용자 보고로 검증되지 않았다. 과거 빌드 보고서의 `runtime_verified: false`와 정적 ABI 증거의 `game_memory_error_root_cause_proven: false`는 각 생성 시점과 검사 범위의 기록으로 유지하며, 이번 사용자 확인과 구분한다.

## 18. 치트창 크기·화면 페이지 수정 (2026-10-21)

사용자가 제공한 게임 화면 캡처에서 치트 문구와 배경 패널이 화면 양쪽에 갈라져 보이고, 창 폭이 왼쪽 아래 미니맵 영역까지 침범했다. 실행하지 않고 치트 후크와 원본 FNT 페이지 선택 경로를 정적으로 대조했다.

### 원인

기존 `DrawVideoPanel`은 VGA 320×200의 `x=16`, `y=160`부터 `288×32`를 `A000:C810`에 직접 썼다. 반면 원본 글리프 렌더러는 `20AA:0E02`를 통해 화면 페이지 표를 조회한 뒤 그 페이지 세그먼트에 기록한다. 따라서 치트창은 현재 게임이 그리는 페이지와 다른 버퍼에 나타날 수 있었다. 각 행은 288바이트를 쓴 뒤 32바이트를 건너뛰지만, 배경 저장은 `A000:C810`부터 연속 `0x2400`바이트만 복사했다. 이 백업은 행 간격을 반영하지 않아 그려진 사각형과 맞지 않았고, 복원 시 패널 밖 픽셀도 포함할 수 있었다.

활성 페이지를 따르지 않는 직접 쓰기와 화면 갱신 중 패널이 사라지는 현상은 코드 구조상 일치한다. 정적 자료만으로 캡처의 각 조각이 어떤 프레임·페이지에서 그려졌는지는 구분할 수 없으므로, 페이지 불일치를 캡처의 유일한 원인이라고 단정하지 않는다.

### 수정 내용

- 패널을 `x=16..143`, `y=160..191`의 `128×32`로 축소해 왼쪽 아래에 배치했다.
- 글리프 텍스트를 패널 안에 배치하고 안내를 `ENTER=RUN ESC=EXIT`로 줄였다. 입력 명령 최대 16자는 기존대로 유지한다.

## 19. 정상 표시 후 게임 진행 중 치트창이 사라지는 원인 (2026-10-21)

## 20. 치트창을 프레임 갱신 후 표시하도록 수정 (2026-10-21)

사용자의 수정 지시에 따라 `044B:0309`에 프레임 시작 후크, `044B:03EF`에 전장·메시지 갱신 후 패널 그리기 후크를 적용했다. 키보드 ISR은 입력 상태만 변경한다. 패널은 표시 페이지 0에만 그리며 전장 작업 페이지 2에는 쓰지 않는다. 다음 프레임 시작에 페이지 2의 최신 전장으로 패널 구역을 복원하므로 별도 화면 백업이 필요하지 않다.

치트 화면용 4 KiB XMS 할당을 제거했고, 상주 모듈 크기 `0x0990`바이트와 기존 스택 이동은 늘리지 않았다. 한글 비트맵용 10 KiB XMS는 유지한다. 아래/오른쪽 테두리도 빨강 `08h`에서 원본 UI 그림자 `EBh`로 바꿨다.

수정 EXE SHA-256은 `0a01ceb6b5c70939b7584860e8a99e36dbf5d3ec104331a3c0ba0d657078ea9b`다. 실행 배치는 기존 `듄2_치트테스트.bat`이다. MASM 빌드와 실제 EXE의 분기·스택·재배치·원래 비교 플래그·기존 한글 코드 보존에 대한 정적 확인을 통과했다. 기존 저장 파일도 빌드 전후 해시가 동일하다.

수정 전 분석 자료는 `build/analysis/cheat-panel-static/before-fix/`에 보관했고, 수정 후 근거는 `build/analysis/cheat-panel-frame-fix/audit.json`에 있다. 자세한 구현 기록은 [치트창 소실 정적 역분석](cheat_panel_redraw.md)의 7절을 따른다. 게임은 실행하지 않았으며 실제 화면 확인은 사용자에게 맡긴다.

## 최신 적용: 게임 중에만 치트 Enter 허용 (2026-10-21)

## 21. 달무리 8×8 치트판에서 폰트 MCB 제거 (2026-10-21)

달무리 8×8 폰트와 치트 모듈을 결합한 실행에서 메모리 오류가 다시 보고됐다. 기존 치트 통합 보고서에는 글리프 표를 DOS `INT 21h/AH=48h`로 224바이트 할당한다고 기록되어 있었고, 이 방식은 폰트용 별도 MCB를 만든다. 새 Dalmuri 후크는 파일을 열거나 DOS 블록을 할당하지 않고, 214바이트 희소 표를 DUNE2의 추가 MZ 상주 구간 안에서 직접 읽도록 바꿨다.

### 정적 확인

### 해석과 한계

이 수정은 폰트용 별도 MCB가 DUNE2 메모리 블록 사이를 끊는 배치 문제를 제거한다. 폰트 표와 치트 모듈은 MZ 이미지에 포함되므로 MZ 상주 이미지가 미패치 원본보다 4,016바이트 커진다. 따라서 conventional memory 총 사용량 자체가 줄어드는 수정은 아니다. 다만 폰트 표 때문에 DOS 메모리 블록 사슬에 새 블록이 삽입되지는 않는다. 치트 화면 백업은 계속 XMS 4KiB를 사용한다.

MASM 빌드와 MZ/오버레이/재배치 및 내장 표 일치 검사는 통과했다. 이후 사용자는 SHA-256 `cff1fbca859634321b798acbd26ac7f16752fe020d61ba542a888badc108a32c`인 이 통합 빌드가 문제없이 작동하고 치트와 폰트가 제대로 적용됐다고 확인했다. 사용자가 실행 중 `DOS MCBS`로 제공한 덤프에는 DUNE2 메인 MCB `074A`가 579,584바이트, 바로 다음 자유 MCB `94CB`가 45,872바이트로 표시됐다. 앞서 이전 덤프에 근거해 계산한 여유 메모리 추산은 이 새 실측값으로 대체한다. 이 수치는 DOSBox-X 덤프이며 실제 DOS 환경의 자유 메모리는 별도 확인하지 않았다. 새 실행 배치는 `build/cheat-dalmuri-8x8-runtime/run_cheat_dalmuri_8x8_test.bat`이다.

## 22. 원본 FNT 구간별 달무리/조합 글꼴 통합과 MZ 배치 (2026-10-21)

앞 절의 214바이트 희소 음절 표 방식은 현재 후보에 사용하지 않는다. 새 후크는 `20AA:[008A/008C]`의 활성 원본 FNT 포인터를 읽는다. 실제 추출된 `NEW6P.FNT`는 3,276바이트이며 헤더 길이 `0x0CCC`, 최대 높이/너비 8/8이다. `NEW8P.FNT`는 5,702바이트이며 길이 `0x1646`, 최대 높이/너비 11/10이다. 이 두 구간에서만 달무리 8×8을 고른다. `INTRO.FNT`는 7,204바이트이고 헤더 길이 `0x1C24`, 최대 높이/너비 19/17로 판별에서 제외되므로 기존 유니폰트 조합 FNT가 사용된다. 다른 원본 FNT도 NEW6P/NEW8P의 정확한 서명과 일치하지 않으면 조합 글꼴 경로를 따른다.

달무리 글꼴 데이터는 희소 표가 아니다. `DUNEHAN.DLM`의 24바이트 헤더 다음에 U+AC00부터 U+D7A3까지 11,172개의 8바이트 비트맵을 순서대로 저장한다. 런타임은 토큰으로부터 구한 음절 번호에 8을 곱해 비트맵 위치를 계산한다. 기존 초·중·종성 선택표와 15×15 구성 비트맵은 별도 `DUNEHAN.FNT`에 유지된다.

### MZ 및 XMS 배치

정적 빌드에서 미패치 원본 MZ 이미지 끝은 `0x41C20`, 폰트 후크 뒤는 `0x43040`, 치트 모듈을 더한 최종 끝은 `0x439D0`이다. 폰트 후크가 5,152바이트, 치트 모듈이 2,448바이트를 더해 원본 대비 총 7,600바이트 증가한다. 폰트 후크의 새 세그먼트는 `3D02h`에서 시작해 `3E44h`까지 차지하고, 치트 모듈은 `3E44h`부터 `3EDDh`까지 연속한다. 시작 스택 기준 `3EDDh`는 모듈 바로 다음이다. MZ 재배치는 4,485에서 4,488로 늘었고 Borland 오버레이는 바이트 단위로 보존됐다.

한글 폰트는 DOS `AH=48h` 메모리 블록이나 게임 FAR 힙을 할당하지 않는다. 비트맵과 치트 화면 백업의 XMS 요청 크기는 달무리 88KiB, 조합 글리프 10KiB, 치트 화면 백업 4KiB로 합계 102KiB다. 조합 선택자 1,554바이트와 256바이트 전송 scratch는 MZ 상주 이미지에 둔다. 따라서 별도 폰트 MCB를 끼워 넣는 배치는 제거했지만, MZ 로드 이미지 자체는 원본보다 7,600바이트 커진다.

이 절의 구간별 통합 후보 SHA-256은 `a6ee65ff88d2c225157d456abb1a3387114ba5f1196d20cf868df155cc11e146`이다. 사용자가 거부한 후보와 동일하므로 현행 실행본으로 채택하지 않았다. 후보의 정적 빌드 검사는 통과했지만 런타임 출력과 MCB 수치는 미확인이다.
