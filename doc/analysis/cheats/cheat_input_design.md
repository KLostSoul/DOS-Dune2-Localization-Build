`build/translation-editor-20261025-102009-308571`에서 10,000 증가를 사용자가 실제 게임으로 확인했다. 현재 입력 오류 처리까지 포함한 생성본은 `build/translation-editor-20261025-103646-558960`, EXE SHA-256 `a9ecc589c0acf177fc409dcdf4716287ca5ab98f924c30ccef1476f65b7a9ab1`이다. 최신 EXE의 `4498Fh` 위치는 `05 10 27`이며, 조립된 `UnknownCommand` 경로는 오류 상태를 설정한 뒤 입력 길이를 0으로 만든다. 사용자는 이 생성본에서 잘못된 명령을 제출했을 때 입력줄이 비워지는 동작도 정상 적용됐다고 확인했다.

상태 (2026-10-21): 사용자는 EXE SHA-256 `67a26ffb3f586db63d205735047401446bec7f0d231588d715e655c866d7a1be`에서 `LOSE` 후 정상 진행을 확인했다. 그 뒤 빈 Enter로 입력창을 닫는 기능을 추가한 현재 EXE의 SHA-256은 `5f554af219935530ca5e71c2d495904f3918824a48d37c1cf7bc0d955aa8a90d`이다. 현재 EXE는 아직 사용자가 실행 확인하지 않았다. 성공 세션의 실행 코드 덤프는 수집하지 않았으며, `WIN`·`CREDITS`·장시간 진행·실제 DOS도 확인되지 않았다.

이전 메모리 오류 당시 실제 덤프는 구형 DOS 폰트 로더와 일치했고, 별도 폰트 MCB가 메인 메모리 블록 뒤를 막는 배치를 확인했다. 이를 최신 XMS판의 실패로 취급했던 판단은 정정한다. 근거와 사용자 확인 범위는 [치트 메모리 오류 정적 대조](cheat_memory_layout.md)의 15–16절을 기준으로 한다. 아래 이전 실행 기록은 해당 시점·해시의 관측 범위만 설명한다.

게임 중 **Enter로 입력창을 열고, 명령을 입력한 뒤 Enter로 실행**하는 기능을 원본 DOS 게임 엔진에 추가한다. 게임에서 Enter 키를 사용하지 않는 점을 활용한다. 영문 대소문자는 구분하지 않는다. 한글화 검증에 필요한 승리·패배 경로를 쉽게 재현할 수 있도록 현재 임무의 결과를 발생시키는 명령을 포함한다.

## 1. 사용할 명령과 동작

| 입력 | 동작 | 처리 원칙 |
|---|---|---|
| `CREDITS` | 현재 플레이어의 사용 가능한 자금에 10,000 추가 | 16비트 덧셈 오버플로 시 `FFFFh`로 포화한다. 적 가문의 자금은 변경하지 않는다. HUD 반영 필드도 갱신한다. |
| `WIN` | 현재 임무를 승리로 끝낸다 | 원래 승리 결과 처리로 연결해 임무 후 설명·점수·다음 임무/캠페인 종료 전환을 수행한다. |
| `LOSE` | 현재 임무를 패배로 끝낸다 | 원래 패배 결과 처리로 연결해 패배 설명·재시도 등의 전환을 수행한다. |

위 세 명령을 첫 구현 범위로 정한다. 지도 공개·무적·즉시 생산은 해당 자료 구조와 갱신 경로를 확인한 뒤 같은 명령 표에 추가할 수 있다.

`WIN`은 현재 임무의 종료를 요청한다. 첫 임무에서 바로 캠페인 엔딩으로 보내는 명령은 아니다. 마지막 임무의 가문별 엔딩 검증에는 그 임무의 실행 상태가 필요하다. 치트로 발생시킨 종료는 검증 기록에 강제 종료 조건으로 명시한다.

현재 코드는 16비트 자금 필드의 덧셈 오버플로를 `FFFFh`로 포화한다. 이 값이 게임의 모든 임무에서 허용되는 실제 자금 상한인지, 향신료 목표 임무에서 자금 증가가 정상 승리 조건에 영향을 주는지는 별도 게임 실행 확인 사항이다.

## 2. 입력창 사용 방식

1. 실제 게임 진행 화면에서 Enter를 눌러 입력창을 연다.
2. 게임의 기존 일시 정지 처리를 이용해 월드 갱신을 멈추고 작은 입력창을 표시한다. 기존 일시 정지 상태는 보관했다가 정확히 복원한다.
3. ASCII 영문 명령을 최대 16자 입력한다. Backspace로 지우고, Enter로 실행하거나 Esc로 취소한다. 입력창이 닫힌 상태의 Enter는 창을 열고, 열린 상태의 Enter는 명령을 실행한다. 앞뒤 공백은 제거하고 대문자로 정규화한다. 다른 문자는 버퍼에 넣지 않는다.
4. 알 수 없는 명령은 입력창에 `UNKNOWN COMMAND`를 표시하고 계속 입력받는다. 입력 없이 Enter를 누르면 명령을 실행하지 않고 입력창을 닫는다.
5. 명령이 유효하면 실행 요청을 하나 등록하고 입력창을 닫는다. 창 복원과 입력 종료가 끝난 뒤 게임 메인 루프의 안전한 지점에서 효과를 한 번 실행한다.

저장 이름 입력, 불러오기 창, Options, Mentat, 브리핑, 오프닝, 승패 처리 중에는 치트 입력창을 열지 않는다. 이 문맥 판정은 게임 화면 상태와 모달 상태를 함께 확인한다. 게임 화면처럼 보이는지만으로 활성화하지 않는다.

평상시 키를 관찰하는 위치는 **원래 키 상태 갱신 뒤, 게임 단축키/유닛 명령 해석 전**이다. 입력창이 열려 있으면 입력 이벤트를 치트 입력기가 소비해 명령의 `C`, `R`, `S` 등이 게임 단축키로 동작하지 않게 한다. 원래 키 눌림/해제 상태 처리는 계속 유지한다.

키를 오래 눌렀을 때 단축키가 반복해서 열리지 않도록 열기 조합은 새로 누른 순간만 인정한다. 열기 조합이 해제되기 전까지 활성화에 사용한 `C`는 입력 문자열에 넣지 않는다. 닫을 때는 Enter/Esc 및 열기 조합의 남은 키 이벤트를 처리해 게임 동작으로 새지 않도록 한다. 입력기와 게임이 같은 이벤트 큐를 각각 꺼내 읽는 구조는 사용하지 않는다.

## 3. 내부 구성과 실행 흐름

아래 이름은 추가할 모듈의 설계 이름이며, 원본 게임에서 이미 확인한 함수명이 아니다.

```text
원래 입력 이벤트 취득 / 키 상태 갱신
    ↓
CheatInputFilter
    ├─ 대기 중: 열기 조합 검사 → 나머지 이벤트는 원래 게임으로 전달
    └─ 입력 중: 문자·Backspace·Enter·Esc 처리 → 게임 동작으로 전달하지 않음
    ↓
원래 모달 처리 종료 / 메인 루프의 안전한 지점
    ↓
CheatApplyPending
    ├─ CREDITS → 현재 플레이어 자금 처리 + HUD 갱신
    ├─ WIN     → 원래 임무 승리 종료 처리
    └─ LOSE    → 원래 임무 패배 종료 처리
```

상태 전이는 `IDLE → OPENING → CAPTURE → CLOSING → IDLE`로 둔다. 유효 명령일 때만 `CLOSING`에서 실행 요청이 생긴다. 메인 루프가 요청을 가져갈 때 먼저 슬롯을 비우고 실행해 재진입이나 반복 발동을 막는다.

```text
if pending != NONE and normal_game_context and not transition_in_progress:
    command = pending
    pending = NONE
    execute(command)
```

인터럽트 핸들러 안이나 FNT 렌더러 안에서는 자금·승패 상태를 변경하지 않는다. `WIN/LOSE`가 성공적으로 결과 전환을 요청하면 그 게임 틱의 나머지 월드 처리는 원래 종료 경로의 규칙에 맞춰 마친다. 파괴된 게임 객체를 이후 코드가 다시 사용하는 상태가 생기지 않도록 한다.

새 임무 시작, 저장 불러오기, 타이틀 복귀 시 입력 버퍼·보류 명령·입력창 소유 상태를 초기화한다. 입력창 상태는 저장 파일 형식에 추가하지 않는다. 자금처럼 실제 게임 상태에 적용된 효과는 이후 정상 저장 시 기존 저장 방식에 따른다.

## 4. 화면과 폰트

첫 입력창은 원본 영문 FNT로 `CHEAT:`, 명령 문자열, 결과/오류 문구를 표시한다. 치트 입력 자체에는 한글 조합 토큰이 필요하지 않다. 후속 한글 안내 문구를 넣을 때는 현재 16×16 한글 출력 경로와 레이아웃을 적용한다.

초기 구현의 `x=16..303`, `y=160..191` 288×32 패널은 화면 대부분을 덮었다. 이 배치는 폐기했다. 현재 시험 빌드는 VGA 320×200에서 `x=16..143`, `y=160..191`의 128×32 패널을 사용한다. 5×7 영문 글꼴은 `(24,162)`, `(24,171)`, `(24,180)`에 표시하며, 안내 문자열은 `ENTER=RUN ESC=EXIT`다. 이 크기는 최대 16자 명령 입력도 패널 안에 수용한다.

현재 후크는 VGA 모드 13h에서만 열린다. 사용자는 이전 빌드에서 창이 처음 정상 표시된 뒤 게임 진행 중 사라진다고 확인했다. 정적 역분석으로 `05DD:153F → 22D5:0007 → 20AA:078D`의 전장 변경 구역 복사가 패널 영역을 덮는 경로를 특정했다. 원본은 2번 작업 페이지와 0번 표시 페이지를 별도로 사용하므로, 키 입력 시 현재 작업 페이지에 그리는 방식은 폐기했다.

2026-10-21 수정 빌드는 키보드 ISR에서 입력 상태만 변경한다. `044B:0309`의 프레임 시작 후크는 표시 페이지 0을 선택하고, 이전에 패널을 그렸다면 현재 전장 작업 페이지 2의 동일한 128×32 영역을 표시 페이지로 복사해 지운다. `044B:03EF`의 후크는 전장·메시지 갱신 후 입력창이 열려 있을 때 표시 페이지 0에 패널을 다시 그린다. 게임 종료 상태에서는 입력 상태를 닫고, 반환 직전에 원본 `CMP [38EC],0`을 실행해 다음 분기에 필요한 플래그를 재현한다.

배경은 별도로 저장하지 않는다. 페이지 2가 깨끗한 전장 배경을 보유하며, 패널은 그 페이지에 기록하지 않는다. 치트창용 4 KiB XMS 할당과 오래된 스냅샷 복원을 제거했다. 빈 Enter·Esc로 닫을 때도 다음 프레임 시작에서 최신 전장으로 복원한다. 화면 쓰기에는 원본 마우스 영역 숨김 `2971:0191`과 표시 `2971:028C`를 짝지어 사용한다. 아래/오른쪽 테두리는 UI 그림자 색 `EBh`다.

수정 EXE SHA-256은 `0a01ceb6b5c70939b7584860e8a99e36dbf5d3ec104331a3c0ba0d657078ea9b`다. 실제 EXE의 후크·스택·재배치·입력 ISR 분리와 기존 한글 코드 보존을 정적으로 확인했으며, 게임 실행 검증은 사용자 확인 전이다. 상세 내용은 [치트창 소실 정적 역분석](cheat_panel_redraw.md)의 7절에 기록했다.

| 공통 포맷 출력 `0EED:1E65` | 기존 정적·런타임 역분석 | 안내문 표시 후보. 호출 규약과 원래 폰트 상태를 보존한다. |
| 문자 루프 `29C7:0004` | 기존 런타임 실측 | 최종 문자열 출력 확인 지점. 키 입력을 여기에 연결하지 않는다. |
| 메시지 큐 `0EED:09AB` | null 갱신 및 실제 완료 문구 입력 실측 | 효과 적용 후 간단한 상태 알림 후보. 메인 루프의 정상 문맥에서 호출한다. |
| 성공 안내 대화상자 호출 `1223:0349` | `DUNE.ENG[82]`를 `0EED:0273`에 넘기는 정적 호출 | 승리 종료 경로를 거슬러 추적할 근거. 이 주소를 승리 처리 함수 진입점으로 간주하지 않는다. |
| 실패 안내 대화상자 호출 `1223:04A7` | `DUNE.ENG[83]`를 같은 대화상자에 넘기는 정적 호출 | 패배 종료 경로를 거슬러 추적할 근거. 이 대화상자만 호출하면 패배 처리 검증이 되지 않는다. |
| `2CA0:24BB`의 `Victory Controls for Player` 등 | 원본 EXE 내장 문자열을 출력하는 정적 함수 | 내부 개발용 제어 코드 가능성을 조사할 단서. 현재 실행 가능하거나 치트 입력이 이미 존재한다는 증거는 아니다. |
| 키 이벤트 취득/게임 명령 분기 함수 | 이 작업 공간의 기존 문서에서 정확한 후크 주소 미확정 | 한 번만 이벤트를 취득하는 경로와 눌림·해제·반복 처리를 먼저 확인한다. |
| 현재 플레이어/자금 필드 | 정확한 구조체·오프셋 미확정 | 자금 지불·획득·저장·HUD 참조를 대조해 필드 크기와 한도를 확정한다. |
| 게임 문맥·일시 정지·임무 종료 상태 | 정확한 상태값/소유권 미확정 | 메뉴 일시 정지 및 승패 판정의 정상 제어 흐름을 따라 확정한다. |

추가 분석은 키 이벤트와 효과 대상만 진행한다. 이미 확인한 FNT 출력 경로의 분석을 반복하지 않는다. 후크 주소·자금 오프셋·승패 플래그 값이 확인되기 전에는 임의의 주소나 값으로 시험 EXE를 만들지 않는다.

## 6. EXE 패치와 한글 후크 공존

원본 EXE의 분석 대상 해시는 `99f44e83b309dd826f3dbc5068c61679bb68047eed8d738dcef594ba0eef7552`다. 현재 16×16 한글 시험본의 빌드 기록에는 별도 해시 `d3196c592f30a8d6bb968e1ae2015b184d5424946a78f093db3498b2365f7e95`가 있다. 구현 시 실제 입력 파일의 해시를 다시 계산해 해당 빌드 기록과 대조한다.

기존 한글 빌더는 MZ 로드 모듈과 FBOV 오버레이 사이에 상주 후크를 삽입한다. 폰트 후크는 원본 상대 세그먼트 `3D02`, 변수 `0500`, 파일명 `0530` 등을 이미 사용한다. 치트 코드/변수를 여기에 임의로 겹쳐 넣지 않는다.

파일 헤더를 이번에 읽어 확인한 값은 다음과 같다. 주소는 로드 모듈 시작 기준이며 DOSBox 실행 중의 절대 주소가 아니다.

| 값 | 원본 | 현재 16×16 시험본 |
|---|---:|---:|
| MZ 헤더 크기 | `0x4C00` | `0x4C00` |
| MZ 파일 영역 끝 | `0x41C20` | `0x42280` |
| 로드 모듈 상대 끝 | `0x3D020` | `0x3D680` |
| 초기 SS:SP | `3CFA:0080` | `3CFA:0080` |
| 최소 추가 문단 수 | 0 | 0 |
| MZ 재배치 항목 수 | 4,485 | 4,485 |

현재 모듈 끝에서 다음 세그먼트를 계산하는 값은 배치 후보일 뿐이다. Borland 시작 코드가 설정하는 실행 중 스택·힙·오버레이 메모리와 겹치지 않는다는 확인이 있어야 사용한다. MZ 헤더의 초기 SS:SP만으로 실행 중 스택 예약 범위를 확정하지 않는다. 기존 원본 런타임 기록에서도 시작 후 SP는 헤더 초기값과 다르다.

구현 빌더는 다음 순서로 하나의 배치 계획을 만든다.

1. 입력 프로필을 명시한다: 원본 영문 또는 확인된 16×16 한글 시험 프로필.
2. 기존 상주 코드·데이터·초기화 후 스택·힙·오버레이 예약 영역을 그려 새 코드의 소유 영역을 확정한다. 필요한 시작 코드/힙 경계 조정도 이 단계에서 함께 설계한다.
3. 치트 코드·상태·명령 표는 별도 소유 영역에 둔다. 임시 화면 백업은 앞 절의 9,216바이트 할당을 사용한다. 코드/상태의 최초 예산은 8 KiB이며 빌드 시 실제 크기를 검사한다.
4. 원본 입력 처리의 명령 경계를 확인해 FAR trampoline을 삽입한다. 덮어쓴 명령을 재실행하고 원래 후속 위치로 돌아간다. 레지스터·플래그·세그먼트·스택 정리는 확인한 호출 규약에 맞춘다.
5. 필요한 MZ 재배치 항목을 추가하거나 기존 항목을 새 피연산자 위치로 옮기고, 헤더 용량과 재배치 영역 충돌을 확인한다. 기존 폰트 콜백의 재배치가 남아 있다는 사실만으로 새 치트 호출의 세그먼트 재배치가 해결됐다고 간주하지 않는다.
6. MZ 페이지 필드·FBOV 시작 위치·패치된 오버레이 파일 오프셋을 최종 배치에서 다시 계산한다. 한글 패치로 이미 이동한 오버레이에 원본 파일 오프셋을 그대로 쓰지 않는다.
7. 기존 한글 후크·FNT 파일·문자열/메뉴 변경이 계획 밖에서 달라지지 않았는지 확인하고, 입력/출력 해시와 모든 변경 바이트를 보고서에 기록한다.

오버레이 후크가 필요하면 파일 오프셋·세그먼트 표 인덱스·원래 바이트로 식별한다. 과거 실행에서 관측한 CS 주소를 EXE에 고정하지 않는다. 현재 FNT 실측의 상주 재배치 값 `+0x824`도 새 실행의 절대 주소로 고정하지 않는다.

영문 치트 시험본은 `build/cheat-runtime/`, 한글과 결합한 시험본은 `build/cheat-hangul16-runtime/`에 각각 생성하도록 한다. 구현 전에는 이 경로를 실행 가능한 산출물로 안내하지 않는다.

| 단계 | 구현/분석 | 통과 기준 |
|---|---|---|
| 1 | 입력·메인 루프·모달/일시 정지·현재 플레이어·자금·승패 종료 분기 정적 추적 | 실제 명령 바이트, 호출 규약, 상태 수명, 메모리 소유 영역을 표로 확정 |

| 3 | 영문 시험 사본에 입력창과 인식기 추가. 효과는 진단 기록만 | 열기·문자·Backspace·오류·Enter·Esc·버퍼 경계·키 반복 및 게임 단축키 차단 확인 |
| 4 | `CREDITS` 연결 | 자금 증가·상한·HUD·실제 구매·저장/불러오기 확인. 적 가문 불변 확인 |

반드시 확인할 실패 조건은 입력창 중 재호출, 명령 자동 반복, 저장 이름에서 오발동, 취소 후 키가 게임으로 누출되는 현상, 불러오기 후 보류 명령 재실행, 화면 백업 할당 실패, 결과 전환 중 추가 입력이다. 기능 구현 뒤 필요한 범위로 검증하며, 설계 단계의 미실행 항목을 통과로 기록하지 않는다.

치트로 `WIN/LOSE`를 발생시키는 검증은 종료 처리 이후의 화면·폰트 경로를 검사한다. 정상 자원 목표·적 전멸·시간 제한 판정 전체를 검증한 결과와 구분해 기록한다.

## 8. 1차 구현 및 현재 검증 상태

### 산출물

치트 후크는 성공한 16×16 한글 시험본을 입력으로 받아 별도 트리에 생성한다. 원본 EXE와 한글 전용 시험본을 덮어쓰지 않는다.

| 항목 | 값 |
|---|---|
| 빌더 | [`build_dune2_cheat_runtime.py`](../../../archives/tools/README.md) |
| 후크 소스 | [`dune2-cheat-hook.asm`](../../../archives/tools/README.md) |
| 출력 EXE | `build/cheat-hangul16-runtime/source/VIRGIN/DUNE2/DUNE2.EXE` |
| 실행 BAT | `build/cheat-hangul16-runtime/run_cheat_hangul16_test.bat` |
| DOSBox-X 설정 | `build/cheat-hangul16-runtime/dosbox-x-cheat-hangul16.conf` |
| 패치 보고서 | `build/analysis/cleanup-2026-10-24/evidence/cheat-hangul16-runtime/cheat-patch-report.json` |

### 입력 및 등록 명령

실제 임무 플레이 화면에서 **Enter**로 입력창을 연다. 영문 명령을 입력하고 Enter로 실행하며, Backspace로 지우고 Esc로 닫는다. 입력 가능한 명령은 16자까지다.

| 명령 | 구현된 효과 |
|---|---|
| `CREDITS` | 현재 인간 플레이어의 자금 필드에 10,000을 더한다. 16비트 덧셈 오버플로 시 `FFFFh`로 포화하고 HUD 반영 필드도 갱신한다. |
| `WIN` | 기존 임무 승리 결과 분기를 요청한다. |
| `LOSE` | 기존 임무 패배 결과 분기를 요청한다. |

명령 표는 문자열 길이, 대문자 ASCII 문자열, 처리기 ID 형식이다. 새 명령은 표에 항목을 추가하고 처리기 분기를 구현하는 방식으로 확장한다. `CREDITS`, `WIN`, `LOSE`가 코드에 연결되었다는 정적 확인은 게임 안에서 효과가 검증되었다는 뜻과 다르다.

### 추가 정적 추적 근거

| 항목 | 확인값 |
|---|---|
| 현재 인간 플레이어 세그먼트 | 데이터 세그먼트 `3342:[3A30]` |
| 인간 플레이어 레코드 포인터 | 데이터 세그먼트 `3342:[3A2E]`의 FAR 포인터 |
| 자금 필드 | 현재 플레이어 레코드 `ES:[BX+12h]`, 16비트 |
| 자금 HUD 미러 | 데이터 세그먼트 `3342:[38A8]` |
| 키 입력 함수 진입 후크 | `27EC:0A54` |
| INT 09h 입력 분기 후크 | `27EC:0F0B` |
| 임무 결과 분기 후크 | `1223:0328`; 원래 승리 `032F`, 패배 `048D`로 전달 |
| MZ 로드 모듈 끝 | 기존 `0x42280` → 현재 치트 사본 `0x42C10` |
| 상주 모듈/스택 경계 | 모듈 세그먼트 `3D68`, 모듈 크기 `0x0990` (2,448바이트), 조정 스택 세그먼트 `3E01` |
| Borland FBOV 오버레이 | 새 로드 모듈 뒤로 이동했으며 바이트 내용은 그대로 보존 |

빌더는 입력 EXE/FNT 해시, 패치 지점의 원래 바이트, MZ 재배치표 확장, 새 페이지 필드, 오버레이 이동 및 원본/한글 전용 출력 파일의 비변경을 확인한 뒤 보고서를 작성한다.

### 아직 확인되지 않은 동작과 실행 방법

초기 EmuCap 시도에서는 DOSBox-X의 프레임 진행 요청이 `VRT` 시간 초과를 반환했고, DOS 프롬프트 일부까지만 관찰했다. 이 시도는 로딩 정지 원인을 확인하지 못했다. 아래의 재배치 수정 후 별도 관리 세대에서 타이틀 메뉴 진입까지 확인했지만, 실제 임무 진입·단축키·자금 변화·승패 결과는 아직 검사하지 않았다. 따라서 보고서의 `runtime_verified`는 `false`로 유지한다.

현재 빌드의 게임 실행 및 치트 효과는 사용자가 확인한다. [`run_cheat_hangul16_test.bat`](../../../build/analysis/cleanup-2026-10-24/evidence/cheat-hangul16-runtime/run_cheat_hangul16_test.bat)을 실행한 뒤 임무 플레이 화면에서 `Enter` → `CREDITS` → Enter로 입력/효과를 확인할 수 있다. `WIN`/`LOSE`는 임무 결과 전환을 확인할 때만 사용한다. 이 사본은 기존 DOSBox-X를 지정한 독립 설정을 사용한다.

현재 1차 구현은 입력창이 열린 동안 게임 시뮬레이션을 정지시키지 않는다. 또한 현재 임무 플레이어 포인터와 텍스트/Mode 13h 화면 모드로 진입을 제한하지만, 설계에서 요구했던 저장/불러오기·모달 화면별 차단과 원래 일시 정지 상태 보존은 아직 구현 또는 검증되지 않았다. 그러므로 이 빌드는 검토용 격리 시험본이며, 이 제한을 해결하고 위 표의 실제 효과를 확인하기 전에는 완성/검증된 패치로 간주하지 않는다.

현재 구현은 입력 화면과 후크를 실행 파일에 연결한 첫 단계다. 추가 명령 등록은 가능하지만, 각 효과는 주소·호출 문맥·상태 갱신을 분석한 뒤 개별 처리기로 추가해야 한다.


### 2026-10-20 로딩 정지 원인과 수정

사용자 실행 캡처에는 `Loading Dune II...`만 표시되고 게임 화면으로 넘어가지 않았다. 이 문구는 `GO.BAT`가 `DUNE2` 실행 직전에 출력하므로, DOSBox-X 설정이나 `SETUP.EXE` 단계가 아니라 EXE 시작 경로를 조사했다.

원인은 MZ 재배치표의 기존 항목이었다. 입력 한글 EXE에는 `0000:005E` 재배치가 하나 있으며, 원래 명령 `BF 42 33 8E C7`의 `mov di,3342` 즉시값을 대상으로 한다. 그 명령을 `EA 00 00 68 3D` far jump로 바꾸면서 기존 항목을 제거하지 않은 채 `0000:0060` 재배치를 추가했었다. DOS 로더는 남아 있던 `005E` 항목 때문에 새 far jump의 오프셋을 `0000` 대신 로드 세그먼트만큼 이동시킨다. 결과적으로 시작 후크 주소를 올바르게 가리키지 않는다. 이 바이트와 재배치표의 위치 관계로 특정되는 정적 원인이다.

빌더를 수정해 기존 재배치 항목 하나를 `0000:005E`에서 `0000:0060`으로 **이동**시키고, 다른 세 후크에만 새 재배치 항목을 추가했다. 수정 빌드의 재배치 수는 `4,485 → 4,488`이며, 정적 로더 시뮬레이션에서 far jump 오프셋은 `0000`을 유지하고 세그먼트만 시험 로드 기준 `2000 + 3D68 = 5D68`로 바뀌는 것을 확인했다. 출력 파일은 위 표의 새 SHA-256으로 재생성했다.

수정본은 설치된 DOSBox-X와 프로젝트의 외부 디버거 어댑터로 격리 실행했다. 720프레임 진행, Escape 입력(3프레임 누름), 추가 360프레임 진행 후 프레임 1203에서 타이틀 메뉴와 한글 메뉴 항목이 표시됐다. 720프레임 직후의 검은 화면은 이 검증에서 원본 실행 때도 같은 시점에 나왔고, Escape로 인트로를 넘기면 메뉴가 나타났다. 따라서 이전 `Loading Dune II...` 정지의 수정 후 시작 경로는 타이틀 메뉴까지 확인됐다. [검증 캡처](../../../build/analysis/cleanup-2026-10-24/evidence/cheat-hangul16-runtime/startup-menu-check.png), [기계 판독 검증 기록](../../../build/analysis/cleanup-2026-10-24/evidence/cheat-hangul16-runtime/startup-validation.json). 이 검증은 치트 입력과 명령 효과까지 보증하지 않으므로 `runtime_verified=false`는 그대로 둔다.

### 2026-10-20 처음하기 선택 때 발생한 메모리 오류

사용자가 제공한 `Insufficient memory error! Press any key to exit to DOS.` 캡처는 타이틀 메뉴 뒤 **처음하기를 선택할 때** 발생했다. `GO.BAT`를 그대로 실행해 두 빌드를 비교했다. 치트가 없는 16×16 한글 빌드는 프레임 1446에서 `Select your House` 화면에 도달했다. 기존 치트 빌드는 같은 프레임에 텍스트 모드로 전환했고, DOS 화면 메모리 `B800:0000`에 위 오류 문구가 실제로 기록되어 있었다. 따라서 이 문구는 DOSBox-X의 자체 메시지가 아니라 게임 실행 파일이 출력한 것이다. 사용자 시작 BAT의 `D2START.BAT` 조건도 확인했다. `DUNE.CFG`가 `DUNE.CFG.before-audio-setup`과 다르므로 `SETUP.EXE`를 건너뛰고 같은 `GO.BAT`를 호출한다.

MZ 헤더에서 `minalloc=0`, `maxalloc=FFFFh`를 확인했다. 오류 시점의 DOS 메모리 제어 블록은 `0813h`의 `M` 블록, 소유 PSP `0814h`, 크기 `9240h` 문단이었다. 기존 한글 실행 이미지 `3D680h`바이트에 치트 이미지가 `41D00h`바이트로 커져 `4680h`바이트(18,048바이트)가 추가됐다. 당시에는 이 이미지 증가량만으로 게임의 동적 할당 공간이 같은 양만큼 감소한 것이 직접 원인이라고 판단했으나, 이 설명은 후속 정적 대조에서 철회했다. 원본 시작 코드가 DOS 블록을 축소하고 스택·힙 경계를 다시 설정하는 동작까지 포함해야 실제 경계 이동량을 계산할 수 있다. 가문 선택 통과만으로 게임 도중 할당 실패까지 해결됐다고 판단할 수 없다.

화면 백업 버퍼는 9KB XMS 블록으로 옮기고, 모듈의 빈 주소 간격을 정리했다. 새 치트 모듈은 `0C50h`바이트이며 실행 이미지 증가는 3,152바이트로 줄었다(기존 실패 빌드보다 14,896바이트 감소). 출력 EXE SHA-256은 `cf3b1b0c96eac9439fe6c1a62454ef345a67439da23c79444c3341249d862c81`이다.

수정본도 동일한 `GO.BAT`로 실행해 프레임 1323의 타이틀 메뉴에서 처음하기를 선택했다. 잠깐 검은 로딩 화면을 지난 뒤 프레임 2046에서 `Select your House` 화면이 표시됐고, 메모리 오류는 재발하지 않았다. XMS 진입점 `C3FF:0010`, 핸들 `0001h`, 준비 플래그를 읽었고, 격리 실행 RAM에서 치트 창의 게임 상태 조건을 임시 충족시켜 화면 저장 호출이 성공하는 것도 확인했다. 이후 Escape로 창을 닫았으며 게임은 계속 실행됐다. 이 확인은 시작 메모리와 화면 백업 경로 검증이다. 실제 임무에서 `CREDITS`·`WIN`·`LOSE` 효과까지 검증한 것은 아니므로 `runtime_verified=false`를 유지한다. 자세한 수치와 실행 세대는 [메모리 오류 재현·수정 검증 기록](../../../build/analysis/cleanup-2026-10-24/evidence/cheat-hangul16-runtime/newgame-memory-validation.json)에 기록했다.

### 2026-10-20 치트 상주 메모리 추가 축소

이전 실행 기록의 3,152바이트 모듈(`0x0C50`)에서 고정 후크 진입점 사이의 미사용 간격을 제거하고, 실제 사용 스캔 코드 범위만 남겨 모듈 이미지 크기를 2,448바이트(`0x0990`)로 줄였다. 상주 이미지 증가량도 3,152바이트에서 2,448바이트로 704바이트(약 22.3%) 줄었다. 이 수치는 이미지 크기이며 전체 힙 경계 변화량은 아니다. 화면 백업은 기존처럼 9,216바이트 XMS 블록을 사용한다.

현재 출력 EXE SHA-256은 `e7b9665830b136f9649dfd50b8a21f3affad0a95f4dc89f6412b68a1515d1b49`이다. MASM 조립과 빌더의 정적 검사(후크 바이트·MZ 재배치·오버레이 보존)가 통과했다. 이는 빌드 구조 확인이며, 게임 내 메모리 부족 재발 여부나 치트 효과의 실행 확인을 뜻하지 않는다. 최신 빌드의 게임 실행 확인은 사용자가 진행한다.

### 2026-10-20 사용자 재발 보고 후 원본 정적 대조

사용자가 이 빌드에서 메모리 오류와 치트 창이 함께 표시된 캡처를 제공했다. 오류 처리기까지의 원본 경로, 초기 스택·힙 계산, 키보드 인터럽트 후크, XMS 성공 판정 및 화면 백업 범위를 정적으로 대조했다. 치트 시작 후크에 따른 초기 힙 경계 이동은 4,208바이트이며, 한글 전용 빌드의 추가 코드도 원본 스택 범위와 겹친다. 치트의 텍스트 모드 허용 조건은 오류 처리 중 Enter까지 가로챈다. XMS 성공 판정과 그래픽 패널 백업 범위에도 별도 결함이 있다. 구체적으로 어느 할당 크기·자유 블록 상태가 이번 오류를 일으켰는지는 정적 파일과 캡처만으로 특정하지 않았다. 상세 근거는 [원본 대조 보고서](cheat_memory_layout.md)와 [정적 증거 JSON](../../../build/analysis/cheat-static/evidence.json)에 기록했다. 이 대조에서는 게임 실행과 실행 파일 수정을 하지 않았다.

## 최신 적용: 게임 중에만 치트 Enter 허용 (2026-10-21)

당시 후보의 SHA-256은 `70798746e1a7b7d50a844aae559b4a354ee8dcc0b66fd2786bcbbdb22cda55fa`이며, 당시 루트 `듄2_치트테스트.bat`로 실행했다. 앞선 빌드 번호와 검증 기록은 해당 시점의 이력이다.

Enter 치트 진입은 정상 게임 진행 중에만 허용한다. 위젯·메뉴 처리 `044B:0317`과 단축키 명령 처리 `044B:03A9`의 원본 호출 안에서는 차단하고, 임무 결과·스코어 진입 `044B:03FD`에서도 해제한다. 저장 이름·스코어 이름 입력은 원래 키 처리기를 사용하도록 했다. 게임 시뮬레이션을 멈추는 기능을 추가한 것은 아니다.

이전 매 프레임 패널 지우기/다시 그리기는 사용자 확인에서 깜박임이 발생했다. 현재는 열린 패널을 유지하고 전장 행 복사가 패널 영역만 건너뛰며, 입력 변경 때 다시 그리고 닫을 때 최신 전장을 복원한다. 치트 XMS 추가 할당은 없고 모듈 크기는 `0x0990` 그대로다.

실제 EXE의 698개 명령에 대한 정적 검사와 행 복사 명령 모델 2,835건, 원본 UI 호출 인자·차단 상태 모델 2건을 통과했다. 게임은 실행하지 않았다. 실제 입력과 화면 결과는 사용자 확인 전이다. 상세 구현·한계·증거는 [치트창 소실 정적 역분석 8절](cheat_panel_redraw.md#8-깜박임-재보고와-게임-중-enter-제한-2026-10-21-최신-적용)에 기록했다.
