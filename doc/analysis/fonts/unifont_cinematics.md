# 오프닝·엔딩 유니폰트 FNT와 에디터 기본 적용

## 2026-10-25 유니폰트 구간의 부호도 함께 생성

사용자 지시에 따라 해당 구간의 부호도 달무리 대체 출력에서 유니폰트로 바꿨다. INTRO.ENG 1~37 및 DUNE.ENG 287~320의 실제 표시 문구에서 Unicode 부호·기호(P/S 분류)를 수집한다. 저장용 `\\r`·`\\n`은 제어 문자로 처리하므로 그 역슬래시는 불필요한 글리프로 넣지 않는다. 현재 필요한 부호는 `! , . ?` 네 개다. 이후 편집에서 콜론 등 다른 지원 부호를 추가하면 빌드 시 자동으로 포함된다.

현재 유니폰트는 한글 245개와 부호 4개, 총 249글리프다. Unifont 원본의 현재 네 부호는 8×16이며, 한글은 16×16이다. 기존 원본 Westwood 렌더러와 고정 128바이트 XMS 전송을 유지하기 위해 부호 비트맵은 16×16 셀의 왼쪽 8픽셀에 넣고 나머지를 0으로 채운다. 문자 전진 폭은 부호 원본의 8픽셀(현재 간격 -1이면 7)을 사용한다. 부호가 달무리의 8픽셀 높이·Y+8 경로로 빠지지 않으며, 실제 유니폰트 16픽셀 높이에서 기준선이 맞는다. 추후 원본 폭이 16인 지원 부호는 그 폭을 사용한다.

`DUNEUNI.MAP`은 이제 물리 글리프 슬롯별 XMS 위치를 담아 한글과 기존 부호 슬롯을 함께 가리킨다. 원문 ASCII·`%s`·`%d`·단축키 바이트는 재인코딩하지 않는다. 번역 문구의 INTRO.FNT 문맥에서 수집한 부호만 새 유니폰트 경로를 쓰며, 달무리 구간과 번역 없는 원본 ASCII 출력은 기존 처리를 유지한다. 문자 폭의 두 진입점(NewWidth·LatinSingleWidth), 글리프 출력과 전체 문자열 배치를 함께 연결했다.

제한 x86 검사에서 네 부호의 원본 유니폰트 비트맵과 폭, 혼합 문자열, `황제의 궁전에서...`의 마침표까지 전체 픽셀을 대조했다. 편집으로 콜론을 추가했을 때 FNT가 자동으로 한 글리프 증가하는 검사도 통과했다. 원본 ASCII 문구, 서식 처리, 단축키 58개, 달무리 픽셀 351경우, 2바이트 문자표, XMS 실패 정리·해제·재적재, 명예의 전당·지도 INI 검사도 통과했다. 게임 영상 재생 확인은 아직 하지 않았다.

## 음절 수집과 FNT 생성

소스는 `font/unifont-16.0.04.hex`이며 SHA-256은 `27256eb99d29545aa461e3b318d9fa9eec4b74f2ca8ede53d35e12bf5809fad7`이다. 이 파일의 U+AC00..U+D7A3 한글 11,172개는 각각 32바이트의 16×16 비트맵이다. **전체 범위를 게임 폰트에 저장하지 않는다.**

현재 CSV의 `INTRO.ENG` 1~19번(오프닝), 20~24번(아트레이데스 엔딩), 25~31번(하코넨 엔딩), 32~37번(오르도스 엔딩)에서 실제 사용하는 한글만 모아 중복을 제거하고 가나다순으로 정렬한다. 현재 필요한 음절은 151개다. 영문·숫자·부호를 유니폰트 FNT에 복제하지 않는다.

표준 Westwood 헤더·글리프 오프셋·폭·Y 오프셋/높이·4bpp 픽셀을 생성한다. 원래 16×16 비트맵을 확대·축소하지 않는다. 네이티브 FNT의 256슬롯 한도를 넘으면 `DUNEUN1.FNT` 등 다음 페이지로 자동 분리한다. 새 음절은 저장된 CSV를 읽는 다음 빌드에서 자동 반영하며, 공통 가나다순 번호가 바뀌면 달무리·유니폰트 문자표와 모든 리소스를 함께 다시 인코딩한다. 한글 토큰은 모두 2바이트다.

## 출력 경로와 엔딩 연결

현재 활성 원본 FNT의 헤더 길이 `1C24h`, 버전 `0500h`, 높이/폭 `19/17`이 원본 `INTRO.FNT`와 일치할 때 유니폰트를 선택한다. 한글 폭은 16픽셀에 원래 문자 간격을 더한다. 원본 `INTRO.FNT`는 그대로 두며, 영문·숫자·부호의 폭과 픽셀은 원래 폰트 경로를 사용한다. 다른 폰트 구간은 기존 달무리 경로다.

엔딩도 같은 애니메이션 초기화기를 호출하는 것을 원본 FBOV 테이블로 대조했다. 엔딩 오버레이 185(`32AE`)는 가문 분기에서 오버레이 199(`32F0`)의 공통 초기화 스텁 `0020`을 호출한다. 그 초기화기의 실제 코드 `00B2`는 `INTRO.FNT`를 로드하고 `00CC`는 해당 폰트를 선택한다. 하코넨 설명표 `DS:1A91`의 첫 문자열 번호는 25이며 현재 CSV의 엔딩 분류와 일치한다. 근거는 `build/analysis/unifont-intro/ending-font-path.json`이다. 이는 정적 호출 추적이며 실제 엔딩을 재생한 기록은 아니다.

실제 픽셀 출력은 기존 듄 드라이버 `DS:[66D8]`를 호출한다. 한 글자를 그릴 동안만 유효한 1슬롯 FNT를 드라이버 캐시에 연결하고, 원본 캐시의 9개 WORD를 모두 복원한다. 문자열 루프의 포인터·분할 순서·음성 호출은 변경하지 않는다.

## 메모리 배치

유니폰트 FNT와 위치표는 **XMS**에 둔다. 파일 데이터 총 22,855바이트와 홀수 파일 끝의 전송 패딩 1바이트를 포함해 22,856바이트를 사용하며, XMS 요청은 23KiB다. 첫 오프닝·엔딩 출력에서 파일을 256바이트씩 읽어 XMS로 옮기고, 각 글자를 출력할 때 위치표 4바이트와 4bpp 글리프 128바이트만 가져온다. XMS 이동 길이는 짝수로 맞춘다.

상주 영역에는 출력 코드·파일 목록·XMS 이동 구조체·257바이트 전송 버퍼·현재 글자용 153바이트 FNT 버퍼만 둔다. 전체 유니폰트 비트맵과 위치표를 상주시키지 않는다. 별도 DOS `AH=48h` 블록과 게임 FAR 힙 할당은 없다. 일반 폰트로 돌아갈 때 유니폰트 XMS 핸들을 해제하고, 나중에 엔딩 등에서 다시 필요하면 재적재한다. XMS·파일 적재가 실패하면 열었던 파일과 XMS 핸들을 정리하고 기존 달무리 출력으로 복귀한다.

달무리는 정상 확인한 2바이트 빌드와 같이 EXE의 `3D02h` 모듈에 내장한다. 현재 시험본의 폰트 모듈은 10,256바이트, 치트 세그먼트는 `3F83h`, 스택은 `401Ch`다. 원래 672글리프 입력 빌드 대비 상주 증가는 2,112바이트이고, 사용자 정상 확인한 688음절 달무리 2바이트 생성본 대비 추가 증가는 **1,424바이트**다. 치트 모듈을 다시 배치하고 MZ 재배치 피연산자 5곳을 갱신했으며 FBOV 오버레이 바이트는 보존했다.
