# Dune II 폰트 메모리 수명과 원본 할당 규약 역분석

작성일: 2026-10-20

## 1. 대상과 증거 범위

원본 `build/source/VIRGIN/DUNE2/DUNE2.EXE`의 SHA-256은 `99f44e83b309dd826f3dbc5068c61679bb68047eed8d738dcef594ba0eef7552`다. 아래 주소의 세그먼트는 로드 기준 상대값이다. 상주 코드는 DOS 재배치 후 로드 세그먼트를 더하며, 오버레이 주소는 해당 FBOV 모듈의 실제 코드 오프셋이다.

원본 폰트 로더 → 게임 공통 할당기 → Borland FAR 힙, 폰트 선택과 해제 규약을 정적으로 추적하고 현재 한글 로더와 대조했다. 게임·에뮬레이터 실행, EXE 및 후크 수정은 하지 않았다.

재현 도구: [analyze_font_memory_lifecycle.py](../../../archives/tools/README.md). 결과: [ownership-evidence.json](../../../build/analysis/font-memory/ownership-evidence.json), [호출 위치](../../../build/analysis/font-memory/direct-call-encodings.json), [폰트 상태 참조 후보](../../../build/analysis/font-memory/font-state-references.json).

9개 주요 명령열을 원본 바이트와 대조했다. 조사 대상 함수의 직접 FAR CALL 인코딩 125건은 앞쪽 프롤로그부터 재디코딩하여 명령 경계를 확인했다. 정규화된 포인터 오프셋 0~15의 정렬·해제 산술도 원래 포인터를 복원한다. 이는 정적 분석이며 모든 호출자의 도달 가능성이나 실행 중 메모리 상태를 입증하는 결과는 아니다.

## 2. 원본 FNT 적재

`2371:000E`는 FAR 파일명 포인터를 받아 다음 순서로 처리한다.

1. `1DB7:15BD`로 파일을 확인하고 `1DB7:0202`로 연다.
2. 앞의 2바이트를 읽어 전체 FNT 길이로 사용한다.
3. `2371:006B–0075`에서 길이와 플래그 `0010h`를 게임 공통 할당기 `21E5:000E`에 전달한다.
4. 반환된 **DX:AX 전체 포인터**를 보관하고, 앞의 길이 워드를 기록한 뒤 나머지 `길이-2`바이트를 `P+2`부터 읽는다.
5. 파일을 닫고 `P+2=00h`, `P+3=05h`를 확인한다. 성공하면 DX:AX를 반환한다.

원본도 폰트 데이터를 메모리에 적재하지만 별도의 DOS `AH=48h` 블록을 직접 만드는 방식은 아니다. 원본 할당기를 통해 FAR 힙에 넣는다.

현재 한글 파일의 앞 8바이트는 `44 32 48 46 4E 54 31 00`(`D2HFNT1\0`)이다. 원본 Westwood FNT와 형식이 다르므로 이 로더에 그대로 전달할 수 없다. 원본 로더는 헤더 불일치 시 NULL로 돌아가면서 이미 할당한 버퍼를 이 함수 안에서 해제하지 않는다. 첫 2바이트 읽기 실패 경로도 닫기 호출을 거치지 않는다. 사용자 정의 형식의 안전한 파서로 재사용해서는 안 된다.

별도의 일반 리소스 로더 `2341:0094`는 파일 크기를 조회하고 호출자가 준 플래그로 공통 할당기를 호출한 후 전체 파일을 읽는다. 형식 검사는 별도로 필요하며, 이를 사용할 경우 파일/PAK 계층과 오류 경로도 함께 확인해야 한다.

근거: [2371 디스어셈블리](../../../build/analysis/font-memory/original-2371.txt), [2341 디스어셈블리](../../../build/analysis/font-memory/original-2341.txt).

## 3. 게임 공통 할당기: 포인터는 세그먼트 하나가 아니다

`21E5:000E`의 FAR 호출 규약은 다음과 같다.

| 항목 | 규약 |
|---|---|
| DS | 게임 데이터 세그먼트, 로드 기준 `3342h` |
| `[BP+6]` | 요청 크기 하위 워드 |
| `[BP+8]` | 요청 크기 상위 워드 |
| `[BP+0Ah]` | 할당 플래그 |
| 반환 | DX:AX = 세그먼트:오프셋 |
| 인자 정리 | 호출자가 SP에 6을 더함 |
| 실패 | NULL 검사 후 등록된 `DS:[6D12]` 오류 콜백을 호출할 수 있음 |

플래그 `10h`는 요청한 데이터 길이만큼 0으로 지운다. `20h`는 반환 포인터를 문단 경계에 정렬하여 오프셋을 0으로 만든다. `40h`는 `244D:0340`의 다른 핸들 할당 경로를 선택하므로 일반 CPU 접근용 폰트 버퍼에 그대로 사용할 플래그가 아니다.

일반 경로는 `0000:1855`의 Borland FAR 할당기를 부른다. `20h`가 없으면 요청 크기에 관리용 1바이트를 더하고, 원시 포인터에 플래그를 기록한 뒤 **그 다음 바이트**를 반환한다. 새 FAR 블록의 원시 오프셋이 4인 경우 게임에 반환되는 오프셋은 5다. 따라서 `10h`로 호출하고 반환 AX를 버린 채 DX:0000부터 읽으면 버퍼 시작을 잘못 읽는다.

`20h`가 있으면 요청 크기에 16바이트를 더한다. 정규화된 원시 포인터를 `S:O`라고 할 때:

```text
padding = 15 - O
관리 바이트 주소 = S:(O + padding)
관리 바이트 값 = flags | padding
사용자 반환 포인터 = (S+1):0000
```

사용자 데이터 바로 앞에 원시 주소 복원용 정보가 남는다. 이 정렬 기능은 원본 화면 버퍼 할당에도 사용된다. `23C9:016F–017C`에서 `30h`를 조합해 공통 할당기를 부르는 경로를 확인했다.

근거: [할당 플래그와 반환 경로](../../../build/analysis/font-memory/allocator-flags.txt), [원본 화면 초기화](../../../build/analysis/font-memory/original-23C9.txt).

## 4. 공통 해제 함수와 짝을 맞춰야 한다

`21E5:01CC`는 FAR 포인터를 `[BP+6]=오프셋`, `[BP+8]=세그먼트`로 받고 호출자가 4바이트를 정리한다. NULL은 허용한다. 대체 핸들 여부를 먼저 검사하고, 일반 포인터는 데이터 직전의 관리 바이트를 읽는다.

- 비정렬 버퍼: 사용자 포인터에서 1바이트를 뺀 원시 주소를 `0000:1741`의 FAR 해제 함수에 넘긴다.
- 정렬 버퍼: 관리 바이트의 하위 4비트를 읽고 `(P.segment-1):(15-padding)`으로 원시 주소를 복원한 뒤 같은 FAR 해제 함수를 부른다.

따라서 공통 할당기에서 받은 **정확한 포인터**를 보관해야 한다. 데이터 내부를 가리키는 `P+2`나 임의로 바꾼 포인터를 해제 함수에 전달하면 관리 정보를 잘못 읽는다. 공통 할당기로 만든 버퍼에 DOS `AH=49h`를 사용하는 것도 규약에 맞지 않는다.

근거: [해제 함수 전체](../../../build/analysis/font-memory/deallocator.txt), [대체 핸들 검사](../../../build/analysis/font-memory/handle-detection.txt).

## 5. 선택은 소유권 이전이나 해제가 아니다

`240A:0006`은 새 FAR 포인터를 받아 활성 폰트와 폭·높이 메트릭을 바꾸고 **이전에 선택되어 있던 포인터**를 DX:AX로 반환한다. NULL이면 활성 상태를 교체하지 않는다. 이 함수는 이전 폰트를 해제하지도, 새 폰트를 할당하지도 않는다.

| 상태 | 데이터 세그먼트 슬롯 | 확인한 저장/사용 지점 |
|---|---|---|
| 기본 NEW8P | `9A7B:9A7D` (오프셋:세그먼트 슬롯) | `23C9:02DC/02E0` 저장, `0328` 선택 |
| 활성 폰트 | `9A7F:9A81` | `240A:0006`이 교체하고 이전 값 반환 |
| 폭 표 | `6CFE:6D00` | 활성 FNT의 `P+word[P+8]` |
| 높이/폭 | 바이트 `6CFD/6CFC` | `P+word[P+4]`의 +4/+5에서 읽음 |
| 작은 NEW6P | `3A20:3A22` | 실제 오버레이 `32BB:197C` 로드 후 `1983/1987` 저장 |
| INTRO | `80F0:80F2` | 실제 오버레이 `32F0:00B6` 로드, `00CC` 선택 |

INTRO 폰트는 `32F0:0187–018F`에서 보관한 전체 포인터를 공통 해제 함수에 전달한다. `32F0:0A99`의 선택은 INTRO 재선택이며 기본 폰트 복구로 해석하면 안 된다. 기본/작은 폰트의 명시적 해제 지점은 이번 참조 조사에서 특정하지 못했다. 이를 근거 없이 누수 또는 특정 시점 해제로 단정하지 않는다.

근거: [폰트 선택 함수](../../../build/analysis/font-memory/original-240A.txt), [INTRO 해제](../../../build/analysis/font-memory/intro-font-free.txt), [INTRO 재선택](../../../build/analysis/font-memory/intro-font-restore.txt). 마지막 파일명은 추출 당시 이름이며 기본 폰트 복원을 뜻하지 않는다.

## 6. 기존 한글 로더와 원본의 차이

기존 `build/hangul-runtime-16x16` 실행 파일에 포함된 `LoadHangulFont`는 DOS 파일을 열고 `AH=48h`, `BX=02B2h`로 11,040바이트를 별도 할당한다. 반환 세그먼트 하나를 저장하며 11,034바이트를 그 세그먼트의 오프셋 0부터 읽는다. 읽기 길이 불일치 때만 `AH=49h`로 해제한다. 성공한 폰트는 프로세스 수명 동안 유지한다. 현재 소스의 메모리 수정은 7절에 기록했다.

최초 16×16 빌드가 이 방식을 사용했다. 별도 폰트 블록은 원본 힙에 포함되지 않으며 PSP 블록 바로 뒤에 놓이면 게임의 `AH=4Ah` 연속 확장을 막는다. 2026-10-21 사용자가 제공한 MCB 목록에서 이 조건과 일치하는 실제 배치를 확인했다. 상세 수치와 실행 중 크기 변경 요청은 [치트 메모리 오류 정적 대조](../cheats/cheat_memory_layout.md)의 8절에 기록했다.

상세 실패 분기와 정적 산술 예시는 [치트 메모리 오류 정적 대조](../cheats/cheat_memory_layout.md)의 8절에 있다. 같은 문서의 상주 코드/스택 겹침과 치트의 추가 예약 문제도 별도로 해결해야 한다. 폰트 할당 방식 하나만 고치면 모든 치트 오류가 없어진다고 결론 내릴 수 없다.

## 7. 수정판 1: 게임 FAR 힙 할당과 당시 판단의 정정

첫 메모리 수정판 `build/hangul-runtime-16x16-memoryfix`는 별도 DOS MCB를 만들지 않도록 `21E5:000E` 게임 FAR 할당기를 사용했다. 그러나 11,034바이트를 게임의 제한된 conventional-memory 힙에서 계속 차지했다. 별도 MCB를 피하더라도 이 메모리 비용은 남으므로 이후 XMS 방식으로 변경했다. 당시 오류 재발 보고만으로 이 수정판이 불충분하다고 판정했으나, 이후 사용자 덤프에서는 구형 DOS 로더가 실행 중이었음을 확인했다. 따라서 그 재발 보고로 FAR 힙 수정판의 실행 실패를 입증할 수는 없다.

## 8. 현재 수정판: 비트맵을 XMS에 배치

현재 동일한 격리 프로필을 XMS 배치로 다시 만들었다. 폰트 파일 구조는 그대로 유지한다.

- 파일 헤더와 조합 선택표 1,530바이트(합계 1,554바이트)는 EXE의 상주 후크 세그먼트에 둔다.
- 316개 구성 글리프 비트맵 9,480바이트는 XMS `AH=09h`로 확보한 10 KiB 핸들에 둔다.
- 화면에 글리프를 그릴 때마다 해당 30바이트 구성 글리프만 XMS `AH=0Bh`로 256바이트 상주 scratch 영역 안으로 이동한다.
- DOS `AH=48h` 별도 블록이나 게임 FAR 힙 폰트 할당은 하지 않는다. 적재 중 짧은 파일 읽기 또는 XMS 이동 실패 시 부분 적재 핸들을 해제한다.
- 로더는 `D2HFNT1` 헤더의 매직, 치수, 구성 요소 수와 조합 규격을 검사한다.

정적으로 확인한 출력 배치:

1. 수정된 실제 코드 `3D02:0550–07AC`는 DOS 파일 읽기와 XMS `AH=09h`, `AH=0Bh`, 실패 시 `AH=0Ah`를 사용한다. 폰트용 `AH=48h`/`AH=49h` 및 `21E5:000E` 호출은 없다.
2. 실행 후크 이미지는 `0xF20`바이트다. 선택표는 `0800h–0E11h`, 256바이트 전송 버퍼는 `0E20h–0F1Fh`에 있다. 어셈블된 코드 범위와 두 데이터 영역의 중첩을 빌더가 검사한다.
3. 내장 선택표 1,554바이트가 원본 `DUNEHAN.FNT` 선두 1,554바이트와 일치하고, 나머지 9,480바이트가 정확히 `316 × 30`이다.
4. 현 DOSBox-X 설정은 XMS를 켠다. 실제 DOS에서는 XMS 관리자가 필요하다.
5. 이 레이아웃은 기존 FAR 힙판의 11,034바이트 런타임 할당을 없애는 대신 후크 이미지가 2,368바이트 커진다. 따라서 conventional-memory 절감은 정적 산술상 약 8,666바이트이며, 실행 중 MCB/힙 사용량으로 측정한 값은 아니다.

최신 시험 실행 파일은 `build/cheat-hangul16-runtime-memoryfix/source/VIRGIN/DUNE2/DUNE2.EXE`이며 SHA-256은 `67a26ffb3f586db63d205735047401446bec7f0d231588d715e655c866d7a1be`이다. 루트 `듄2_치트테스트.bat`이 `build/cheat-hangul16-runtime-memoryfix/run_cheat_hangul16_test.bat`으로 연결된다. 작업 에이전트는 DOSBox-X를 실행하지 않았다. 2026-10-21 사용자는 최신판 실행 안내 후 “lose를 사용해도 문제없이 진행된다”고 확인했다. 최신판의 MCB 배치와 실제 메모리 절감량은 아직 측정하지 않았다. 성공 세션의 실행 코드 덤프는 별도로 수집하지 않았다.

기존 XMS판(`ca34cd…`)에는 이동 구조체의 길이를 WORD로 취급한 결함이 있었다. XMS의 실제 구조는 DWORD 길이와 WORD 핸들이므로 필드 위치는 `0/4/6/10/12`여야 한다. 2026-10-21 재점검에서 업로드·다운로드 코드를 수정했다. [정적 ABI 검사](../../../archives/tools/README.md)는 실제 EXE에 들어간 기계어의 메모리 기록을 제한적으로 해석하여 이전 결함을 재현하고, 수정판의 38개 파일 청크와 316개 구성 요소 이동 요청·페이로드를 확인한다. 이 검사 자체는 XMS API나 게임을 실행하지 않는다. 치트를 사용하지 않아도 오류가 났다는 당시 보고는 이후 덤프에서 구형 DOS 로더 실행으로 확인됐으므로 최신 XMS판의 실패 증거로 사용하지 않는다. 이 XMS 결함과 구형 실행의 conventional-memory 오류 사이 직접 인과관계도 입증되지 않았다. 실제 덤프와 LOSE 사용자 확인은 [치트 메모리 오류 정적 대조](../cheats/cheat_memory_layout.md)의 15–16절을 참조한다.

## 9. 남은 경계

이번 분석은 폰트 파일의 메모리 소유권·포인터·정렬·해제 규약을 구체화했다. 전체 엔진의 모든 출력 호출과 수명, 모든 간접 호출을 완전히 검증했다는 의미는 아니다.

사용자가 제공한 2026-10-21 관측으로 실제 메모리 요청 크기와 MCB 상태는 확인했다. 호출 뒤 CF/AX와 수정판의 MCB 배치는 아직 확인하지 않았다. 기존 전체 FNT 문서의 오버레이 주소 해석 오류도 아래와 같이 정정한다.

- FBOV flags=3 항목의 표 크기는 상주 스텁 크기다. 실제 코드 크기와 위치는 스텁 내부의 페이로드 정보를 사용해야 한다.
- 같은 세그먼트의 중복 레코드는 충분한 실제 코드 범위를 선택해야 한다.
- 예: 과거 NEW6P `31F7:03EB` 표기는 실제 모듈 기준 `32BB:197C`로 정정한다. 파일 오프셋 `49A7Ch`는 같다.
- 이 문서와 분석기는 [수정된 코드 범위](../../../build/analysis/cheat-static/code-ranges.json)를 사용한다. 과거 오버레이 논리 주소와 호출 총계를 그대로 최종 증거로 재사용하지 않는다.
