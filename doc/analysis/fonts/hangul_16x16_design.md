# Dune II 16×16 한글 폰트 적용 설계

분석일: 2026-10-20  
상태: 15×15 저장 글리프를 16×16 셀의 (1,1) 위치에 출력하는 격리 시험본을 준비했다. 원본 게임과 정상 출력된 10×10 시험본은 유지했다. DOSBox-X는 실행하지 않았다.

## 목표와 유지 조건

- 사용자가 제공한 `font/unifont-16.0.04-minimized-316-selfcontained.fnt`의 16×16 구성 글리프와 조합표를 그대로 쓴다. 크기 조절이나 잉크 픽셀 제거 없이, 각 15×15 저장 글리프를 16×16 셀의 (1,1)에서 그린다.
- 원본 `INTRO.FNT`, `INTRO.PAK`, `DUNE.PAK` 글꼴은 그대로 둔다. 한글 구성 글리프는 별도 `DUNEHAN.FNT`에서 읽는다.
- 이미 정상 출력이 확인된 10×10 시험본은 유지한다. 16×16은 별도 산출물과 별도 게임 사본으로 만든다.
- 문자열의 2바이트 한글 토큰 형식과 조합 인덱스 계산은 변경하지 않는다.

## 확인된 입력 자료와 규격

`unifont-16.0.04-minimized-316-selfcontained.fnt`는 11,666바이트다. 헤더는 16×16, 316개 구성 글리프, 초성 19종·중성 21종·종성 28종을 선언한다. `font/compose.py`는 이미 16×16 비트맵을 읽고 L/V/T 선택표대로 OR 조합할 수 있다.

FNT의 데이터 배치는 다음과 같다.

| 영역 | 크기 |
|---|---:|
| 헤더 | 24바이트 |
| 초성 배치 클래스 두 표 | 42바이트 |
| L/V/T 글리프 선택표 | 1,488바이트 |
| 글리프 비트맵 316 × 32바이트 | 10,112바이트 |
| 합계 | 11,666바이트 |

원본 316개 구성 글리프는 모두 첫 행과 첫 열이 빈 픽셀임을 확인했다. 새 게임용 파일은 선택표를 그대로 복사하고, 저장 비트맵에서 그 빈 첫 행·열만 생략해 15×15로 만든다. 렌더러는 이를 셀 원점에서 X/Y 각 1픽셀 안쪽에 그려 원본 잉크 좌표를 복원한다. 파일 헤더는 15×15이며 결과는 `font/dune2-hangul-compose-15x15-cell16.fnt`다. 기존 10×10 파일과 이전 16×16 파일은 덮어쓰지 않는다.

## 현재 후크에서 바뀌어야 할 값

현재 `tools/hangul-render-hook.asm`은 크기를 여러 위치에 즉시값으로 넣고 있다. 새 시험 프로필은 15×15 저장 글리프를 (1,1) 위치에서 그리되 문자 전진 폭과 메뉴 행 간격은 16픽셀로 둔다.

| 후크 위치/동작 | 현재 10×10 값 | 16×16 설계값 |
|---|---:|---:|
| `WidthLookup`의 한글 셀 폭 | 10 | 16 |
| 정·역방향 `StringWidthLookup`의 한글 셀 폭 | 10 + 글꼴 간격 | 16 + 같은 글꼴 간격 |
| `DrawComponent`의 셀 원점 검사 | X `< 311`, Y `< 191` | X `< 305`, Y `< 185` |
| 구성 글리프 데이터 주소 | `1554 + index × 20` | `1554 + index × 30` |
| 행 반복 횟수 | 10 | 15 |
| 행당 픽셀 반복 횟수 | 10 | 15 |
| 320픽셀 화면의 다음 행 이동 | 310 | 305 |
| 구성 글리프 행 저장 | 2바이트 | 2바이트, 최하위 비트는 저장 여분 |
| 한글 FNT 로드 길이 | 7,874바이트 | 11,034바이트 |

화면 원점 한계는 320×200 화면에 16×16 셀 전체가 들어오도록 계산했다. 셀 원점 X=304, Y=184까지 글리프는 각각 305..319, 185..199에 그려져 화면 안에 들어온다. 셀 원점이 `X >= 305`, `Y >= 185`일 때는 생략한다. 15픽셀을 쓴 뒤 `DI`에 305를 더하면 다음 행 시작까지 총 320바이트 이동한다.

15픽셀 폭은 한 행에 2바이트로 저장한다. 원본 각 행의 x=0 비트는 0이므로 15비트 창을 만들 때 x=0을 생략하고, 출력 시작점에 1을 더해 원본 x=1..15 위치를 그대로 되살린다. 원본 y=0 행도 0이어서 같은 방식으로 y=1..15를 보존한다. 따라서 축소·잉크 손실 없이 15×15 FNT 데이터와 16×16 셀 전진 폭을 함께 쓴다.

## 메모리와 파일 로더

현재 후크는 DOS 메모리 할당에 `0x02B2` 문단(11,040바이트)을 요청한다. 11,034바이트 폰트와 6바이트 여유를 담는다. 파일 읽기 길이와 읽기 완료 비교는 `11,034`다. 빌더는 파일 길이, 매직·버전·15×15 헤더, 글리프 수, 선택표 개수를 확인한 뒤 별도 시험 사본에 배치한다.

## 메뉴 폭과 세로 배치

메뉴 스크린샷에서 16픽셀 한글 글자 면이 기존 메뉴 행 배치와 맞지 않았다. 정적 역분석 결과, 메뉴 상자 높이·세로 중앙 계산과 메뉴 행 Y 이동은 `DS:[6CFD]` 값을 사용하며, 한글 후크의 글리프 크기를 자동으로 반영하지 않는다. 확인한 명령 위치는 원본 `DUNE2.EXE` 파일 오프셋 `0x4A04F`, `0x4A060`, `0x5050D`, `0x505CD`이며 네 곳 모두 `mov al,[6CFD]` (`A0 FD 6C`)이다. 이 값이 각각 상자 크기, 상자 기준 위치, 메뉴 행 pitch, 선택 행 위치 계산으로 들어간다.

16×16 메뉴 셀과 계산 단위를 맞추기 위해 격리 시험본에서 네 3바이트 명령을 각각 `mov al,16` + `nop` (`B0 10 90`)으로 바꾼다. 메뉴 상자 높이 계산(`16 × 항목 수 + 11`), 행 간격, 선택 행 위치가 모두 16을 사용한다. 영문 글꼴 설정이나 원본 `INTRO.FNT`는 변경하지 않는다.

가로 폭은 기존처럼 2바이트 토큰 하나를 글자 하나로 세되 셀 폭 16을 반환한다. 메뉴 폭 계산과 중앙·우측 정렬의 정방향·역방향 문자열 폭 조회는 `16 + DS:[6CF8]`를 반환한다. 메뉴 패널 폭은 이 폭으로 재계산한다. 토큰 trail 바이트 소비는 기존 2바이트 규칙을 유지한다.

### 메뉴 박스 내부가 검게 남는 원인 — 정적 역분석 확정

원본 화면의 제목 배경은 검정이고, 회색 박스 내부는 별도 CG 파일이 아니라 메뉴 UI의 채우기 루틴이 그린다. 메뉴 오버레이 파일 오프셋 `0x4A13C`는 `0A0:057F`를 `(1, 2, 13)` 인자로 호출한다. 이 함수는 메뉴 사각형 `DS:[4126..412C]`를 읽고 `0A0:0008` 프레임 헬퍼를 호출한다. 헬퍼는 채우기를 먼저 수행하고, 그 다음 테두리 선을 따로 그린다.

채우기는 데이터 함수 포인터 `3342:[66F4]`가 가리키는 `20AA:0D3B`로 간다. 이 함수는 화면 끝 좌표를 포함형으로 받는다. `x2 >= 320` 또는 `y2 >= 200`이면 픽셀을 쓰기 전에 반환한다. 반면 테두리 선은 별도 호출이므로 채우기 실패 뒤에도 보일 수 있다. 그 결과 화면 바탕색 검정이 박스 안에 남는다.

16×16 셀을 쓰는 네 항목 메뉴의 박스 높이는 `16 × 4 + 11 = 75`픽셀이다. 기준점 158이었던 이전 값은 위쪽 126, 포함형 아래쪽 200이어서 채우기 함수의 `y2 >= 200` 검사에 걸렸다. 기준점 157 시험값은 위쪽 125, 아래쪽 199다. 이번 요청에 따라 거기서 2픽셀 더 올려 현재 기준점은 155이며, 박스 위쪽 123, 포함형 아래쪽 197이다. 계산상 채우기 함수의 범위 안이다.

색상값도 코드와 팔레트에서 확인했다. 프레임 헬퍼의 스타일 3 첫 색은 팔레트 인덱스 `E9`; `IBM.PAL`의 6비트 `(44, 44, 49)`를 VGA 8비트로 확장하면 화면 RGB `(178, 178, 199)`가 된다. 같은 스타일의 테두리 색 `E8`은 흰색, `EB`는 RGB `(85, 85, 121)`로 스크린샷의 밝은 테두리와 그림자색에 맞는다. 따라서 검정은 한글 글꼴 색상 변경이나 메뉴 박스 CG 누락이 아니라, 이전 좌표에서 내부 채우기만 경계 검사로 거부된 결과다.

이 결론은 원본 EXE 오버레이·함수 포인터·팔레트의 정적 역분석이다. 사용자는 이후 시험본에서 한글 선택문이 정상 출력됨을 확인했다. 회색 채우기 색상 자체를 별도로 확인했다는 보고는 없으므로 `panel_fill_static_analysis.runtime_verified`는 `false`로 유지한다.

## 게임 전체 적용 전의 줄 높이 조사

메인 메뉴에서 16×16이 들어가는 것만으로 모든 게임 화면의 줄 배치가 검증되는 것은 아니다. 원본 게임에는 서로 다른 크기의 `NEW6P.FNT`, `NEW8P.FNT`, `NEW10P.FNT`, `STD3P.FNT`가 있으며, 조사 자료의 해당 폰트에서 시험 문자 D0–D3 글리프 높이는 각각 8, 10, 9, 4픽셀이다. 텍스트 호출부에 따라 기준 줄 간격도 달라질 수 있다.

따라서 엔진 전체에 16픽셀 높이를 무조건 적용하지 않는다. 각 한글 문자열 출력 경로에서 실제 폰트 선택, Y 기준선, 줄 이동, 클리핑 사각형, 대화 상자·버튼·표 행의 크기를 먼저 매핑한다. 줄 간격이 16보다 작은 다중 행 영역은 그 영역의 한글 텍스트 레이아웃을 별도로 조정하거나 해당 영역에 맞는 표시 방식을 설계한 뒤 적용한다. `DS:[6CFD]`를 전역으로 16으로 덮어쓰면 영문 행 배치와 상자 크기까지 바뀌므로 사용하지 않는다.

### 2026-10-20 사용자 실행 확인 — 한국어 메인 메뉴

사용자가 DOSBox-X에서 16×16 시험본을 실행해 아래 네 선택문이 한글로 정상 출력됨을 확인했다. 네 문구는 `DUNE.ENG`의 지정 항목을 2바이트 한글 조합 토큰으로 바꾼 것이다.

| `DUNE.ENG` 인덱스 | 원문 | 시험 번역 |
|---:|---|---|
| 27 | Play a Game | 처음하기 |
| 28 | Replay Introduction | 오프닝 다시 보기 |
| 92 | Load a game | 불러오기 |
| 29 | Exit Game | 종료하기 |

실행 확인 기록은 `build/analysis/cleanup-2026-10-24/evidence/hangul-runtime-16x16/menu-labels-test.json`과 `patch-report.json`에 남겼다. 이 확인은 한글 선택문 출력에 대한 사용자 실행 결과다. 메뉴 채우기 픽셀 경계 분석의 별도 실행 검증 여부는 해당 정적 분석 항목에 따로 표시한다.

16×16 후크는 15×15 FNT 저장 글리프, (1,1) 출력 시작점, 16픽셀 셀 간격, 30바이트 글리프 간격, 화면 가장자리 검사, 파일 읽기 길이를 반영한다. 격리 시험본 메뉴 전용 오버레이에서만 네 행 높이 참조를 16으로 바꾼다. 원본 게임과 10×10 시험본은 유지한다.

**현재 런타임 상태:** `build/analysis/cleanup-2026-10-24/evidence/hangul-runtime-16x16/patch-report.json`의 `runtime_verified`는 한글 메인 메뉴 네 항목의 정상 출력을 사용자가 DOSBox-X에서 확인한 사실을 반영한다. 이 확인은 사용자 실행 결과이며, 어시스턴트가 DOSBox-X를 실행한 결과가 아니다. 메뉴 채우기 색상의 별도 확인 상태는 `panel_fill_static_analysis.runtime_verified`에 분리해 기록했다.

## 남은 적용·검증 순서

1. 메인 메뉴 네 한글 선택문의 출력 검증은 완료했다. 글리프 여백, 선택 색상, 화면 가장자리 등 별도로 기록되지 않은 세부 항목은 추가 UI 적용 때 확인한다.
2. 한글 문자열을 사용하는 다른 UI의 출력 경로와 실제 줄 간격을 정적으로 매핑한다.
3. 줄 간격이 16보다 작은 UI는 텍스트별 레이아웃 수정과 별도 확인을 거친 뒤에 전체 적용 범위를 확장한다.

## 완료 기준

- 15×15 시험 FNT의 선택표가 사용자 원본과 같고, 각 글리프를 (1,1)에서 출력했을 때 11,172개 음절이 16×16 원본과 모두 일치한다.
- 11,172개 조합 결과가 16×16 기준 결과와 전수 일치하고 PNG로 육안 확인할 수 있다.
- 게임 내 한글 가로 이동이 16픽셀+원래 글꼴 간격과 일치하며, 메뉴 폭·정렬이 문자열 폭 계산과 맞는다.
- 화면 우·하단에서 16×16 셀이 화면 메모리 밖으로 쓰이지 않는다.
- 줄 간격이 16픽셀보다 작은 게임 UI는 레이아웃 조정 전까지 전체 적용 완료로 표시하지 않는다.
- 10×10 검증 사본과 원본 게임 폰트 파일의 해시가 전과 동일하다.

## 2026-10-21 Hall of Fame 포함 다섯 항목 메뉴 수정

원본의 메뉴 높이는 `16×항목 수+11`, 위쪽은 `기준점−(16×항목 수)/2`다. 이전 기준점 155에서 다섯 항목은 위쪽 115, 높이 91, 포함형 아래쪽 205였다. 요청대로 기준점만 150으로 옮기면 위쪽 110, 아래쪽 200이다. 원본 채우기 `20AA:0D3B`는 Y2가 200 이상이면 사각형 전체를 그리지 않기 때문에 5픽셀 이동만으로는 해결되지 않는다.

## 2026-10-21 사용자 확인 — 명예의 전당 정상 출력

`Hall of Fame`을 `명예의 전당`으로 변경한 뒤 사용자가 **“잘 나온다”**고 보고했다. 따라서 메인 메뉴의 `DUNE.ENG[334]` 번역 출력은 사용자 실행으로 확인된 상태다. 이 작업에서 에이전트가 게임을 실행한 것은 아니다.
